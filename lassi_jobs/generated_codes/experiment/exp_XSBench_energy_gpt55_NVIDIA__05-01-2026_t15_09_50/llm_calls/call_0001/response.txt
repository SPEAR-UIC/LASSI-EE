## Key actionable CUDA energy-efficiency techniques for NVIDIA A100- **Coalesce global memory accesses**  - Arrange data so consecutive threads in a warp access consecutive addresses.  - Prefer Struct-of-Arrays over Array-of-Structs when each thread reads the same field.  - Avoid strided patterns such as `arr[threadIdx.x * N + j]`; prefer layouts like `arr[j * blockDim.x + threadIdx.x]`.  - **Most impactful when:** the kernel is memory-bound or Nsight Compute shows poor global load/store coalescing or high DRAM traffic.- **Use shared memory for reused data**  - Cooperatively load reusable global-memory tiles into shared memory once per block, then reuse them from on-chip SRAM.  - Avoid shared-memory bank conflicts by ensuring warp threads do not repeatedly access addresses mapping to the same bank.  - On A100, use the large configurable shared memory capacity when beneficial, but watch occupancy.  - **Most impactful when:** multiple threads in a block reuse the same or nearby data, such as tiled stencils, matrix-like access patterns, reductions, or shared lookup data.- **Tune occupancy**  - Use block sizes that are multiples of 32; 128–256 threads per block is often a good starting point on A100.  - Balance occupancy against register use and shared-memory use.  - Avoid register spilling, because spilled “local” memory resides in global memory and increases DRAM energy.  - Use the CUDA occupancy calculator, `cudaOccupancyMaxPotentialBlockSize`, and optionally `__launch_bounds__`.  - **Most impactful when:** the kernel has latency from memory accesses or insufficient active warps to hide stalls, but not when increasing occupancy causes spilling or reduces cache/shared-memory efficiency.- **Reduce warp divergence**  - Keep threads in the same warp on the same control-flow path.  - Replace short divergent branches with predication, ternary selection, or branchless arithmetic where appropriate.  - Group or sort inputs so warps process similar work when possible.  - Keep unavoidable divergent regions small.  - **Most impactful when:** branch paths are long, data-dependent, or frequently differ across threads in the same warp.- **Fuse kernels when possible**  - Combine consecutive kernels that operate on the same data so intermediate values stay in registers or shared memory instead of being written to and reread from DRAM.  - Also reduces kernel-launch overhead.  - Do not fuse if it creates excessive register pressure, lowers occupancy too much, or breaks synchronization/data-dependency requirements.  - **Most impactful when:** kernels are memory-bound, use intermediate arrays, or launch many small kernels.- **Use read-only cache paths with `__ldg` or `const __restrict__`**  - Mark read-only input arrays as `const __restrict__`.  - Use `__ldg(&arr[i])` for explicit read-only loads when appropriate.  - This can reduce L2/DRAM pressure by using the read-only/texture cache path.  - **Most impactful when:** arrays are read-only within the kernel and have spatial or temporal locality; it can still help for irregular read-only lookup tables.- **Choose arithmetic precision carefully**  - Use `float` instead of `double` when accuracy requirements allow.  - Prefer FP32/FP16/BF16/Tensor Core paths where numerically valid.  - Use fast math intrinsics such as `__expf`, `__sinf`, `__fdividef` only when their reduced precision is acceptable.  - Use FMA (`fmaf`, compiler-generated FMA) to reduce instruction count and improve accuracy.  - **Most impactful when:** the kernel is compute-bound, uses many FP64 operations, or moves large arrays whose size can be reduced by using lower precision.- **Minimize synchronization**  - Avoid unnecessary `__syncthreads()`, especially inside loops.  - Use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or `__reduce_sync` when only warp-local coordination is needed.  - Reduce high-contention atomics by doing block-level or warp-level reductions first, then issuing fewer global atomics.  - **Most impactful when:** barriers or atomics appear in hot loops, reductions, histograms, or highly contended update patterns.- **Use prefetching and transfer overlap carefully**  - Keep data resident on the GPU across multiple kernel launches.  - Prefer explicit `cudaMalloc`/`cudaMemcpy` over unmanaged page migration when possible.  - If transfers are required, use pinned host memory and `cudaMemcpyAsync` in streams to overlap transfers with computation.  - If using Unified Memory, prefetch data to the GPU before kernels to avoid page-fault-driven migration during execution.  - **Most impactful when:** host-device transfers, Unified Memory migrations, or predictable data movement contribute significantly to runtime and energy.
