## 1. Overall algorithm and GPU resource utilization profile### Algorithm- The profiled workload is an event-based XSBench-style macroscopic cross-section lookup simulation.- Each lookup:  1. Generates or reads a sampled neutron energy.  2. Generates or reads a sampled material ID.  3. Computes a macroscopic cross-section vector with 5 reaction channels.  4. For every nuclide in the selected material, performs a microscopic cross-section lookup and interpolation.  5. Accumulates the microscopic values multiplied by nuclide concentration.  6. Writes a small verification value to global memory.- Materials have highly uneven nuclide counts:  - Fuel material has many nuclides: 34 for small, 321 for large/default.  - Other materials have 4–27 nuclides.- This creates severe per-thread workload imbalance when neighboring threads choose different materials.### Resource utilization profile- The dominant cost is irregular global-memory access plus control-flow divergence.- The lookup phase is generally memory-latency-bound rather than peak-bandwidth-bound or compute-bound.- Arithmetic intensity is low to moderate:  - Each microscopic lookup loads two `NuclideGridPoint` records.  - Each `NuclideGridPoint` contains 6 doubles, so two points imply up to 96 bytes of cross-section/energy data per nuclide, before counting index-grid, concentration, and material-list accesses.  - Only a small number of floating-point interpolation operations are performed per loaded byte.- On an A100, the double-precision arithmetic itself is unlikely to be the primary bottleneck for the lookup kernels; the larger issue is random access, cache inefficiency, and warp divergence.- The sampling phase has more integer arithmetic due to fast-forwarding the LCG RNG and is less memory-intensive. It writes sequential sample arrays and is comparatively well-behaved.- The baseline kernel combines sampling and lookup in one kernel, which avoids intermediate global writes but mixes RNG work, material selection divergence, and cross-section lookup divergence in a single execution path.- Optimized variants split sampling from lookup and then group or sort by material and/or energy. These variants are primarily energy-efficiency optimizations because they reduce wasted warp lanes, improve cache reuse, and reduce random-access entropy.### Access type summary- Sampling arrays and verification arrays are accessed sequentially and coalesced.- Cross-section data, index grids, and binary-search energy grids are accessed irregularly.- Sorting by material improves control-flow uniformity.- Sorting by material and energy improves both control-flow uniformity and memory/cache locality.### Main energy-efficiency opportunities- Group work by material to reduce warp divergence from different nuclide-count loops.- Group work by energy to improve locality in the unionized grid, index grid, and nuclide grid.- Use smaller precision where scientifically valid.- Move small read-only tables to constant memory or shared memory.- Consider structure-of-arrays layout for cross-section fields if not all fields are always needed.- Reduce repeated global-memory reads of material composition and concentration data.- Avoid launching kernels that scan the entire lookup array while most threads immediately return.- Use larger blocks than 32 threads where possible to improve A100 occupancy, unless the one-warp block design is intentionally used for scheduling reasons.---## 2. CUDA kernel launch configurations and likely A100 occupancy### Baseline#### `xs_lookup_kernel_baseline`- Launch configuration:  - Threads per block: 256  - Blocks: `ceil(in.lookups / 256)`- A100 occupancy expectation:  - 256-thread blocks are generally a good occupancy choice on A100.  - Theoretical occupancy can be high if register usage is moderate.  - Actual occupancy may be reduced by register pressure from local arrays, double variables, inlined device functions, and binary-search state.  - Despite reasonable occupancy, latency hiding is limited by highly divergent and random memory access.- Energy-efficiency note:  - High occupancy alone does not solve the random-access bottleneck.  - The baseline wastes energy due to warp lanes doing very different amounts of work depending on material.---### Optimization 1#### `sampling_kernel`- Launch configuration:  - Threads per block: 32  - Blocks: `ceil(in.lookups / 32)`- A100 occupancy expectation:  - One warp per block.  - On A100, the resident-block limit can cap this at around 32 resident blocks per SM, i.e. 32 resident warps or roughly 50% of the 64-warp maximum.  - Likely not full occupancy.- Energy-efficiency note:  - Accesses are coalesced, but 32-thread blocks underuse SM scheduling capacity.#### `xs_lookup_kernel_optimization_1`- Launch configuration:  - Threads per block: 32  - Blocks: `ceil(in.lookups / 32)`- A100 occupancy expectation:  - Same one-warp-per-block issue.  - Likely lower theoretical occupancy than the 256-thread baseline.  - May suffer from the same lookup divergence as the baseline.- Energy-efficiency note:  - Splitting sampling and lookup adds extra global-memory traffic for sampled energies and materials.  - By itself this likely reduces energy efficiency unless later grouping/sorting benefits are used.---### Optimization 2#### `sampling_kernel`- Same as Optimization 1:  - `ceil(in.lookups / 32)` blocks  - 32 threads per block#### `xs_lookup_kernel_optimization_2`- Launch configuration:  - 12 separate launches, one per material ID.  - Each launch uses:    - Threads per block: 32    - Blocks: `ceil(in.lookups / 32)`- A100 occupancy expectation:  - Each launch has one-warp blocks, so likely capped near 50% theoretical occupancy.  - Each material-specific kernel scans the entire lookup array, so many threads return immediately.- Energy-efficiency note:  - Reduces divergence among active lookup threads because each kernel targets one material.  - However, because the data are not compacted, most threads in many launches are inactive.  - This causes large instruction, scheduling, and memory-read overhead for the material-filter check.  - Energy efficiency is questionable unless the divergence savings outweigh 12 full-array scans.---### Optimization 3#### `sampling_kernel`- Same as Optimization 1:  - `ceil(in.lookups / 32)` blocks  - 32 threads per block#### `xs_lookup_kernel_optimization_3`- Launch configuration:  - Less launch and scan overhead than Optimization 2.- Energy-efficiency note:  - Better than 12 full scans in Optimization 2.  - Separates the very expensive fuel material from all other materials.  - Non-fuel kernel still contains mixed material sizes, so some divergence remains.---### Optimization 4#### `sampling_kernel`- Same as Optimization 1:  - `ceil(in.lookups / 32)` blocks  - 32 threads per block#### Thrust operations- Uses 12 `thrust::count` operations.- Uses `thrust::sort_by_key` to sort material IDs and associated sampled energies.- Internal CUDA launch configurations are controlled by Thrust and are not explicit in the source.#### `xs_lookup_kernel_optimization_4`- Launch configuration:  - 12 launches, one per material.  - For material `m`:    - Threads per block: 32    - Blocks: `ceil(n_lookups_per_material[m] / 32)`- A100 occupancy expectation:  - One-warp blocks still limit theoretical occupancy.  - However, compacted per-material ranges eliminate most inactive-thread waste.  - Active warps are materially uniform, so SIMD efficiency is much better.- Energy-efficiency note:  - Material sorting improves warp efficiency substantially.  - Sorting overhead may be worthwhile for large lookup counts.  - Energy efficiency improves if the cost of sorting is amortized over enough lookups.---### Optimization 5#### `sampling_kernel`- Same as Optimization 1:  - `ceil(in.lookups / 32)` blocks  - 32 threads per block#### Thrust operations- Uses `thrust::count` to count fuel lookups.- Uses `thrust::partition` to place fuel lookups first.- Internal launch configurations are not explicit in the source.#### `xs_lookup_kernel_optimization_5`- Launch configuration:  - 2 launches:    - Fuel segment:      - Blocks: `ceil(n_fuel_lookups / 32)`      - Threads per block: 32    - Non-fuel segment:      - Blocks: `ceil((in.lookups - n_fuel_lookups) / 32)`      - Threads per block: 32- A100 occupancy expectation:  - One-warp blocks likely limit theoretical occupancy.  - Better active-thread utilization than Optimization 3 because ranges are compacted.- Energy-efficiency note:  - Lower sorting/partitioning cost than full material sort.  - Separates fuel from non-fuel, which addresses the largest workload imbalance.  - Non-fuel segment still mixes materials, so residual divergence remains.---### Optimization 6#### `sampling_kernel`- Same as Optimization 1:  - `ceil(in.lookups / 32)` blocks  - 32 threads per block#### Thrust operations- Uses 12 `thrust::count` operations.- Uses one material `thrust::sort_by_key`.- Uses 12 additional energy `thrust::sort_by_key` operations, one per material segment.- Internal launch configurations are not explicit in the source.#### `xs_lookup_kernel_optimization_4`- Optimization 6 reuses `xs_lookup_kernel_optimization_4`.- Launch configuration:  - 12 launches, one per material.  - For material `m`:    - Threads per block: 32    - Blocks: `ceil(n_lookups_per_material[m] / 32)`- A100 occupancy expectation:  - One-warp blocks likely limit theoretical occupancy.  - However, material and energy sorting should greatly improve warp coherence and cache locality.- Energy-efficiency note:  - Likely the most energy-efficient lookup phase because neighboring threads access similar energy regions and the same material.  - Sorting cost may be high, but for large batches it can reduce total energy by reducing wasted memory transactions and divergent execution.---## 3. Global memory access patterns in each kernel### `xs_lookup_kernel_baseline`- Verification writes:  - `GSD.verification[i]`  - Consecutive threads write consecutive addresses.  - Coalesced.- Material and energy sampling:  - Generated locally, no sample-array access.- `GSD.num_nucs`, `GSD.mats`, `GSD.concs`:  - Accessed according to randomly selected material.  - Across a warp, materials usually differ, so accesses are partially scattered.  - `num_nucs[mat]` has only 12 entries and should cache well.  - `mats[mat * max_num_nucs + j]` and `concs[...]` are sequential within a thread for a fixed material, but across warp lanes they are often non-coalesced because materials and loop indices differ.- `GSD.unionized_energy_array`:  - Binary search uses data-dependent locations.  - Across threads, sampled energies differ, so accesses are scattered.- `GSD.index_grid`:  - For unionized grid, accesses use `idx * n_isotopes + nuc`.  - `idx` differs across threads, so warp-level accesses are scattered.  - Within one thread, accesses over material nuclides are not necessarily contiguous because `nuc` IDs are material-list dependent.- `GSD.nuclide_grid`:  - Accesses are random/scattered across nuclides and energy indices.  - Each microscopic lookup reads neighboring grid points, so per-thread locality exists for `low` and `high`.  - Across threads, coalescing is poor.### `sampling_kernel`- `GSD.p_energy_samples[i]` write:  - Consecutive thread to consecutive address.  - Coalesced.- `GSD.mat_samples[i]` write:  - Consecutive thread to consecutive address.  - Coalesced.- No large random global-memory reads.- Energy-efficient memory behavior, but significant integer/RNG compute per thread.### `xs_lookup_kernel_optimization_1`- Reads:  - `GSD.p_energy_samples[i]`: coalesced.  - `GSD.mat_samples[i]`: coalesced.- Writes:  - `GSD.verification[i]`: coalesced.- Lookup data:  - Same scattered pattern as baseline.- Energy-efficiency note:  - Adds two coalesced global reads per lookup compared with baseline.  - Does not reduce lookup divergence by itself.### `xs_lookup_kernel_optimization_2`- Reads:  - `GSD.mat_samples[i]`: coalesced for the filter check.  - `GSD.p_energy_samples[i]`: coalesced only for active threads.- Writes:  - `GSD.verification[i]`: sparse because only threads with matching material write.  - Within a warp, active lanes may be sparse, reducing memory transaction efficiency.- Lookup data:  - Active threads all target the same material kernel, so material-loop length is uniform among active lanes.  - Energies are unsorted, so energy-grid and nuclide-grid accesses remain scattered.- Energy-efficiency note:  - 12 full passes over `mat_samples` are expensive.  - Many lanes exit early, wasting scheduling energy.### `xs_lookup_kernel_optimization_3`- Reads:  - `GSD.mat_samples[i]`: coalesced for the filter check.  - `GSD.p_energy_samples[i]`: coalesced for active threads.- Writes:  - `GSD.verification[i]`: sparse in each of the two launches.- Lookup data:  - Fuel launch is uniform for material 0.  - Non-fuel launch still mixes materials 1–11, so material-loop lengths differ.  - Energy accesses remain scattered.- Energy-efficiency note:  - Less redundant scanning than Optimization 2.  - Still wastes lanes due to sparse active masks.### `xs_lookup_kernel_optimization_4`- Reads:  - `GSD.p_energy_samples[i]`: coalesced within each material segment.  - `GSD.mat_samples[i]`: coalesced and mostly uniform.- Writes:  - `GSD.verification[i]`: coalesced within the sorted material segment.- Lookup data:  - Material composition and concentration accesses are much more coherent because all threads in a kernel launch target the same material.  - Energy accesses remain random unless combined with Optimization 6.- Energy-efficiency note:  - Much better than unsorted material filtering.  - Removes most inactive-lane waste from material filtering.### `xs_lookup_kernel_optimization_5`- Reads:  - `GSD.p_energy_samples[i]`: coalesced within fuel and non-fuel segments.  - `GSD.mat_samples[i]`: coalesced.- Writes:  - `GSD.verification[i]`: coalesced within each partitioned segment.- Lookup data:  - Fuel segment is uniform and efficient.  - Non-fuel segment remains mixed-material and therefore still divergent.- Energy-efficiency note:  - Good compromise between sorting overhead and divergence reduction.  - Likely more energy-efficient than Optimization 3 because it avoids full-array scans in each lookup kernel.### Optimization 6 lookup phase- Uses `xs_lookup_kernel_optimization_4` after sorting by both material and energy.- Reads:  - Sample arrays are coalesced.  - Material IDs are uniform per segment.  - Energies are ordered, so neighboring threads tend to search/access nearby regions.- Writes:  - Verification writes are coalesced.- Lookup data:  - Best locality among all variants.  - Binary-search paths and index-grid accesses become more similar within a warp.  - Nuclide-grid accesses are more cache-friendly because neighboring threads tend to access similar energy indices for the same material.- Energy-efficiency note:  - Best opportunity for reducing wasted memory traffic and cache misses.  - Sorting overhead must be amortized.---## 4. Shared memory usage### Current shared memory usage- No explicit shared memory is used.- There are no `__shared__` allocations.- There is no dynamic shared memory in any kernel launch.- All per-thread temporary arrays such as `macro_xs_vector[5]` and `xs_vector[5]` are private local variables, likely placed in registers unless register pressure causes spilling.### Potential shared memory opportunities- Material composition and concentration data are small enough to consider caching:  - `num_nucs[12]` is tiny.  - `mats` and `concs` are small compared with the nuclide grid.  - For large/default case, `12 * 321` integers and `12 * 321` doubles are roughly tens of KiB.- For material-specific kernels, one material row of `mats` and `concs` could be staged in shared memory:  - Fuel row: up to 321 integers plus 321 doubles.  - Approximate size: around 3.8 KiB for one material row.  - This is very feasible on A100.- Shared memory could reduce repeated global loads of:  - `mats[mat * max_num_nucs + j]`  - `concs[mat * max_num_nucs + j]`- `num_nucs`, material IDs, and the probability distribution in `pick_mat` are better candidates for constant memory because they are small and read-only.- The nuclide grid and index grid are too large and too randomly accessed for general shared-memory caching.- With energy-sorted workloads, limited tiling of nearby energy-index data might become possible, but it would require careful design and may not generalize.### Energy-efficiency implications- Moving small read-only tables to constant or shared memory can reduce DRAM traffic and improve cache efficiency.- Shared-memory staging is most useful in material-sorted variants where all threads in a block use the same material composition.- Adding shared memory may require `__syncthreads()`, but the current code avoids all block-level barriers.---## 5. Warp divergence### Major divergence sources- Random material selection causes threads in the same warp to execute different loop trip counts in `calculate_macro_xs`.- Fuel lookups are much longer than non-fuel lookups.- Binary searches have data-dependent branches and loop paths.- Material-filtering kernels create sparse active masks.- Hash and boundary-condition checks introduce additional per-thread branches.### Conditional branches inside kernels and called device functions#### In all explicit kernels- Bounds check:  - `if (i >= ...) return;`  - Causes divergence only in the final partial block.#### `xs_lookup_kernel_baseline`- Bounds check.- Verification max-reduction branch:  - `if (macro_xs_vector[j] > max)`  - Small loop, minor divergence.#### `sampling_kernel`- Bounds check.- Calls `pick_mat`, which contains data-dependent branches.#### `xs_lookup_kernel_optimization_1`- Bounds check.- Verification max-reduction branch.#### `xs_lookup_kernel_optimization_2`- Bounds check.- Material filter:  - `if (mat != m) return;`  - Potentially severe divergence and many inactive lanes.- Verification max-reduction branch.#### `xs_lookup_kernel_optimization_3`- Bounds check.- Fuel/non-fuel predicate:  - Executes lookup only if the selected material belongs to the current kernel category.  - Can create sparse active masks.- Verification max-reduction branch inside the active path.#### `xs_lookup_kernel_optimization_4`- Bounds check.- Material check:  - `if (mat != m) return;`  - Mostly redundant after sorting, but still present.  - Should usually be uniform, except if data are not perfectly sorted or counts/offsets are inconsistent.- Verification max-reduction branch.#### `xs_lookup_kernel_optimization_5`- Bounds check.- Verification max-reduction branch.- No explicit material-filter branch in this kernel.#### `calculate_macro_xs`- Grid-type branch:  - Unionized grid path.  - Hash grid path.  - Nuclide path.- Loop bound:  - `for (j = 0; j < num_nucs[mat]; j++)`  - Major divergence source when warp lanes have different materials.- Inner accumulation loop over 5 channels:  - Uniform fixed trip count, low divergence.#### `calculate_micro_xs`- Grid-type branch:  - `NUCLIDE`  - `UNIONIZED`  - `HASH`- Edge-condition branches:  - Checks for last grid point.  - Hash-grid boundary checks.  - Energy comparisons against `e_low` and `e_high`.- These branches may diverge because each thread has a different energy and nuclide.#### `grid_search` and `grid_search_nuclide`- Binary-search loop:  - Data-dependent branch on energy comparison.  - Threads may access different locations and take different branch paths.  - The loop count is mostly similar for equal search ranges, but branch directions differ.#### `pick_mat`- Data-dependent material selection:  - Loop over 12 materials.  - Branch on `roll < running`.  - Different lanes return at different iterations.#### `fast_forward_LCG`- Loop depends on `n`.- Branch on `if (n & 1)`.- Different lookup IDs have different bit patterns, so divergence is expected.### Energy-efficiency implications- Material sorting directly addresses the largest divergence source.- Energy sorting reduces binary-search and memory-access divergence.- Fuel/non-fuel partitioning is a lower-cost compromise.- The 32-thread block design aligns each block to one warp, avoiding intra-block divergence interactions, but it reduces SM occupancy potential.---## 6. Data types and double-precision operations replaceable with float### Current double-precision usageThe code uses double precision extensively in:- `NuclideGridPoint` fields:  - `energy`  - `total_xs`  - `elastic_xs`  - `absorbtion_xs`  - `fission_xs`  - `nu_fission_xs`- `unionized_energy_array`- `concs`- `p_energy_samples`- `p_energy`- `macro_xs_vector`- `xs_vector`- Interpolation factor `f`- Hash/bin calculations involving `du`- Random number generation output from `LCG_random_double`- Material probability distribution in `pick_mat`- Host-side initialization, sorting, and timing-related calculations.### Candidates for float replacementIf scientific accuracy and verification requirements allow, the following are candidates for single precision:- Sampled particle energy.- Unionized energy array.- Nuclide grid energy and cross-section values.- Nuclide concentrations.- Microscopic cross-section vector.- Macroscopic cross-section vector.- Interpolation factor.- Material probability distribution.- Hash-bin floating-point arithmetic.### Expected benefits of float- Reduces memory footprint:  - `NuclideGridPoint` would shrink from 48 bytes to 24 bytes if all six fields become floats.  - `concs`, `unionized_energy_array`, and `p_energy_samples` would halve in size.- Reduces DRAM traffic.- Improves cache residency.- Reduces memory energy per lookup.- Potentially improves arithmetic throughput and lowers FP64 power usage, although the main gain is likely memory-system efficiency.### Caution- Replacing doubles with floats will likely change the verification checksum.- If benchmark reproducibility is required, the current double-precision behavior must be preserved.- The LCG uses 64-bit integer arithmetic and converts to double. Replacing the returned random value with float changes sampling and material selection behavior.- Any float conversion must be validated against the intended physics accuracy and benchmark rules.---## 7. Additional energy-efficiency observations### Sorting tradeoff- Optimization 6 likely has the most efficient lookup kernel because it improves both material uniformity and energy locality.- However, it pays for many Thrust operations.- For small lookup counts, sorting energy may dominate.- For large lookup counts, sorting can reduce total energy by improving cache reuse and reducing warp inefficiency.### Block size- The optimized variants use 32-thread blocks.- This maps one block to one warp, which simplifies warp-level uniformity, but on A100 it can limit occupancy due to the maximum resident-block limit.- Testing 64, 128, or 256 threads per block may improve latency hiding and reduce scheduling overhead.- Material grouping can still be preserved with larger blocks.### Read-only data placement- `num_nucs`, `mats`, `concs`, and the material probability distribution are read-only during kernels.- `num_nucs` and the probability distribution are strong candidates for constant memory.- Material rows are strong candidates for shared-memory staging in material-specific kernels.### Data layout- The current `NuclideGridPoint` is array-of-structures.- This is reasonable if all six fields are always read together.- If only selected fields are needed in other variants, structure-of-arrays could reduce unnecessary memory traffic.- For this code, all five cross-section channels and energy are used during interpolation, so AoS is defensible.### Verification reduction- Each lookup writes one `unsigned long` verification value and then Thrust reduces it.- This is coalesced but adds a full global-memory write/read pass.- A custom block-level reduction could reduce global traffic, but would introduce shared memory and synchronization.- Because there are no current `__syncthreads()` calls, this would be a tradeoff between less DRAM traffic and more intra-block synchronization.### Memory allocation issue- Device memory for `GSD.index_grid` is allocated but not freed in `release_device_memory`.- This does not affect a single short run much, but repeated runs or long-lived processes could waste GPU memory and energy through allocator pressure.
