- **Memory access coalescing**: Arrange global memory accesses so consecutive threads in a warp access consecutive addresses. Prefer struct-of-arrays over array-of-structs for per-field access, and avoid strided patterns such as `arr[threadIdx.x * N + j]`.    **Most impactful when** the kernel is memory-bound and DRAM traffic dominates energy, especially with large HBM2e reads/writes on A100.- **Shared memory use**: Use shared memory to stage data that is reused by multiple threads in a block, loading it once from global memory and reusing it from on-chip SRAM. Avoid shared-memory bank conflicts by choosing layouts where warp threads do not repeatedly hit the same bank. On A100, shared memory can be configured up to about 163 KB per SM.    **Most impactful when** threads in a block repeatedly access overlapping or nearby global memory regions, such as tiled stencils, reductions, matrix-like operations, or reusable lookup data.- **Occupancy optimization**: Choose block sizes that keep enough active warps per SM to hide memory latency, typically 128–256 threads per block. Watch limits from registers, shared memory, and block size. Avoid register spilling, because spilled values go to local memory backed by DRAM. Use the CUDA occupancy calculator or `cudaOccupancyMaxPotentialBlockSize`, and consider `__launch_bounds__` when register pressure is excessive.    **Most impactful when** kernels are latency-bound or memory-bound and need many active warps to hide HBM2e latency, but not at the cost of excessive spilling or reduced cache locality.- **Warp divergence reduction**: Minimize branches where threads in the same warp take different paths. Replace short divergent branches with predication, conditional selection, or branchless arithmetic where appropriate. Group or sort inputs so threads in a warp follow similar control flow when possible.    **Most impactful when** branch paths are long, data-dependent, or frequent, causing the warp to serialize multiple execution paths and waste active cycles.- **Kernel fusion**: Merge consecutive kernels that operate on the same data so intermediate values stay in registers or shared memory instead of being written to and reread from global memory. Fusion also reduces kernel launch overhead.    **Most impactful when** multiple simple kernels are memory-bandwidth-bound, use the same data stream, or produce temporary arrays consumed immediately by the next kernel.- **Read-only cache / `__ldg` / `const __restrict__`**: Mark read-only input arrays as `const __restrict__` and use `__ldg()` where beneficial to route immutable data through the read-only/texture cache path. This can reduce L2 and DRAM pressure for repeated or spatially local reads.    **Most impactful when** large input arrays are read-only within the kernel and exhibit temporal or spatial locality; it can still help moderately with irregular read-only lookup patterns.- **Arithmetic precision tradeoffs**: Use the lowest precision that preserves correctness. Prefer `float` over `double` when acceptable, because FP32 uses less memory bandwidth, fewer registers, and has much higher throughput than FP64 on A100. Use fast math intrinsics such as `__expf`, `__logf`, or `__fdividef` only when their reduced accuracy is acceptable. Use FMA where possible to reduce instruction count and improve accuracy.    **Most impactful when** the kernel is compute-bound, register-limited, or moving large floating-point arrays; reducing from FP64 to FP32 can cut data movement and register footprint significantly.- **Synchronization minimization**: Remove unnecessary `__syncthreads()` calls, move barriers out of loops when possible, and use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or `__reduce_sync` when only intra-warp coordination is needed. Reduce high-contention atomics by doing block-level reductions in shared memory and issuing one atomic per block.    **Most impactful when** barriers occur inside hot loops, when only part of a block needs synchronization, or when many threads contend on the same atomic address.- **Prefetching and data movement control**: Keep data resident on the GPU across kernel launches, minimize host-device transfers, use pinned host memory for required transfers, and overlap transfers with computation using streams and `cudaMemcpyAsync`. For Unified Memory, avoid costly implicit page migrations by using explicit allocation/copying or prefetching managed data to the GPU before kernels run.    **Most impactful when** runtime includes significant CPU-GPU transfer time, Unified Memory page faults, or repeated movement of the same data between host and device.
