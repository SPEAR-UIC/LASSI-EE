## 1. Overall Algorithm and GPU Resource Utilization Profile### Algorithm SummaryThis is a CUDA implementation of an XSBench-style continuous-energy Monte Carlo macroscopic cross-section lookup workload.For each lookup:1. A pseudo-random neutron energy is generated.2. A material is selected using a probabilistic distribution.3. For that material, the code loops over all nuclides present in the material.4. For each nuclide:   - It locates the bounding energy grid points using one of three lookup modes:     - `NUCLIDE`: binary search in each nuclide grid.     - `UNIONIZED`: one binary search in the unionized energy grid, then indexed lookup into each nuclide grid.     - `HASH`: hash-bin lookup followed by a bounded nuclide-grid search.   - It interpolates five microscopic cross-section values.   - It multiplies by the nuclide concentration and accumulates into a five-element macroscopic cross-section vector.5. A verification value is produced by finding the index of the maximum macroscopic cross-section component.### Resource Utilization ProfileThe dominant work is the cross-section lookup, especially `calculate_macro_xs()` and `calculate_micro_xs()`.This workload is primarily **memory-latency-bound and memory-bandwidth-sensitive**, not purely compute-bound.Reasons:- The nuclide grid is large and accessed with random or semi-random indices.- Each microscopic lookup loads two adjacent `NuclideGridPoint` records.- Each `NuclideGridPoint` contains six `double` fields, so two points require up to 96 bytes of raw structure data before accounting for cache-line effects.- The access pattern depends on random sampled energy, material, and nuclide composition.- Binary searches introduce irregular control flow and non-sequential reads.- Fuel material has many more nuclides than other materials, causing severe per-thread workload imbalance.The arithmetic work per nuclide is moderate:- Several double-precision subtractions, multiplications, divisions, and accumulations.- Five interpolation channels per nuclide.- However, the arithmetic intensity is still low relative to the irregular global-memory traffic.### Random vs Sequential AccessThe workload is dominated by **random/scattered access**:- Random energy samples produce random positions in the energy grids.- Random material selection produces different loop lengths per thread.- Nuclide-grid accesses are scattered across `nuclide_grid`.- Unionized-grid binary search is also scattered.- Hash-grid mode reduces the search range but still performs irregular accesses.Sequential/coalesced access appears mainly in:- Writing `GSD.verification[i]`.- Writing and reading sampled energies and materials in optimized split kernels.- Thrust reductions/counts/sorts/partitions, which operate over contiguous arrays.### Energy Efficiency OpportunitiesMajor energy-efficiency opportunities are:- Reduce global memory traffic, especially from `NuclideGridPoint` loads.- Improve cache locality by grouping lookups by material and energy, as in optimizations 4–6.- Reduce warp divergence caused by different material loop lengths.- Consider replacing double precision with single precision where accuracy and checksum requirements allow.- Use constant or read-only memory paths for small, frequently read material metadata.- Avoid launching many kernels that scan the full lookup array while most threads immediately return.- Avoid excessive sorting/partitioning unless the improved lookup locality outweighs the extra memory traffic and kernel-launch overhead.---## 2. Global Memory Access Patterns### `xs_lookup_kernel_baseline`Global-memory behavior:- `GSD.verification[i]` writes are coalesced because consecutive threads write consecutive indices.- The main lookup data accesses are scattered:  - `num_nucs[mat]`: small array, random material index, likely cached.  - `mats[mat * max_num_nucs + j]`: per-thread sequential within the material, but across a warp `mat` may differ.  - `concs[mat * max_num_nucs + j]`: same pattern as `mats`.  - `unionized_energy_array`: binary search with random energy, scattered across the array.  - `index_grid[idx * n_isotopes + nuc]`: scattered because `idx` and `nuc` differ across threads.  - `nuclide_grid[nuc * n_gridpoints + index]`: scattered and latency-heavy.Coalescing assessment:- Verification writes: coalesced.- Nuclide-grid reads: mostly uncoalesced/scattered.- Index-grid reads: mostly uncoalesced/scattered.- Energy-grid binary search reads: scattered.- Material metadata accesses: small and cache-friendly, but not necessarily coalesced.---### `sampling_kernel`Global-memory behavior:- `GSD.p_energy_samples[i] = p_energy`- `GSD.mat_samples[i] = mat`Coalescing assessment:- Writes are coalesced because consecutive threads write consecutive addresses.- The kernel is mostly compute/integer-heavy due to RNG and material selection.- It has little global-memory pressure aside from the output arrays.Energy-efficiency note:- The memory pattern is efficient, but storing samples creates additional global-memory traffic compared with the baseline.---### `xs_lookup_kernel_optimization_1`Global-memory behavior:- Reads `GSD.p_energy_samples[i]` and `GSD.mat_samples[i]`.- Writes `GSD.verification[i]`.- Performs the same scattered lookup accesses as the baseline.Coalescing assessment:- Sample reads are coalesced.- Verification writes are coalesced.- Cross-section data accesses remain mostly scattered.---### `xs_lookup_kernel_optimization_2`Global-memory behavior:- Every material kernel reads `GSD.mat_samples[i]` for all lookups.- Threads whose material does not match return early.- Active threads read `GSD.p_energy_samples[i]`.- Active threads write `GSD.verification[i]`.Coalescing assessment:- Initial `mat_samples` reads are coalesced.- Because only a subset of lanes remain active, subsequent energy reads and verification writes are masked and less efficient.- Cross-section accesses are less divergent among active threads for a given material, but because the array is not sorted, active lanes may be sparse within warps.Energy-efficiency issue:- Twelve full scans of `mat_samples` are performed.- Most threads do no useful cross-section work in each material-specific launch.---### `xs_lookup_kernel_optimization_3`Global-memory behavior:- Similar to Optimization 2, but with only two filtering kernels: fuel and non-fuel.- Reads `GSD.mat_samples[i]` for all lookups in both launches.- Active threads read energy and perform lookup.Coalescing assessment:- `mat_samples` reads are coalesced.- Active energy reads and verification writes may be sparse due to filtering.- Fuel and non-fuel grouping reduces large loop-length imbalance but does not fully eliminate material diversity in the non-fuel kernel.Energy-efficiency note:- Better than Optimization 2 because only two global scans are performed instead of twelve.---### `xs_lookup_kernel_optimization_4`Global-memory behavior:- Operates on sorted-by-material contiguous ranges.- Reads `GSD.mat_samples[i]` and `GSD.p_energy_samples[i]`.- Writes `GSD.verification[i]`.- Performs cross-section lookup.Coalescing assessment:- Sample reads are coalesced.- Verification writes are coalesced.- Material values are uniform within each kernel’s range.- Material-specific loop lengths are uniform across active threads.- Energy values are not sorted in Optimization 4, so energy-grid and nuclide-grid accesses remain scattered.Energy-efficiency note:- Sorting by material improves warp execution efficiency.- It does not fully solve random memory access into cross-section tables.---### `xs_lookup_kernel_optimization_5`Global-memory behavior:- Operates on partitioned fuel and non-fuel regions.- Reads samples from contiguous regions.- Writes verification contiguously within each region.- Performs cross-section lookup.Coalescing assessment:- Sample reads are coalesced.- Verification writes are coalesced.- Fuel kernel has uniform material and loop length.- Non-fuel kernel still contains multiple material types, so some divergence remains.- Energy-grid and nuclide-grid accesses remain scattered because energy is not sorted.Energy-efficiency note:- Less sorting overhead than Optimization 4.- Less material uniformity than full material sorting.---### `xs_lookup_kernel_optimization_6`Lookup kernel is `xs_lookup_kernel_optimization_4` after both material and energy sorting.Global-memory behavior:- Reads samples from contiguous, material-homogeneous, energy-sorted ranges.- Writes verification contiguously.- Cross-section lookups access nearby energy locations across neighboring threads.Coalescing assessment:- Sample reads and verification writes are coalesced.- Nuclide-grid and unionized-grid accesses are significantly more cache-friendly than in other versions.- Consecutive threads are more likely to access the same or nearby grid indices.- Accesses are still not guaranteed to be perfectly coalesced as consecutive thread → consecutive address, but locality and cache reuse are substantially improved.Energy-efficiency note:- This is the strongest version for reducing memory-system energy during lookup.- The benefit must be weighed against the energy cost of multiple Thrust sorting passes.---### Thrust OperationsThe code uses Thrust for:- `thrust::reduce`- `thrust::count`- `thrust::sort_by_key`- `thrust::partition`Global-memory behavior:- Reductions and counts mostly stream through contiguous arrays and are generally coalesced.- Sorts and partitions perform large amounts of global-memory movement.- Sorts are bandwidth-intensive and can consume significant energy, especially for large lookup counts.---## 4. Shared Memory Usage### Current Shared Memory UsageThere is no explicit shared-memory allocation in any CUDA kernel.There are also no uses of:- `extern __shared__`- statically declared `__shared__` arrays- cooperative shared-memory staging### Potential Shared Memory OpportunitiesPotentially useful candidates:1. **Material metadata**   - `num_nucs`   - `mats`   - `concs`   These arrays are small and repeatedly accessed. For material-specific kernels, the relevant material’s nuclide IDs and concentrations could be staged in shared memory once per block.2. **Material distribution in `pick_mat()`**   - The `dist[12]` array is currently a local per-thread array.   - This is better suited for constant memory or compile-time constants than shared memory.3. **Frequently reused index-grid regions**   - In energy-sorted kernels, neighboring threads may access nearby or identical `idx` values.   - Shared-memory staging could help if a block’s threads reuse the same `index_grid` rows.   - The benefit depends strongly on energy locality and material grouping.4. **Nuclide grid staging**   - Full nuclide grids are too large for shared memory.   - Small tiles may help in energy-sorted, material-specific kernels, but random access limits general usefulness.### Better Alternatives Than Shared Memory for Some Data- Use `__constant__` memory for very small read-only arrays such as material counts or material distributions.- Use read-only cache paths for immutable global arrays.- Consider structure-of-arrays layout if energy sorting makes threads access the same field across nearby grid points.---## 5. Warp Divergence### Major Sources of Divergence#### Boundary GuardsAll kernels include bounds checks such as:- `if (i >= in.lookups) return;`- `if (i >= n_lookups) return;`These only diverge in the final partial block and are minor.---### `sampling_kernel`Divergence sources:- `fast_forward_LCG()`:  - `while (n > 0)`  - `if (n & 1)`  - Loop count and branch behavior vary with lookup index `i`.- `pick_mat()`:  - Loop over materials.  - Conditional return based on random `roll`.  - Different threads may return at different loop iterations.---### `xs_lookup_kernel_baseline`Divergence sources:- Material choice differs across threads.- `calculate_macro_xs()` loop bound:  - `for (int j = 0; j < num_nucs[mat]; j++)`  - This is a severe divergence source because material 0 may have 321 nuclides while other materials may have as few as 4 or 5.- Verification max search:  - `if (macro_xs_vector[j] > max)`  - Minor divergence over a five-iteration loop.- `calculate_macro_xs()`:  - `if (grid_type == UNIONIZED)`  - `else if (grid_type == HASH)`  - This is uniform across all threads for a given run, so it is not expected to cause intra-warp divergence.- `calculate_micro_xs()`:  - `if (grid_type == NUCLIDE)`  - `else if (grid_type == UNIONIZED)`  - `else`  - Also uniform across a run.- Binary searches:  - `if (A[examinationPoint] > quarry)`  - Branch direction differs by thread because `quarry` differs.- Hash edge cases:  - `if (idx == hash_bins - 1)`  - `if (p_energy <= e_low)`  - `else if (p_energy >= e_high)`  - Branches may diverge across threads.- Nuclide-grid boundary checks:  - `if (idx == n_gridpoints - 1)`  - `if (index_data[...] == n_gridpoints - 1)`  - May diverge depending on sampled energy and index.---### `xs_lookup_kernel_optimization_1`Same lookup divergence as baseline, except sampling has been moved out.Additional behavior:- Reads precomputed material and energy samples.- Material-loop divergence remains unchanged.---### `xs_lookup_kernel_optimization_2`Divergence sources:- `if (mat != m) return;`  - Severe divergence unless lookups are already grouped by material.  - Most threads return in each material-specific launch.- Active threads have uniform material, which reduces divergence in `num_nucs[mat]`.- Binary-search and energy-dependent divergence remains.---### `xs_lookup_kernel_optimization_3`Divergence sources:- Fuel/non-fuel condition:  `if (((is_fuel == 1) && (mat == 0)) || ((is_fuel == 0) && (mat != 0)))`- Threads diverge based on whether their material matches the fuel/non-fuel category.- The fuel launch has uniform loop length for active threads.- The non-fuel launch still contains multiple material types, so loop-length divergence remains among non-fuel materials.---### `xs_lookup_kernel_optimization_4`Divergence sources:- `if (i >= n_lookups) return;`- `if (mat != m) return;`After sorting by material, `mat != m` should normally be false for the intended range, but the branch remains.Benefits:- Material-loop divergence is largely eliminated because each kernel handles one material.- Energy-dependent binary-search divergence remains.---### `xs_lookup_kernel_optimization_5`Divergence sources:- `if (i >= n_lookups) return;`- Fuel and non-fuel are separated by partition.- Fuel kernel has low material-loop divergence.- Non-fuel kernel still has divergence from different non-fuel material sizes.---### `xs_lookup_kernel_optimization_6`Divergence sources:- Same kernel-level branches as Optimization 4.- Material divergence is minimized.- Energy sorting improves binary-search branch coherence because neighboring threads have nearby `p_energy` values.- This likely reduces both branch divergence and memory divergence compared with other variants.---## 6. Data Types and Double-Precision Replacement Opportunities### Current Double-Precision DataThe code uses `double` extensively:- `NuclideGridPoint::energy`- `NuclideGridPoint::total_xs`- `NuclideGridPoint::elastic_xs`- `NuclideGridPoint::absorbtion_xs`- `NuclideGridPoint::fission_xs`- `NuclideGridPoint::nu_fission_xs`- `SimulationData::concs`- `SimulationData::unionized_energy_array`- `SimulationData::p_energy_samples`- `p_energy`- `macro_xs_vector[5]`- `xs_vector[5]`- Interpolation factor `f`- Hash-bin spacing `du`- Material probability array `dist[12]`- RNG return value from `LCG_random_double()`### Operations That Could Potentially Use `float`If physics accuracy and verification requirements permit, the following are candidates for conversion to single precision:1. Cross-section storage:   - `total_xs`   - `elastic_xs`   - `absorbtion_xs`   - `fission_xs`   - `nu_fission_xs`2. Energy grid storage:   - `energy`   - `unionized_energy_array`3. Concentrations:   - `concs`4. Sampled particle energies:   - `p_energy`   - `p_energy_samples`5. Interpolation arithmetic:   - `f`   - `xs_vector`   - `macro_xs_vector`6. Material-selection probabilities:   - `dist`   - `roll`### Expected Energy Benefits of Using `float`Using `float` instead of `double` would:- Reduce `NuclideGridPoint` size from 48 bytes to 24 bytes.- Halve bandwidth demand for the largest data structure.- Improve cache residency.- Reduce energy per arithmetic operation.- Potentially improve occupancy by reducing register pressure.### CautionChanging double precision to float may alter:- Interpolation results.- Material selection behavior if RNG output conversion changes.- Verification checksum.Therefore, replacing double with float is an energy-efficiency opportunity only if the application tolerates reduced numerical precision and changed checksum behavior.---## 7. Synchronization Overhead### `__syncthreads()` CountThere are no calls to `__syncthreads()` in the CUDA kernels.Total explicit device-side barrier count:- `__syncthreads()` calls: **0**### Host-Side SynchronizationAlthough there are no intra-kernel barriers, the code uses many host-side synchronization points:- `cudaDeviceSynchronize()` after explicit kernel launches.- `cudaDeviceSynchronize()` after Thrust reductions.- Thrust algorithms also introduce implicit synchronization/ordering through the default stream.Examples:- Baseline:  - Synchronize after lookup kernel.  - Synchronize after reduction.- Optimization 1:  - Synchronize after sampling.  - Synchronize after lookup.  - Synchronize after reduction.- Optimization 2:  - Synchronize after sampling.  - Synchronize after 12 material lookup launches.  - Synchronize after reduction.- Optimization 4:  - Synchronize after sampling.  - Thrust counts and sort introduce additional library-kernel work.  - Synchronize after lookup launches.  - Synchronize after reduction.Energy-efficiency note:- Kernel splitting and multiple Thrust operations increase launch overhead and global-memory traffic.- Reducing unnecessary host synchronizations or using streams carefully could improve throughput and energy efficiency, provided correctness is preserved.---## 8. Material sorting and energy sorting reduce random access and divergence.   - Optimization 6 is strongest for lookup locality but has high sorting overhead.2. **Reduce precision if allowed**   - Converting grid data and interpolation from `double` to `float` could significantly reduce memory traffic and energy.3. **Use better memory placement for small read-only data**   - Material metadata and probability tables are candidates for constant memory or shared-memory staging.4. **Reduce divergence**   - Grouping by material reduces loop-length imbalance.   - Grouping by energy improves binary-search coherence and cache reuse.5. **Avoid wasteful full-array scans**   - Optimization 2 performs 12 full scans and is likely energy-inefficient unless material grouping benefits dominate.6. **Reconsider one-warp block size**   - The optimized kernels use 32-thread blocks, limiting theoretical A100 occupancy to about 50%.   - Larger blocks could improve occupancy, though this must be balanced against divergence and register pressure.7. **Minimize unnecessary synchronization and kernel-launch overhead**   - Multiple kernel launches and Thrust operations add overhead.   - Combining stages or using asynchronous execution may improve energy efficiency if correctness is maintained.
