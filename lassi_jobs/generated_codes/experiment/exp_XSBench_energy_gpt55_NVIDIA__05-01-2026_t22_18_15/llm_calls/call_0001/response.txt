## Key CUDA energy-efficiency techniques for NVIDIA A100### 1. Coalesce global memory accessesMake consecutive threads in a warp access consecutive memory addresses. Prefer struct-of-arrays layouts over array-of-structs when each thread reads the same field from different elements. Avoid strided or scattered warp accesses when possible.**Most impactful when:** the kernel is memory-bound and spends significant time reading/writing HBM2e. Coalescing can greatly reduce DRAM transactions, lowering both runtime and memory power.---### 2. Use shared memory for reused dataLoad data cooperatively from global memory into shared memory when multiple threads in a block reuse the same or nearby data. Avoid shared-memory bank conflicts by choosing access patterns whose stride is not a multiple of 32 banks.**Most impactful when:** there is spatial or temporal reuse within a thread block, such as stencil operations, tiled matrix operations, reductions, or repeated lookups into a shared working set.---### 3. Tune occupancy, but avoid chasing maximum occupancy blindlyUse block sizes that are multiples of 32; 128–256 threads per block are often a good starting point on A100. Watch register usage and shared-memory usage because both can limit active warps per SM. Avoid register spilling, since spilled registers go to local memory backed by global memory.Useful tools and controls include `cudaOccupancyMaxPotentialBlockSize`, Nsight Compute occupancy metrics, and `__launch_bounds__`.**Most impactful when:** the kernel has latency to hide, especially memory latency, and occupancy is limited by excessive registers, shared memory, or poor block sizing.---### 4. Reduce warp divergenceKeep threads in a warp on the same control-flow path. Replace short divergent branches with predicated or branchless expressions where appropriate. Group or sort inputs so that nearby threads perform similar work when feasible.**Most impactful when:** different threads in the same warp frequently take different branches, causing serialized execution of multiple paths.---### 5. Fuse kernels when intermediate data is reusedCombine consecutive kernels that operate on the same data so intermediate values can remain in registers or shared memory instead of being written to and reread from global memory. Fusion also reduces kernel launch overhead.**Most impactful when:** kernels are memory-bound, use temporary global arrays, or perform small stages with low arithmetic intensity.---### 6. Use read-only cache paths for immutable dataMark read-only input arrays as `const __restrict__` and, where useful, explicitly use `__ldg()` for read-only loads. This can route data through the read-only/texture cache path and reduce pressure on normal global-load paths and L2.**Most impactful when:** arrays are read-only within the kernel and have spatial or temporal locality. It can still help for irregular lookup-heavy workloads if cache lines are reused.---### 7. Choose arithmetic precision carefullyUse `float` instead of `double` when accuracy requirements allow. FP32 uses less memory bandwidth, fewer registers, and has much higher throughput than FP64 on A100. Use FMA where possible, and consider CUDA fast-math intrinsics such as `__expf`, `__logf`, or `__fdividef` only when reduced precision is acceptable.**Most impactful when:** the kernel is compute-bound or when double precision increases memory traffic, register pressure, or occupancy limits. Always verify numerical correctness.---### 8. Minimize synchronization and atomicsRemove unnecessary `__syncthreads()`, especially inside loops. Use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or warp reductions when only intra-warp coordination is needed. Replace high-contention atomics with block-level reductions in shared memory followed by one atomic per block.**Most impactful when:** barriers or atomics cause frequent stalls, serialization, or contention, especially in reductions and histogram-like updates.---### 9. Prefetch and manage data movement explicitlyKeep data resident on the GPU across multiple kernels. Avoid unnecessary host-device transfers. Prefer explicit `cudaMalloc`/`cudaMemcpy` over unmanaged page migration for predictable performance. When transfers are required, use pinned host memory and `cudaMemcpyAsync` with streams to overlap transfer and computation.For unified memory, use explicit prefetching, e.g. `cudaMemPrefetchAsync`, to move data to the A100 before kernels access it and avoid page-fault-driven migrations.**Most impactful when:** the application repeatedly moves data between CPU and GPU, uses unified memory, or suffers from transfer stalls and page migrations.
