## 1. Overall Algorithm and GPU Resource Utilization Profile### Algorithm summaryThis is a CUDA implementation of the XSBench event-based macroscopic cross-section lookup workload.For each lookup:1. A thread derives a deterministic RNG seed from the lookup index.2. It samples:   - neutron energy,   - material ID.3. It computes a macroscopic cross-section vector with 5 reaction channels.4. For the selected material, it loops over all nuclides in that material.5. For each nuclide, it performs a microscopic cross-section lookup by finding bounding energy grid points and interpolating between them.6. It accumulates the microscopic cross sections weighted by nuclide concentration.7. It writes a small verification value to global memory.8. A Thrust reduction sums the verification array.The dominant work is in `calculate_macro_xs()` and `calculate_micro_xs()`.### Grid lookup modesThe code supports three lookup modes:- **UNIONIZED**  - One binary search over the unionized energy grid per macroscopic lookup.  - Then uses `index_grid` to find corresponding nuclide-grid indices.  - Very large memory footprint, especially `index_grid`.  - Fewer binary searches, but significant random global-memory traffic.- **NUCLIDE**  - Performs a binary search inside each nuclide grid.  - More compute and control-flow work.  - Avoids the large unionized index grid.  - Still dominated by scattered memory reads.- **HASH**  - Uses a hash/bin index to narrow the search range.  - Smaller acceleration structure than unionized grid.  - Requires additional local bounded search.  - Potentially more energy-efficient than UNIONIZED if it reduces memory footprint and DRAM traffic enough.### Compute-bound vs memory-bound assessmentThis workload is primarily **memory-latency-bound and memory-bandwidth-sensitive**, not purely compute-bound.Reasons:- Nuclide grid accesses are data-dependent and effectively random.- Binary searches cause irregular access patterns.- Threads in a warp usually operate on different energies and materials.- Material 0 has many more nuclides than most other materials, causing severe load imbalance.- Each microscopic lookup reads two `NuclideGridPoint` records, each containing 6 double-precision values.- In UNIONIZED mode, `index_grid` can be extremely large and is accessed with random or strided patterns.- The arithmetic per byte loaded is moderate: interpolation uses several floating-point operations, but global memory traffic and cache misses dominate energy cost.On an A100, double-precision throughput is strong compared with consumer GPUs, but the dominant energy issue here is still **irregular global-memory traffic and warp inefficiency**, not raw FP64 throughput alone.### Random vs sequential accessThe code contains both sequential and random-access phases:- **Sequential/coalesced phases**  - Sampling kernels write `p_energy_samples[i]` and `mat_samples[i]` consecutively.  - Verification writes are mostly consecutive in the baseline and compacted variants.  - Thrust reduction/count/sort/partition operations operate over contiguous arrays.- **Random/scattered phases**  - Binary searches into energy grids.  - Nuclide-grid interpolation loads.  - UNIONIZED `index_grid` lookups.  - Per-material nuclide/concentration access when materials are mixed inside a warp.### Main energy-efficiency opportunities- Improve locality by sorting or grouping lookups by material and energy.- Avoid launching full-grid material kernels where most threads return immediately.- Use larger thread blocks than 32 threads where possible to improve occupancy and latency hiding.- Convert double-precision data to single precision if physics/verification tolerances permit.- Move small read-only material tables and probability distributions to constant memory or read-only cache.- Consider a structure-of-arrays layout for `NuclideGridPoint`, especially separating energy from cross-section fields.- Prefer compacted material-specific kernels over full-array filtered kernels.- Reconsider UNIONIZED mode for large cases because `index_grid` can dominate memory footprint and energy.---## 2. CUDA Kernel Launch Configurations and A100 Occupancy Assessment### Baseline kernel#### Launch- Kernel: `xs_lookup_kernel_baseline`- Threads per block: 256- Blocks: ceiling of `in.lookups / 256`#### Occupancy assessment on A100This is the best launch shape in the file from a pure occupancy perspective.- 256 threads/block = 8 warps/block.- A100 can support up to 64 resident warps/SM, subject to register and block limits.- With 256-thread blocks, high theoretical occupancy is possible if register usage is not excessive.- Actual occupancy may be reduced by:  - local arrays such as `macro_xs_vector[5]` and `xs_vector[5]`,  - inlined device functions,  - double-precision temporaries,  - binary-search state,  - RNG state.Likely occupancy: **moderate to high**, depending on compiler register allocation.Energy implication: the block size is reasonable for hiding memory latency, but warp divergence and random memory accesses still reduce effective energy efficiency.---### Optimization 1#### Launches1. `sampling_kernel`   - Threads per block: 32   - Blocks: ceiling of `in.lookups / 32`2. `xs_lookup_kernel_optimization_1`   - Threads per block: 32   - Blocks: ceiling of `in.lookups / 32`#### Occupancy assessment on A100- 32 threads/block = 1 warp/block.- A100 has a maximum resident block limit per SM, commonly 32 blocks/SM.- With one warp per block, even with very low register use, the maximum is typically 32 resident warps/SM.- This caps theoretical occupancy at roughly 50% of the 64-warp maximum.Likely occupancy: **limited by one-warp blocks**, approximately half of maximum even before register effects.Energy implication: kernel splitting adds extra global-memory traffic for sample arrays and an extra kernel launch. By itself, this variant is unlikely to be more energy-efficient than the baseline.---### Optimization 2#### Launches1. `sampling_kernel`   - Threads per block: 32   - Blocks: ceiling of `in.lookups / 32`2. `xs_lookup_kernel_optimization_2`   - Launched 12 times, once per material ID.   - Threads per block: 32   - Blocks per launch: ceiling of `in.lookups / 32`#### Occupancy assessment on A100- Same one-warp-block occupancy limitation as Optimization 1.- Each material-specific launch scans the entire lookup array.- Most threads return immediately because their material does not match the current kernel’s material.Likely occupancy: **nominal occupancy limited to about 50%, but useful occupancy is much lower** because many threads exit early.Energy implication: this is likely energy-inefficient. It launches 12 full-array kernels and repeatedly reads `mat_samples`, causing high scheduling and memory energy for work that often does nothing.---### Optimization 3#### Launches1. `sampling_kernel`   - Threads per block: 32   - Blocks: ceiling of `in.lookups / 32`2. `xs_lookup_kernel_optimization_3`   - Launched twice:     - one launch for non-fuel,     - one launch for fuel.   - Threads per block: 32   - Blocks per launch: ceiling of `in.lookups / 32`#### Occupancy assessment on A100- Same one-warp-block occupancy limitation.- Better than Optimization 2 because only two full-array lookup kernels are launched instead of 12.- Still scans the full lookup array twice.Likely occupancy: **limited to roughly 50% theoretical maximum**, with useful occupancy reduced by early-return filtering.Energy implication: better than Optimization 2, but still wastes energy by launching over the entire lookup space twice.---### Optimization 4#### Launches1. `sampling_kernel`   - Threads per block: 32   - Blocks: ceiling of `in.lookups / 32`2. Thrust count operations   - One `thrust::count` per material, 12 total.3. Thrust material sort   - `thrust::sort_by_key` over all lookups.4. `xs_lookup_kernel_optimization_4`   - Launched once per material, 12 launches.   - Threads per block: 32   - Blocks per material: ceiling of `n_lookups_per_material[m] / 32`#### Occupancy assessment on A100- Each lookup kernel still uses one-warp blocks, so theoretical occupancy is capped.- However, unlike Optimization 2, each material kernel operates only on the compacted range for that material.- This greatly improves useful occupancy inside the lookup kernels.- Rare materials may produce small grids and underutilize the GPU.Likely occupancy: **hardware occupancy still limited by 32-thread blocks, but useful work density is much better than Optimization 2 or 3**.Energy implication: this variant trades expensive sorting and counting for better SIMD efficiency and less wasted lookup work. It can be energy-beneficial for large lookup counts, but sorting overhead may dominate for small runs.---### Optimization 5#### Launches1. `sampling_kernel`   - Threads per block: 32   - Blocks: ceiling of `in.lookups / 32`2. Thrust count   - Counts fuel lookups.3. Thrust partition   - Partitions fuel lookups to the front.4. `xs_lookup_kernel_optimization_5`   - First launch: fuel range.   - Second launch: non-fuel range.   - Threads per block: 32   - Blocks:     - ceiling of `n_fuel_lookups / 32`     - ceiling of `(in.lookups - n_fuel_lookups) / 32`#### Occupancy assessment on A100- One-warp-block occupancy limitation remains.- Fuel and non-fuel ranges are compacted, so fewer inactive threads than Optimization 3.- Non-fuel range still mixes many material types, so intra-warp divergence remains for non-fuel lookups.Likely occupancy: **moderate useful occupancy, but capped by 32-thread blocks**.Energy implication: usually more energy-efficient than Optimization 3 because it avoids scanning the entire lookup array twice. Less expensive than a full material sort, but also less effective at reducing divergence.---### Optimization 6#### Launches1. `sampling_kernel`   - Threads per block: 32   - Blocks: ceiling of `in.lookups / 32`2. Thrust count operations   - One count per material, 12 total.3. Thrust material sort   - Sorts by material.4. Per-material energy sorts   - One energy sort per material, 12 total.5. `xs_lookup_kernel_optimization_4`   - Reused for the actual lookup.   - Launched once per material, 12 launches.   - Threads per block: 32   - Blocks per material: ceiling of `n_lookups_per_material[m] / 32`#### Occupancy assessment on A100- Lookup kernels still use 32-thread blocks, so theoretical occupancy remains capped.- Material and energy sorting substantially improves locality and warp coherence.- The actual lookup phase is likely the most energy-efficient of all variants.- However, the additional sorting work can be expensive.Likely occupancy: **hardware occupancy capped by block size, but memory efficiency and useful SIMD efficiency are best among the variants**.Energy implication: best lookup-kernel efficiency, but total energy depends heavily on whether the saved lookup energy exceeds the cost of multiple global sorts.---## 3. Global Memory Access Patterns by Kernel### `xs_lookup_kernel_baseline`#### Access pattern- Each thread processes one independent lookup.- Verification write to `GSD.verification[i]` is coalesced for consecutive active threads.- RNG state is per-thread and does not require global memory.- Material and energy are generated inside the kernel.- The expensive global accesses occur inside `calculate_macro_xs()` and `calculate_micro_xs()`.#### Coalescing assessment- Verification writes: **coalesced**.- `num_nucs`, `mats`, `concs`: often **scattered or non-uniform** because neighboring threads usually have different materials.- `unionized_energy_array`: binary search accesses are **scattered and divergent**.- `index_grid`: **scattered**, often large-stride, and usually not coalesced.- `nuclide_grid`: **scattered**; each thread reads different nuclide/energy locations.- Within one thread, fields of a `NuclideGridPoint` are contiguous, but across a warp, addresses are generally not consecutive.Energy implication: high memory-transaction overhead and poor cache reuse.---### `sampling_kernel`#### Access pattern- Writes `GSD.p_energy_samples[i]`.- Writes `GSD.mat_samples[i]`.#### Coalescing assessment- Writes are **coalesced**: consecutive threads write consecutive addresses.- No expensive global reads except kernel arguments and metadata.Energy implication: efficient memory access pattern, but it adds extra global-memory traffic compared with the baseline.---### `xs_lookup_kernel_optimization_1`#### Access pattern- Reads `GSD.p_energy_samples[i]`.- Reads `GSD.mat_samples[i]`.- Writes `GSD.verification[i]`.- Performs the same lookup pattern as the baseline.#### Coalescing assessment- Sample reads: **coalesced**.- Verification writes: **coalesced**.- Cross-section lookup data: still mostly **scattered**.- Materials remain mixed within warps, so divergence and uncoalesced grid accesses remain.Energy implication: adds coalesced sample traffic but does not substantially fix the random lookup behavior.---### `xs_lookup_kernel_optimization_2`#### Access pattern- Every material kernel scans the full lookup array.- Reads `GSD.mat_samples[i]` to check whether the lookup belongs to material `m`.- Nonmatching threads return.- Matching threads read energy and perform lookup.#### Coalescing assessment- `mat_samples[i]` reads: **coalesced**.- Many threads return before useful work.- Active threads are sparse within warps.- Verification writes for active threads are not dense in general.- Lookup accesses are material-homogeneous only for active threads, but active lanes may be sparse.Energy implication: poor energy efficiency due to repeated full-array scans and sparse useful work.---### `xs_lookup_kernel_optimization_3`#### Access pattern- Two full-array scans:  - fuel,  - non-fuel.- Reads `GSD.mat_samples[i]`.- Threads either perform lookup or skip.#### Coalescing assessment- `mat_samples[i]` reads: **coalesced**.- Fuel launch has sparse active threads because fuel is only a fraction of lookups.- Non-fuel launch has denser active threads but still mixed non-fuel materials.- Lookup accesses remain mostly **scattered**.- Non-fuel branch still suffers variable loop lengths due to different material nuclide counts.Energy implication: better than 12 full scans, but still wastes energy on early-return threads.---### `xs_lookup_kernel_optimization_4`#### Access pattern- Operates on a compacted material-specific range after sorting.- Reads `GSD.p_energy_samples[i]` and `GSD.mat_samples[i]` from contiguous ranges.- Threads in a kernel should mostly have the same material.- Writes `GSD.verification[i]` over a compacted contiguous range.#### Coalescing assessment- Sample reads: **coalesced**.- Verification writes: **coalesced**.- Material table accesses are much more uniform.- `mats` and `concs` accesses can become broadcast-like because all threads in a warp often access the same material and same nuclide-loop index.- Energy values are not sorted in Optimization 4, so grid searches and nuclide-grid loads remain largely **scattered**.- The redundant material check should normally be almost always false after sorting.Energy implication: significantly improved warp efficiency and small-table locality, but large-grid memory accesses remain random.---### `xs_lookup_kernel_optimization_5`#### Access pattern- Operates on two compacted ranges:  - fuel,  - non-fuel.- Reads samples contiguously.- Writes verification contiguously.#### Coalescing assessment- Sample reads: **coalesced**.- Verification writes: **coalesced**.- Fuel range has uniform material and good loop coherence.- Non-fuel range still mixes multiple material types, so divergence remains.- Energy-grid and nuclide-grid accesses are still mostly **scattered**.Energy implication: good compromise between compaction cost and reduced wasted work, but not as locality-friendly as full material sorting.---### `xs_lookup_kernel_optimization_4` as used by Optimization 6#### Access pattern- Inputs are sorted by material and then by energy within each material.- Each material-specific kernel processes a compacted, energy-ordered range.#### Coalescing assessment- Sample reads: **coalesced**.- Verification writes: **coalesced**.- Material data accesses: highly uniform.- Binary searches become more coherent across neighboring threads because energies are sorted.- Nuclide-grid accesses are more clustered.- Cache reuse is much better than in other variants.- Accesses are still not perfectly coalesced because lookup addresses depend on energy-grid indices and data layout, but they are much less random.Energy implication: best lookup-stage energy efficiency due to improved cache reuse and reduced warp divergence.---### `calculate_macro_xs()`#### Access pattern- Reads `num_nucs[mat]`.- Loops over material nuclides.- Reads:  - `mats[mat * max_num_nucs + j]`,  - `concs[mat * max_num_nucs + j]`.- Calls `calculate_micro_xs()` for each nuclide.- Accumulates a 5-element local macro vector.#### Coalescing assessment- If threads in a warp have different materials, reads are **scattered** and loop trip counts diverge.- If threads are grouped by material, `mats` and `concs` reads become highly cache-friendly and potentially broadcast-like.- The material arrays are small and good candidates for constant memory or read-only cache.Energy implication: sorting/grouping by material can substantially reduce wasted warp execution and small-table memory traffic.---### `calculate_micro_xs()`#### Access patternDepending on grid type:- **NUCLIDE**  - Binary search over one nuclide’s energy grid.  - Reads `A[examinationPoint].energy`.  - Later reads two adjacent `NuclideGridPoint` records.- **UNIONIZED**  - Uses previously found unionized index.  - Reads `index_grid[idx * n_isotopes + nuc]`.  - Reads two adjacent `NuclideGridPoint` records.- **HASH**  - Reads hash index bounds from `index_grid`.  - Reads energy bounds from `nuclide_grid`.  - May perform bounded binary search.  - Reads two adjacent `NuclideGridPoint` records.#### Coalescing assessment- Nuclide-grid loads are generally **scattered** across threads.- Per-thread access to `low` and `high` is contiguous, but across a warp, addresses are usually unrelated.- UNIONIZED `index_grid` accesses are often not coalesced because adjacent threads generally have different energy indices.- Energy sorting improves locality, especially for Optimization 6.Energy implication: this is the primary target for energy reduction through sorting, data-layout changes, and precision reduction.---## 4. Shared Memory Usage### Current shared memory usageThe CUDA kernels do **not** explicitly use shared memory.There are no declared shared-memory arrays and no cooperative block-level staging.### Potential shared-memory opportunities#### Material data cachingThe arrays below are small and frequently reused:- `num_nucs`- `mats`- `concs`For material-specific kernels, especially Optimizations 4 and 6, all threads in a block generally process the same material. The material’s nuclide IDs and concentrations could be staged into shared memory once per block.Potential benefit:- Reduces repeated global reads of `mats` and `concs`.- Improves energy efficiency for material-specific kernels.- Shared memory footprint is small. For the largest material, roughly 321 entries of `int` and 321 entries of `double` are needed, which is only a few KiB.Potential drawback:- Requires at least one block-level synchronization after loading.- Constant memory may be even better for these small read-only tables.#### Constant memory / read-only cache alternativeBecause material composition and concentration data are read-only during kernels, they are strong candidates for:- CUDA constant memory,- read-only data cache via compiler/read-only path,- texture-style read-only caching.The probability distribution inside `pick_mat()` is also constant and should not be rebuilt per thread.#### Nuclide grid stagingStaging large portions of `nuclide_grid`, `unionized_energy_array`, or `index_grid` in shared memory is less attractive because:- Accesses are data-dependent.- Working sets are large.- Neighboring threads often access different locations unless energy sorting is used.Optimization 6 improves locality enough that limited cooperative caching might become useful, but the large-grid data are still not obvious shared-memory candidates.---## 5. Warp Divergence### Boundary checksAll explicit kernels contain a bounds check of the form:- if lookup index is outside the valid range, return.This creates divergence only in the final partial block.### `pick_mat()`Divergence sources:- Material selection loop.- Conditional return based on sampled random value.- Different threads likely return different material IDs.This directly causes later divergence in `calculate_macro_xs()`.### `calculate_macro_xs()`Divergence sources:- Branch on grid type:  - UNIONIZED,  - HASH,  - otherwise NUCLIDE.This branch is uniform across the grid if `in.grid_type` is fixed, so it should not cause warp divergence during a given run.Major divergence source:- Loop over `j < num_nucs[mat]`.Different materials have very different numbers of nuclides:- fuel material has up to 321 nuclides,- other materials may have as few as 4 or 5.When materials are mixed within a warp, some lanes execute many more loop iterations than others.This is one of the largest sources of wasted energy.### `calculate_micro_xs()`Divergence sources:- Grid-type branch. Usually uniform across the run.- Binary-search branch:  - comparison between grid energy and particle energy.- Boundary checks for the last grid point.- HASH-specific branches:  - last hash bin check,  - low-energy edge case,  - high-energy edge case,  - bounded binary search path.Binary searches are highly divergent because each thread has a different sampled energy.### `grid_search()` and `grid_search_nuclide()`Divergence sources:- The branch that compares the midpoint energy against the queried energy.- All threads execute approximately the same number of loop iterations for a given grid size, but they take different branch directions.This creates branch divergence and scattered memory reads.### Verification max-index loopDivergence source:- Conditional update when a cross-section channel exceeds the current maximum.The loop is only over 5 entries, so the energy impact is small compared with the lookup phase.### Optimization-specific divergence#### Baseline- High divergence due to mixed materials, mixed energies, and binary searches.#### Optimization 1- Same lookup divergence as baseline.- Sampling separated, but divergence remains.#### Optimization 2- Severe divergence and wasted work from material-filter early returns.- Within active lanes, material is uniform, but active lanes may be sparse.#### Optimization 3- Divergence from fuel/non-fuel predicate.- Non-fuel kernel still has mixed material loop lengths.#### Optimization 4- Much reduced material-loop divergence due to full material sorting.- Energy divergence remains.#### Optimization 5- Fuel range has low material divergence.- Non-fuel range still has mixed material divergence.#### Optimization 6- Lowest divergence among lookup variants.- Material sorting reduces loop-count divergence.- Energy sorting improves binary-search coherence and cache behavior.---## 6. Data Types and Replaceable Double-Precision Operations### Current double-precision usageThe code uses `double` extensively for:- `NuclideGridPoint.energy`- `NuclideGridPoint.total_xs`- `NuclideGridPoint.elastic_xs`- `NuclideGridPoint.absorbtion_xs`- `NuclideGridPoint.fission_xs`- `NuclideGridPoint.nu_fission_xs`- `SimulationData.concs`- `SimulationData.unionized_energy_array`- `SimulationData.p_energy_samples`- `macro_xs_vector`- `xs_vector`- interpolation factor `f`- sampled energy `p_energy`- material probability distribution in `pick_mat()`- random number return value from `LCG_random_double()`- hash-bin width `du`- local energy bounds such as `e_low` and `e_high`### Candidates for conversion to floatIf scientific accuracy and verification requirements allow, the following could be converted from double to float:- particle energy samples,- unionized energy grid,- nuclide energy values,- cross-section values,- concentration values,- microscopic cross-section vectors,- macroscopic cross-section vectors,- interpolation factor,- material-selection probabilities,- hash-bin calculations.### Energy-efficiency benefitPotential benefits of using `float`:- Halves memory footprint for many large arrays.- Reduces DRAM traffic.- Improves cache residency.- Reduces register pressure.- Reduces arithmetic energy per operation.- May improve occupancy if register pressure decreases.### CautionChanging from double to float can change:- binary-search outcomes near energy boundaries,- interpolation results,- maximum-channel selection,- final verification checksum.Therefore, this should be treated as a physics/validation decision, not a purely mechanical optimization.---## 7. Summary of Energy-Efficiency Opportunities### Highest-impact opportunities1. **Reduce random global-memory traffic**   - Sort or group by material and energy.   - Consider HASH mode for reduced memory footprint.   - Separate energy arrays from cross-section arrays to avoid fetching unused fields during binary search.2. **Improve warp coherence**   - Material sorting is valuable because material 0 has far more nuclides than other materials.   - Energy sorting improves binary-search coherence and cache reuse.3. **Avoid wasted full-array material scans**   - Optimization 2 is especially wasteful.   - Optimization 3 is better but still scans the full array twice.   - Compacting or sorting before lookup is more energy-efficient for large workloads.4. **Increase block size for optimized kernels**   - 32-thread blocks cap occupancy on A100.   - 128- or 256-thread blocks would likely improve latency hiding, especially for memory-bound lookup kernels.   - Material grouping can still be preserved with larger blocks.5. **Reduce precision where valid**   - Converting major arrays from double to float could significantly reduce memory energy.   - Must be validated because checksums and boundary decisions may change.6. **Use constant/read-only memory for small tables**   - `num_nucs`, `mats`, `concs`, and material probabilities are good candidates.   - This can reduce repeated global-memory traffic.7. **Minimize unnecessary synchronization and launch overhead**   - Fuse stages when sorting/grouping is not used.   - Avoid repeated full-array launches with early returns.   - Be cautious with Thrust sort/partition overhead for small lookup counts.### Best existing variant from an energy perspective- For large workloads where sorting cost is amortized, **Optimization 6** is likely the most energy-efficient lookup path because it improves both material coherence and energy locality.- For moderate workloads, **Optimization 5** may be a better tradeoff because it reduces fuel/non-fuel divergence with less sorting overhead.- The **baseline** has a better block size but much worse divergence and memory locality.- **Optimization 2** is likely the least energy-efficient due to 12 full-array scans with sparse active work.
