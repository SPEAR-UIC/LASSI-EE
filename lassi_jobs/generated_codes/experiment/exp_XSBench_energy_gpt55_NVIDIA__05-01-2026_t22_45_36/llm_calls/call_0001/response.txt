## Key CUDA Energy-Efficiency Techniques for NVIDIA A100### 1. Coalesce global memory accessesArrange data and indexing so threads in a warp access consecutive memory locations, ideally thread `i` reading `base + i`. Prefer Struct-of-Arrays over Array-of-Structs when each thread reads the same field from different elements.  **Most impactful when:** the kernel is memory-bound or has high HBM2e traffic. On A100, reducing uncoalesced DRAM transactions can greatly reduce both runtime and memory power.### 2. Use shared memory for reused dataLoad data cooperatively from global memory into shared memory when multiple threads in a block reuse the same or nearby values. Avoid shared-memory bank conflicts by choosing layouts where warp threads do not repeatedly hit the same bank.  **Most impactful when:** there is spatial or temporal reuse within a thread block, such as tiled stencils, reductions, matrix-like access patterns, or repeated lookup of shared tables.### 3. Tune occupancy, but avoid chasing maximum occupancy blindlyUse block sizes that are multiples of 32; 128–256 threads per block are often good starting points on A100. Watch register use and shared-memory allocation because excessive use can reduce active warps per SM. Avoid register spilling, since spilled values go to local memory backed by DRAM. Use tools such as the CUDA Occupancy Calculator, `cudaOccupancyMaxPotentialBlockSize`, and Nsight Compute.  **Most impactful when:** latency hiding is poor, memory latency dominates, or register/shared-memory use limits active warps. Good occupancy reduces idle SM time and improves work completed per joule.### 4. Reduce warp divergenceRestructure branches so threads in the same warp follow the same path when possible. Replace short divergent branches with predication or branchless expressions, and group or sort inputs so similar work is processed by the same warps.  **Most impactful when:** branch paths are long, data-dependent, or highly irregular, causing warps to serialize multiple paths with inactive lanes.### 5. Fuse compatible kernelsCombine consecutive kernels that operate on the same data so intermediate results stay in registers or shared memory instead of being written to and reread from global memory. This also reduces kernel launch overhead.  **Most impactful when:** kernels are bandwidth-bound, operate elementwise or pipeline-style on the same arrays, and have compatible launch configurations and dependencies.### 6. Use read-only cache paths with `__ldg` or `const __restrict__`Mark read-only input arrays as `const __restrict__`, and use `__ldg()` explicitly where appropriate. This can route loads through the read-only/texture cache path and reduce L2 and DRAM pressure.  **Most impactful when:** arrays are read-only within the kernel and have spatial or temporal locality. It can also help irregular read-heavy workloads by improving cache behavior.### 7. Choose arithmetic precision carefullyUse single precision instead of double where numerical requirements allow. Prefer FMA operations where possible, and consider CUDA fast-math intrinsics such as `__expf`, `__logf`, `__sinf`, or `__fdividef` only when reduced precision is acceptable. Lower precision reduces data movement, register pressure, instruction cost, and execution time.  **Most impactful when:** kernels are compute-bound, use many floating-point operations, or move large arrays of floating-point data. Always verify that results remain correct.### 8. Minimize synchronization and high-contention atomicsUse `__syncthreads()` only when required by true block-wide data dependencies. Move barriers out of loops when possible, and use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or warp reductions when only intra-warp coordination is needed. Replace many contended atomics with block-level reductions followed by one atomic per block.  **Most impactful when:** barriers occur inside hot loops, blocks have load imbalance, or many threads contend on the same atomic address.### 9. Prefetch and manage data movement explicitlyKeep data resident on the GPU across kernels when possible. Avoid unnecessary host-device transfers. Use pinned host memory and asynchronous copies with streams when transfers are required. For Unified Memory, use explicit prefetching or prefer explicit `cudaMalloc`/`cudaMemcpy` to avoid costly page migrations.  **Most impactful when:** the application repeatedly transfers data between CPU and GPU, uses Unified Memory with page faults, or can overlap data movement with computation.
