## 1. Overall algorithm and GPU resource utilization profile### Algorithm summary- The application implements the event-based XSBench macroscopic cross-section lookup workload.- Each lookup samples:  - A neutron energy.  - A material ID.- For each sampled material, the kernel computes a macroscopic cross-section vector of 5 reaction channels by:  1. Iterating over all nuclides in the selected material.  2. Looking up microscopic cross-section data for each nuclide at the sampled energy.  3. Interpolating between two neighboring energy grid points.  4. Multiplying by the nuclide concentration.  5. Accumulating into the 5-entry macroscopic cross-section vector.- A verification value is generated by finding the index of the maximum cross-section channel.### Workload character- The lookup kernels are primarily memory-latency-bound and irregular-access-bound, not pure compute-bound.- The dominant cost is scattered global memory access into:  - `nuclide_grid`  - `index_grid`  - `unionized_energy_array`  - `mats`  - `concs`- There is also significant control-flow divergence from:  - Material-dependent loop lengths.  - Binary searches.  - Random material selection.  - Conditional early returns in material-specialized kernels.- The sampling kernel is more compute/integer-heavy due to LCG random number generation and fast-forwarding, but its global memory writes are simple and coalesced.### Grid-type effects- `UNIONIZED`:  - Performs one binary search in the large unionized energy grid per lookup.  - Then uses `index_grid` to locate per-nuclide data.  - Still heavily scattered because each thread samples a different energy.- `NUCLIDE`:  - Performs a separate binary search for every nuclide in the material.  - This is the most branch-heavy and divergence-prone mode.- `HASH`:  - Reduces search range using a hash-bin table.  - Still performs scattered accesses into `index_grid` and `nuclide_grid`.### Energy-efficiency profile- The code likely wastes energy through:  - Poor memory coalescing in the main lookup path.  - Low cache reuse for randomly sampled energies.  - Warp divergence from mixed materials and binary searches.  - Double-precision arithmetic and storage where single precision may be sufficient.  - Multiple small-block kernels using 32-thread blocks, which can limit A100 occupancy.  - Extra global-memory traffic and launch overhead in the split/sort variants.- The most energy-efficient variants are likely those that improve locality and reduce divergence, especially Optimization 6, which sorts by material and then by energy.---## 2. CUDA kernel launch configurations and likely A100 occupancy### Baseline- Kernel: `xs_lookup_kernel_baseline`- Launch:  - Block size: 256 threads  - Grid size: `ceil(in.lookups / 256)`- A100 occupancy expectation:  - 256 threads/block = 8 warps/block.  - This is a reasonable block size for A100 and can achieve high theoretical occupancy if register usage is not excessive.  - Actual occupancy may be reduced by register pressure from:    - `macro_xs_vector[5]`    - `xs_vector[5]`    - inlined interpolation logic    - `pick_mat` local `dist[12]`    - 64-bit integer RNG state  - No shared-memory pressure.### Optimization 1- Kernels:  - `sampling_kernel`  - `xs_lookup_kernel_optimization_1`- Launch:  - Block size: 32 threads  - Grid size: `ceil(in.lookups / 32)`- A100 occupancy expectation:  - 32 threads/block = 1 warp/block.  - On A100, the architectural block limit per SM can cap occupancy before the warp limit is reached.  - With a maximum of 32 resident blocks/SM, one-warp blocks can reach at most 32 resident warps/SM, approximately 50% of the 64-warp A100 maximum.  - This configuration may underutilize the SMs even if register usage is modest.### Optimization 2- Kernels:  - `sampling_kernel`  - `xs_lookup_kernel_optimization_2`, launched once for each of 12 materials.- Launch:  - Sampling:    - Block size: 32 threads    - Grid size: `ceil(in.lookups / 32)`  - Lookup:    - 12 launches    - Each uses block size: 32 threads    - Each uses grid size: `ceil(in.lookups / 32)`- A100 occupancy expectation:  - Same one-warp-block occupancy limitation as Optimization 1.  - Additionally, each material-specific kernel scans the full lookup array and most threads return early for nonmatching materials.  - This can waste launch energy and instruction energy, especially for rare materials.### Optimization 3- Kernels:  - `sampling_kernel`  - `xs_lookup_kernel_optimization_3`, launched twice.- Launch:  - Sampling:    - Block size: 32 threads    - Grid size: `ceil(in.lookups / 32)`  - Lookup:    - 2 launches    - Each uses block size: 32 threads    - Each uses grid size: `ceil(in.lookups / 32)`- A100 occupancy expectation:  - Same one-warp-block occupancy limitation.  - Less launch overhead than Optimization 2.  - Still scans the full lookup array twice.  - Reduces some material-loop divergence by separating fuel from nonfuel work, but the nonfuel kernel still contains mixed material loop lengths.### Optimization 4- Kernels:  - `sampling_kernel`  - `xs_lookup_kernel_optimization_4`, launched once per material after sorting.- Launch:  - Sampling:    - Block size: 32 threads    - Grid size: `ceil(in.lookups / 32)`  - Lookup:    - 12 launches    - Each uses block size: 32 threads    - Grid size per material: `ceil(n_lookups_per_material[m] / 32)`- A100 occupancy expectation:  - One-warp-block occupancy cap remains.  - Better work efficiency than Optimization 2 because each material kernel processes only its material’s compacted range.  - Material-homogeneous warps reduce loop-length divergence.  - Sorting overhead may be large but can improve energy efficiency if lookup cost dominates.### Optimization 5- Kernels:  - `sampling_kernel`  - `xs_lookup_kernel_optimization_5`, launched once for fuel and once for nonfuel.- Launch:  - Sampling:    - Block size: 32 threads    - Grid size: `ceil(in.lookups / 32)`  - Fuel lookup:    - Block size: 32 threads    - Grid size: `ceil(n_fuel_lookups / 32)`  - Nonfuel lookup:    - Block size: 32 threads    - Grid size: `ceil((in.lookups - n_fuel_lookups) / 32)`- A100 occupancy expectation:  - One-warp-block occupancy cap remains.  - Less launch overhead than Optimization 4.  - Better separation of the high-cost fuel material from lower-cost materials.  - Nonfuel work remains heterogeneous.### Optimization 6- Kernels:  - `sampling_kernel`  - `xs_lookup_kernel_optimization_4`, reused after material and energy sorting.- Launch:  - Sampling:    - Block size: 32 threads    - Grid size: `ceil(in.lookups / 32)`  - Lookup:    - 12 launches    - Each uses block size: 32 threads    - Grid size per material: `ceil(n_lookups_per_material[m] / 32)`- A100 occupancy expectation:  - One-warp-block occupancy cap remains.  - Despite limited theoretical occupancy, this variant likely has the best energy behavior because it improves:    - Material uniformity within warps.    - Energy locality.    - Cache reuse.    - Binary-search path similarity.    - `index_grid` and `nuclide_grid` locality.  - Sorting overhead is substantial, so this is most beneficial for large lookup counts.### Thrust operationsThe following Thrust operations launch internal CUDA kernels with implementation-defined configurations:- `thrust::reduce`- `thrust::count`- `thrust::sort_by_key`- `thrust::partition`These add additional kernel launches, memory traffic, and synchronization dependencies. Their launch configurations are not explicitly visible in the source.---## 3. Global memory access patterns by kernel### `sampling_kernel`- Reads:  - Mostly scalar input fields from `Inputs`.- Writes:  - `GSD.p_energy_samples[i]`  - `GSD.mat_samples[i]`- Access pattern:  - Consecutive thread IDs write consecutive array elements.  - These writes are coalesced.- Energy-efficiency note:  - This kernel has efficient global memory behavior.  - Main cost is integer RNG and control flow in `pick_mat`.### `xs_lookup_kernel_baseline`- Reads/writes:  - `GSD.verification[i]` write is coalesced.  - Main data reads are scattered.- Access pattern:  - `nuclide_grid` accesses are highly scattered because each thread uses a different random energy and material.  - `unionized_energy_array` binary-search accesses are divergent and noncoalesced.  - `index_grid[idx * n_isotopes + nuc]` is scattered because `idx` differs by sampled energy.  - `mats[mat * max_num_nucs + j]` and `concs[mat * max_num_nucs + j]` may be partially cache-friendly for threads with the same material, but baseline warps mix materials randomly.- Coalescing:  - Verification writes: coalesced.  - Main lookup data: mostly noncoalesced/scattered.### `xs_lookup_kernel_optimization_1`- Reads:  - `GSD.p_energy_samples[i]`  - `GSD.mat_samples[i]`- Writes:  - `GSD.verification[i]`- Access pattern:  - Sample reads and verification writes are coalesced.  - Main lookup data remains scattered as in baseline.- Energy-efficiency note:  - Splitting sampling and lookup adds extra global-memory traffic for sampled energy/material arrays.  - By itself, this likely reduces energy efficiency unless it enables later grouping/sorting optimizations.### `xs_lookup_kernel_optimization_2`- Reads:  - Coalesced reads of `mat_samples[i]` to test material.  - Coalesced reads of `p_energy_samples[i]` only for matching material threads.- Writes:  - Coalesced verification writes for active threads.- Access pattern:  - Each of 12 kernels scans the full sample array.  - Most threads return early in each material-specific kernel.  - Main lookup accesses are less divergent among active threads with matching material, but active lanes are sparse without sorting.- Coalescing:  - Sample-array reads: coalesced.  - Main lookup accesses: still scattered.- Energy-efficiency note:  - Wastes energy scanning nonmatching entries 12 times.### `xs_lookup_kernel_optimization_3`- Reads:  - Coalesced sample-array reads.- Writes:  - Coalesced verification writes for active threads.- Access pattern:  - Full sample array is scanned twice.  - Fuel and nonfuel paths are separated.  - Fuel work becomes more homogeneous, but nonfuel remains mixed.- Coalescing:  - Sample-array access: coalesced.  - Lookup data: mostly scattered, with some improvement for fuel/nonfuel separation.### `xs_lookup_kernel_optimization_4`- Reads:  - Sorted `mat_samples` and associated `p_energy_samples`.- Writes:  - `GSD.verification[i]` in compact material ranges.- Access pattern:  - Processes contiguous ranges per material.  - Material reads are coalesced.  - Energy reads are coalesced.  - `mats` and `concs` become much more cache-friendly because all active threads in a kernel use the same material.  - `nuclide_grid`, `index_grid`, and `unionized_energy_array` accesses are still energy-scattered unless energies are also sorted.- Coalescing:  - Sample reads and verification writes: coalesced.  - Material metadata: improved locality/broadcast potential.  - Main grid data: still partially scattered.### `xs_lookup_kernel_optimization_5`- Reads:  - Partitioned fuel/nonfuel sample ranges.- Writes:  - Verification writes in contiguous ranges.- Access pattern:  - Fuel range has improved material uniformity.  - Nonfuel range remains material-heterogeneous.  - Main grid access remains mostly scattered by energy.- Coalescing:  - Sample reads and verification writes: coalesced.  - Fuel material metadata: improved locality.  - Nonfuel metadata and grid accesses: still irregular.### Optimization 6 lookup path- Uses `xs_lookup_kernel_optimization_4` after sorting by material and then sorting by energy within each material.- Access pattern:  - Best locality among all variants.  - Consecutive threads tend to process:    - Same material.    - Nearby energy values.    - Similar binary-search paths.    - Nearby `unionized_energy_array` indices.    - Nearby `index_grid` rows.    - More reusable `nuclide_grid` locations.- Coalescing:  - Sample reads and verification writes: coalesced.  - Material metadata: highly cache-friendly.  - Grid accesses: still not perfectly coalesced, but significantly less scattered than random-energy variants.- Energy-efficiency note:  - Likely the strongest energy-efficiency opportunity, especially when lookup count is large enough to amortize sorting cost.---## 4. Shared memory usage: current and potential### Current usage- There is no explicit shared memory allocation.- There are no `__shared__` variables.- There are no dynamic shared-memory kernel launches.- The code relies on:  - Global memory.  - Registers/local memory.  - L1/L2 cache.  - Thrust internal temporary storage.### Potential shared or constant memory opportunities- Small read-only data could be moved to constant memory or cached per block:  - `num_nucs[12]`  - `mats`  - `concs`  - `pick_mat` probability distribution `dist[12]`  - Frequently used fields of `Inputs`- Material-specific kernels are especially good candidates for caching material data because all threads in a kernel use the same material.- For fuel material, the data volume is larger but still modest:  - Up to 321 nuclides.  - Nuclide IDs and concentrations for one material could fit in shared memory.- Benefits:  - Reduced repeated global loads of material metadata.  - Better broadcast behavior.  - Lower L2 traffic.  - Lower energy per lookup.- Limitations:  - `nuclide_grid`, `index_grid`, and `unionized_energy_array` are too large for shared memory.  - Per-block shared caching of grid points may only help after energy sorting, where neighboring threads access nearby energy intervals.- Optimization 6 provides the best precondition for useful shared-memory tiling because energy locality is improved.---## 5. Warp divergence### Boundary checksAll explicit kernels contain boundary checks such as:- `if (i >= in.lookups) return`- `if (i >= n_lookups) return`These only diverge in the final partial block and are not a major concern.### Sampling divergence- `pick_mat` contains nested loops and an early return based on random `roll`.- Different lanes may return different materials at different iterations.- This causes warp divergence during material selection.### RNG divergence- `fast_forward_LCG` contains:  - A `while (n > 0)` loop.  - A branch on `if (n & 1)`.- Since `n` depends on the lookup index, lanes may take different branch paths.### Material-loop divergence- `calculate_macro_xs` loops over:  - `j < num_nucs[mat]`- `num_nucs[mat]` varies greatly by material:  - Fuel has up to 321 nuclides.  - Other materials may have as few as 4 or 5.- In baseline and unsorted variants, a warp can contain mixed materials, causing severe loop-length divergence.- Material sorting in Optimizations 4 and 6 reduces this substantially.### Grid-type branches- `calculate_macro_xs` branches on:  - `grid_type == UNIONIZED`  - `grid_type == HASH`- `calculate_micro_xs` branches on:  - `grid_type == NUCLIDE`  - `grid_type == UNIONIZED`  - otherwise HASH- Since `grid_type` is uniform for the whole run, these branches are not warp-divergent, but they still add instruction overhead unless specialized kernels are generated.### Binary-search divergence- `grid_search` and `grid_search_nuclide` contain:  - `while (length > 1)`  - `if (A[examinationPoint] > quarry)`- Even when loop counts are similar, branch direction differs by sampled energy.- This causes warp divergence and scattered memory access.- Energy sorting in Optimization 6 reduces this by making nearby lanes search nearby locations.### Edge-case divergence in `calculate_micro_xs`Branches include:- `if (idx == n_gridpoints - 1)`- `if (index_data[idx * n_isotopes + nuc] == n_gridpoints - 1)`- `if (idx == hash_bins - 1)`- `if (p_energy <= e_low)`- `else if (p_energy >= e_high)`- `if (lower == n_gridpoints - 1)`These can diverge across lanes depending on energy and nuclide.### Verification divergenceEach lookup kernel finds the maximum channel using:- `if (macro_xs_vector[j] > max)`This is a small fixed loop of length 5. Divergence cost is minor compared with grid lookup divergence.### Material-filter divergence- Optimization 2:  - `if (mat != m) return`  - Highly divergent and inefficient before sorting.- Optimization 3:  - Fuel/nonfuel conditional is divergent but less severe than 12 separate material filters.- Optimization 4:  - `if (mat != m) return`  - Mostly redundant after sorting and count-based range selection; should rarely diverge except for safety.- Optimization 5:  - No material equality branch in the lookup kernel, but nonfuel range remains material-heterogeneous.---## 6. Data types and double-precision replacement opportunities### Current double-precision usageThe following are stored or computed as `double`:- `NuclideGridPoint.energy`- `NuclideGridPoint.total_xs`- `NuclideGridPoint.elastic_xs`- `NuclideGridPoint.absorbtion_xs`- `NuclideGridPoint.fission_xs`- `NuclideGridPoint.nu_fission_xs`- `concs`- `unionized_energy_array`- `p_energy_samples`- `p_energy`- `macro_xs_vector[5]`- `xs_vector[5]`- interpolation factor `f`- `du`- material probability values in `pick_mat`- RNG return value from `LCG_random_double`### Replacement opportunitiesIf numerical tolerance and benchmark verification requirements permit, the following could be converted to `float`:- Cross-section values in `NuclideGridPoint`.- Energy values in `NuclideGridPoint`.- `unionized_energy_array`.- `concs`.- `p_energy_samples`.- `p_energy`.- `xs_vector`.- `macro_xs_vector`.- Interpolation arithmetic.- Material probability distribution in `pick_mat`.### Energy-efficiency benefit of using float- Reduces global-memory footprint.- Reduces memory bandwidth and L2 traffic.- Improves cache residency.- Reduces register footprint.- Improves arithmetic energy efficiency.- May increase occupancy if register pressure drops.### Caution- Replacing `double` with `float` will likely change the verification checksum.- If bitwise or checksum compatibility is required, the double-precision behavior must be preserved.- The LCG state should remain 64-bit integer because it defines the random sequence.---## 7. Main energy-efficiency opportunities### Highest-impact opportunities1. **Use material and energy sorting when lookup count is large**   - Optimization 6 is the strongest locality-improving strategy.   - It reduces warp divergence and increases cache reuse.2. **Increase block size for 32-thread kernels**   - Many optimized kernels use one-warp blocks.   - On A100, this can cap occupancy around 50%.   - Larger blocks such as 128 or 256 threads may improve occupancy and energy efficiency, assuming material grouping benefits are not lost.3. **Specialize kernels by grid type**   - `grid_type` is uniform for a run.   - Separate kernels for `UNIONIZED`, `NUCLIDE`, and `HASH` would remove uniform branches and improve compiler optimization.4. **Specialize kernels by material**   - Material-specific kernels could hard-code or pre-load `num_nucs[mat]`.   - This would reduce loop-control overhead and enable better unrolling for small materials.5. **Move small read-only arrays to constant memory**   - Good candidates:     - `num_nucs`     - material nuclide lists     - concentrations     - material probability distribution   - Especially beneficial after sorting by material.6. **Consider single precision**   - If checksum and accuracy requirements allow, replacing many `double` values with `float` would reduce memory traffic and arithmetic energy.7. **Reduce host synchronization**   - Remove unnecessary `cudaDeviceSynchronize()` calls where stream ordering is enough.   - Use CUDA graphs for multi-kernel variants.8. **Improve data layout**   - Current `NuclideGridPoint` is an array-of-structures layout.   - Since each lookup reads all reaction channels for a selected point, AoS has some per-thread locality.   - However, across threads accesses are scattered.   - A structure-of-arrays or hybrid layout may improve coalescing when energy sorting causes neighboring threads to access nearby grid points.9. **Cache material data per block**   - For material-sorted kernels, load material nuclide IDs and concentrations into shared memory once per block.   - This reduces repeated global reads of `mats` and `concs`.10. **Avoid repeated full-array scans**   - Optimization 2 scans the full lookup array 12 times.   - Optimization 3 scans it twice.   - Compaction/sorting approaches are more energy efficient when the lookup computation is expensive enough to amortize the sort.
