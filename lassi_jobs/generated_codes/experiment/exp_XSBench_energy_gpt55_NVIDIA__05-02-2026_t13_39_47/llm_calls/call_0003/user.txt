## Key CUDA Energy-Efficiency Techniques for NVIDIA A100

### 1. Coalesce global memory accesses
Arrange data and indexing so threads in a warp access consecutive memory locations. Prefer structure-of-arrays layouts over array-of-structures when each thread reads the same field from different elements.  
**Most impactful when:** the kernel is memory-bound and performs large global-memory reads/writes; poor coalescing can multiply HBM transactions and energy use.

### 2. Use shared memory for reused data
Load reusable global-memory data once per block into shared memory, then have threads reuse the on-chip copy. Avoid shared-memory bank conflicts by ensuring warp threads do not repeatedly map to the same bank. On A100, shared memory is large enough to support substantial tiling when occupancy remains acceptable.  
**Most impactful when:** multiple threads in a block access overlapping or nearby data, such as tiled stencils, matrix-like operations, reductions, or shared lookup regions.

### 3. Tune occupancy, but avoid chasing maximum occupancy blindly
Use block sizes that are multiples of 32; 128–256 threads per block are often a good starting point on A100. Balance occupancy against register use and shared-memory use. Avoid register spilling, because spilled local memory goes to DRAM. Use Nsight Compute and CUDA occupancy tools to identify limits.  
**Most impactful when:** latency hiding is insufficient, memory latency dominates, or excessive registers/shared memory reduce active warps per SM.

### 4. Reduce warp divergence
Keep threads in the same warp on the same control-flow path when possible. Replace short divergent branches with predication or branchless arithmetic, and group or sort work so neighboring threads execute similar paths.  
**Most impactful when:** branches depend on per-thread data and large portions of a warp take different paths, causing serialized execution and wasted active cycles.

### 5. Fuse kernels when it eliminates global-memory round trips
Combine consecutive kernels that operate on the same data so intermediate values stay in registers or shared memory instead of being written to and reread from HBM. This also reduces launch overhead.  
**Most impactful when:** kernels are bandwidth-bound, use temporary arrays, or perform simple producer-consumer stages with compatible launch configurations and dependencies.

### 6. Use read-only cache paths for immutable data
Mark read-only input pointers as `const __restrict__`, and use `__ldg()` where appropriate to route loads through the read-only/texture cache path. This can reduce L2 and DRAM traffic for repeated or spatially local reads.  
**Most impactful when:** arrays are read-only within the kernel and have temporal or spatial locality; it can still help for irregular read-heavy lookup workloads.

### 7. Choose arithmetic precision deliberately
Use `float`, FP16/BF16, or Tensor Cores where the application’s accuracy requirements allow it. Avoid unnecessary `double`, which increases memory traffic, register pressure, and compute cost. Use FMA where possible, and consider fast-math intrinsics only when reduced precision is acceptable.  
**Most impactful when:** the kernel is compute-bound, uses many floating-point operations, or stores/transfers large numeric arrays whose precision can be safely reduced.

### 8. Minimize synchronization and high-contention atomics
Remove unnecessary `__syncthreads()`, move barriers out of loops when safe, and use warp-level primitives such as `__syncwarp()` or warp reductions when only intra-warp coordination is needed. Replace per-thread atomics with block-level reductions followed by one atomic per block.  
**Most impactful when:** kernels contain frequent barriers, reductions, or many threads contending for the same atomic location.

### 9. Prefetch and overlap data movement where possible
Keep data resident on the GPU across kernels. For host-device transfers, use pinned memory and `cudaMemcpyAsync` with streams to overlap transfers with computation. If using Unified Memory, prefetch data explicitly to the GPU to avoid costly page migrations during kernels.  
**Most impactful when:** runtime includes significant host-device transfers, Unified Memory page faults, or pipelines where data movement can be overlapped with GPU execution.

## 1. Overall algorithm and GPU resource-utilization profile

### Algorithm summary
- The program implements an event-based XSBench-style macroscopic cross-section lookup workload.
- Each lookup samples:
  - one neutron energy,
  - one material ID,
  - then computes a macroscopic cross-section vector over the nuclides in that material.
- For each nuclide in the selected material, the code:
  - finds the bounding energy grid points using one of three grid modes:
    - unionized grid,
    - nuclide grid,
    - hash grid,
  - interpolates five microscopic cross-section channels,
  - multiplies by material concentration,
  - accumulates into a five-element macroscopic cross-section vector.
- The final verification value is the index of the maximum cross-section channel, written per lookup and later reduced with Thrust.

### Compute-bound vs memory-bound behavior
- The workload is primarily memory-latency-bound / cache-behavior-bound, not purely compute-bound.
- There is nontrivial double-precision arithmetic, especially interpolation and RNG, but the dominant cost is irregular global-memory access:
  - random or data-dependent accesses into `nuclide_grid`,
  - binary-search access patterns into `unionized_energy_array`,
  - data-dependent accesses into `index_grid`,
  - material-dependent loop lengths.
- On an A100, FP64 throughput is high, so the irregular memory access pattern and branch divergence are more likely to dominate energy and time than raw floating-point throughput.
- The unionized and hash modes reduce search work compared with per-nuclide binary search, but introduce additional index-grid memory traffic.
- Optimization 6, which groups by material and then sorts by energy, is the most energy-relevant variant because it improves:
  - warp uniformity,
  - cache reuse,
  - locality in energy-grid searches,
  - locality in `nuclide_grid` accesses.

### Random vs sequential access profile
- Sampling and verification arrays are accessed sequentially and are generally coalesced.
- Cross-section data accesses are mostly scattered in the baseline and early optimized variants.
- Material sorting improves access regularity for material metadata and loop bounds.
- Energy sorting improves locality for energy-grid and nuclide-grid accesses, but does not make all accesses strictly coalesced because the index-grid and nuclide-grid layout still create strided or indirect patterns.

### Energy-efficiency opportunities
- The most important energy opportunities are:
  - reduce scattered global-memory traffic,
  - improve warp uniformity by grouping work by material,
  - improve cache reuse by sorting or binning by energy,
  - use lower precision where validation allows,
  - avoid one-warp blocks when larger blocks can preserve grouping,
  - reduce redundant scans of the lookup arrays in Optimization 2 and 3,
  - move small read-only tables to constant memory or otherwise exploit broadcast caching,
  - avoid unnecessary host/device synchronization when measuring is not required.

## 2. CUDA kernel launch configurations and likely A100 occupancy

### Baseline: `xs_lookup_kernel_baseline`
- Launch configuration:
  - block size: 256 threads
  - grid size: `ceil(in.lookups / 256)`
- A100 occupancy expectation:
  - Theoretical occupancy can be high.
  - 256-thread blocks allow up to 8 resident blocks per SM on A100, reaching 2048 resident threads / 64 warps per SM if registers and other limits permit.
  - Actual occupancy may be reduced by register pressure from:
    - local arrays such as five-element cross-section vectors,
    - inlined interpolation logic,
    - double-precision temporaries,
    - RNG state and binary-search variables.
  - Despite potentially high theoretical occupancy, effective utilization is reduced by:
    - divergent material loop lengths,
    - divergent binary-search branches,
    - scattered memory accesses.

### Optimization 1: `sampling_kernel` and `xs_lookup_kernel_optimization_1`
- Launch configuration for both kernels:
  - block size: 32 threads
  - grid size: `ceil(in.lookups / 32)`
- A100 occupancy expectation:
  - One warp per block.
  - A100 allows at most 32 resident blocks per SM, so this configuration is limited to at most 32 resident warps / 1024 resident threads per SM.
  - This caps theoretical occupancy at roughly 50% of the A100 maximum thread/warp occupancy.
  - The one-warp block size also increases block scheduling overhead.
- Energy implication:
  - Kernel splitting adds global-memory writes and reads for sampled energies/materials.
  - Without later sorting or partitioning, this is likely less energy-efficient than the baseline.

### Optimization 2: `sampling_kernel` plus twelve launches of `xs_lookup_kernel_optimization_2`
- Sampling launch:
  - block size: 32 threads
  - grid size: `ceil(in.lookups / 32)`
- Lookup launches:
  - 12 separate kernel launches
  - each launch uses block size 32
  - each launch uses grid size `ceil(in.lookups / 32)`
  - each launch processes only one material ID and returns early for all other materials.
- A100 occupancy expectation:
  - Same one-warp-block limitation: at most about 50% theoretical occupancy.
  - Effective occupancy is much lower for each material kernel because most threads return early unless their sampled material matches the launch material.
- Energy implication:
  - This variant repeatedly scans the entire `mat_samples` array 12 times.
  - It reduces intra-thread workload imbalance for active threads, but wastes energy on inactive threads and repeated memory reads.

### Optimization 3: `sampling_kernel` plus two launches of `xs_lookup_kernel_optimization_3`
- Sampling launch:
  - block size: 32 threads
  - grid size: `ceil(in.lookups / 32)`
- Lookup launches:
  - two launches
  - block size: 32 threads
  - grid size: `ceil(in.lookups / 32)`
  - one launch handles non-fuel materials, one launch handles fuel.
- A100 occupancy expectation:
  - Same one-warp-block limitation: at most about 50% theoretical occupancy.
  - Better than Optimization 2 because there are only two full-array scans instead of twelve.
  - Still suffers from early-return lanes and sparse active work.
- Energy implication:
  - More energy-efficient than Optimization 2 for the same grouping concept, but still not ideal because all lookups are scanned twice.

### Optimization 4: `sampling_kernel`, Thrust counts/sort, then per-material `xs_lookup_kernel_optimization_4`
- Sampling launch:
  - block size: 32 threads
  - grid size: `ceil(in.lookups / 32)`
- Lookup launches:
  - 12 launches, one per material
  - block size: 32 threads
  - grid size per material: `ceil(n_lookups_per_material[m] / 32)`
- Additional GPU work:
  - 12 Thrust count operations
  - one Thrust sort by material
  - one Thrust reduction
- A100 occupancy expectation:
  - Each custom lookup kernel still uses one-warp blocks, limiting theoretical occupancy to about 50%.
  - For common materials, there may be enough blocks to fill the GPU.
  - For rare materials or small lookup counts, the per-material grids may be too small to saturate the A100.
- Energy implication:
  - Sorting cost may be significant.
  - However, material grouping greatly improves warp uniformity and reduces divergent material loop lengths.
  - For large lookup counts, this can be more energy-efficient despite the sort overhead.

### Optimization 5: `sampling_kernel`, Thrust count/partition, then two launches of `xs_lookup_kernel_optimization_5`
- Sampling launch:
  - block size: 32 threads
  - grid size: `ceil(in.lookups / 32)`
- Lookup launches:
  - fuel segment:
    - block size: 32 threads
    - grid size: `ceil(n_fuel_lookups / 32)`
  - non-fuel segment:
    - block size: 32 threads
    - grid size: `ceil((in.lookups - n_fuel_lookups) / 32)`
- Additional GPU work:
  - one Thrust count
  - one Thrust partition
  - one Thrust reduction
- A100 occupancy expectation:
  - Same one-warp-block limit of about 50% theoretical occupancy.
  - Better GPU utilization than Optimization 3 because work is compacted into contiguous fuel and non-fuel regions.
  - Non-fuel material variation remains.
- Energy implication:
  - Likely a good compromise between sorting overhead and divergence reduction.
  - Less expensive than full material sorting, but less locality improvement than Optimization 4 or 6.

### Optimization 6: `sampling_kernel`, material sort, per-material energy sort, then per-material `xs_lookup_kernel_optimization_4`
- Sampling launch:
  - block size: 32 threads
  - grid size: `ceil(in.lookups / 32)`
- Lookup launches:
  - 12 launches of `xs_lookup_kernel_optimization_4`
  - block size: 32 threads
  - grid size per material: `ceil(n_lookups_per_material[m] / 32)`
- Additional GPU work:
  - 12 Thrust count operations
  - one Thrust material sort
  - 12 Thrust energy sorts, one per material segment
  - one Thrust reduction
- A100 occupancy expectation:
  - Custom lookup kernels remain one-warp-block kernels, so theoretical occupancy is capped around 50%.
  - Effective utilization can nevertheless improve substantially because warp lanes perform similar work and access similar energy regions.
- Energy implication:
  - Potentially the best lookup-kernel energy efficiency due to improved cache reuse and reduced divergence.
  - Total application energy depends on whether the extra sorting cost is amortized by the lookup savings.
  - For very large lookup counts, this is likely favorable.
  - For small lookup counts, sorting overhead may dominate.

### Thrust kernels
- The code also invokes Thrust reductions, counts, sorts, and partition operations.
- Their internal launch configurations are library-controlled and not visible in the source.
- These operations can consume significant energy, especially:
  - full-array sort by material,
  - per-material energy sorts,
  - repeated counts in Optimization 4 and 6.

### Block-size opportunity
- Many optimized variants use 32-thread blocks.
- On A100, this limits theoretical occupancy because of the maximum resident-block limit.
- Using 128- or 256-thread blocks would allow more resident warps per SM while preserving independent-thread semantics.
- If material/energy grouping is retained, larger blocks could improve latency hiding and energy efficiency without necessarily increasing divergence.

## 3. Global-memory access patterns by kernel

### `sampling_kernel`
- Reads:
  - no major global reads except structure metadata.
- Writes:
  - `GSD.p_energy_samples[i]`
  - `GSD.mat_samples[i]`
- Access pattern:
  - consecutive thread IDs write consecutive addresses.
  - writes are coalesced.
- Energy profile:
  - Mostly compute/RNG plus coalesced stores.
  - The per-thread material distribution array may increase register pressure or spill if not optimized.

### `xs_lookup_kernel_baseline`
- Writes:
  - `GSD.verification[i]`
  - consecutive thread IDs write consecutive addresses.
  - verification stores are coalesced.
- Major reads:
  - `num_nucs`
  - `mats`
  - `concs`
  - `unionized_energy_array`
  - `index_grid`
  - `nuclide_grid`
- Access pattern:
  - The sampled energy and material are generated inside the kernel, so there are no sample-array reads.
  - `num_nucs[mat]` is small-table access but material varies across threads.
  - `mats[mat * max_num_nucs + j]` and `concs[mat * max_num_nucs + j]` are only coalesced or broadcast-like when warp lanes share the same material and loop index.
  - In the baseline, materials are random, so these accesses are often scattered or partially divergent.
  - `unionized_energy_array` binary searches are data-dependent. Early binary-search iterations may touch common locations, but branches quickly diverge.
  - `index_grid[idx * n_isotopes + nuc]` is indirect and generally scattered across warp lanes.
  - `nuclide_grid[nuc * n_gridpoints + index]` is highly scattered across warp lanes.
  - Within one thread, the low/high grid-point pair is adjacent, but across threads addresses are generally not consecutive.
- Coalescing:
  - verification writes: coalesced.
  - main cross-section data reads: mostly uncoalesced/scattered.

### `xs_lookup_kernel_optimization_1`
- Reads:
  - `GSD.p_energy_samples[i]`
  - `GSD.mat_samples[i]`
  - both are consecutive-thread to consecutive-address reads.
- Writes:
  - `GSD.verification[i]`, coalesced.
- Cross-section data access:
  - same as baseline after the sampled values are loaded.
- Coalescing:
  - sample reads and verification writes are coalesced.
  - cross-section grid reads remain mostly scattered.
- Energy profile:
  - Adds sample-array memory traffic relative to baseline.
  - Does not by itself fix the scattered lookup pattern.

### `xs_lookup_kernel_optimization_2`
- Reads:
  - all threads read `GSD.mat_samples[i]` sequentially; this read is coalesced.
  - only matching-material threads continue and read `GSD.p_energy_samples[i]`.
- Writes:
  - active threads write `GSD.verification[i]`.
  - addresses correspond to original lookup IDs, so stores are within consecutive regions but with inactive lanes.
- Cross-section data access:
  - active lanes within a given material launch have uniform material ID, which improves loop-bound uniformity.
  - However, because the array has not been compacted, active lanes are sparse and not necessarily adjacent.
- Coalescing:
  - material-sample scan is coalesced but repeated 12 times.
  - active lookup work is sparse.
  - cross-section data reads remain scattered by energy.
- Energy profile:
  - High overhead from repeated full-array scans and early returns.

### `xs_lookup_kernel_optimization_3`
- Reads:
  - all threads read `GSD.mat_samples[i]` sequentially in each of two launches.
  - active threads read `GSD.p_energy_samples[i]`.
- Writes:
  - active threads write `GSD.verification[i]`.
- Cross-section data access:
  - fuel and non-fuel are separated, reducing the worst material loop-length divergence.
  - Non-fuel materials are still heterogeneous.
- Coalescing:
  - sample reads are coalesced.
  - active lanes may be sparse.
  - cross-section reads remain mostly scattered.
- Energy profile:
  - Better than Optimization 2 because only two full scans occur.
  - Still wastes work on inactive lanes.

### `xs_lookup_kernel_optimization_4`
- Reads:
  - after material sorting, `GSD.mat_samples[i]` and `GSD.p_energy_samples[i]` are read from contiguous material-specific segments.
- Writes:
  - `GSD.verification[i]` is written contiguously within each material segment.
- Cross-section data access:
  - all lanes in a material kernel should have the same material.
  - `num_nucs[mat]` loop bounds become uniform across warp lanes.
  - `mats` and `concs` accesses become broadcast-like because all lanes use the same material and same loop index.
  - Energy values are not sorted in Optimization 4, so `unionized_energy_array`, `index_grid`, and `nuclide_grid` accesses remain energy-scattered.
- Coalescing:
  - sample and verification accesses are coalesced.
  - material metadata access is much more cache/broadcast-friendly.
  - nuclide and energy-grid accesses remain mostly indirect/scattered.
- Energy profile:
  - Significant divergence reduction.
  - Sorting overhead must be justified by lookup count.

### `xs_lookup_kernel_optimization_5`
- Reads:
  - after partitioning, fuel and non-fuel segments are contiguous.
  - `GSD.p_energy_samples[i]` and `GSD.mat_samples[i]` are coalesced within each segment.
- Writes:
  - `GSD.verification[i]` is contiguous within each segment.
- Cross-section data access:
  - fuel segment is uniform and benefits strongly.
  - non-fuel segment still contains mixed materials, so divergence remains.
- Coalescing:
  - sample and verification accesses are coalesced.
  - fuel metadata accesses are uniform.
  - non-fuel metadata and grid accesses remain mixed.
- Energy profile:
  - Lower overhead than full sort.
  - Good practical energy compromise when fuel/non-fuel imbalance is the main source of divergence.

### `xs_lookup_kernel_optimization_6`
- Uses `xs_lookup_kernel_optimization_4` after both material sorting and per-material energy sorting.
- Reads:
  - sample arrays are contiguous by material and ordered by energy within material.
- Writes:
  - verification writes are contiguous within each sorted segment.
- Cross-section data access:
  - material metadata access is uniform.
  - energy-grid searches become much more coherent across warp lanes.
  - neighboring lanes are more likely to access nearby or identical energy-grid and nuclide-grid locations.
  - cache reuse improves substantially.
- Coalescing:
  - sample and verification accesses are coalesced.
  - grid accesses are still indirect, but spatial and temporal locality are much better than in the baseline.
- Energy profile:
  - Best opportunity for lowering memory-system energy in the lookup kernel.
  - Sorting overhead is the main tradeoff.

## 4. Shared-memory usage

### Current shared-memory usage
- No CUDA shared memory is declared or used.
- No static shared memory.
- No dynamic shared memory.
- No shared-memory tiling.
- No shared-memory reductions.

### Potential shared-memory or constant-memory opportunities
- Small read-only tables are good candidates for constant memory or other broadcast-friendly storage:
  - material distribution table used by material sampling,
  - number of nuclides per material,
  - material-to-nuclide mapping for small materials,
  - possibly concentration values for materials if access is uniform after sorting.
- The `dist[12]` table in material sampling is rebuilt per thread. Moving it to constant memory would reduce per-thread register/local-memory pressure and instruction count.
- `num_nucs`, `mats`, and `concs` are small compared with the cross-section grid. When warps are grouped by material, many lanes read the same locations, so constant memory could be energy-efficient.
- Shared-memory caching of `nuclide_grid` is less straightforward because baseline access is random. It becomes more plausible only after material and energy sorting, where a block may access nearby energy ranges.
- Shared-memory tiling of unionized/index-grid regions could be useful if energy-binned work is used, but the current code does not expose a block-level tile structure.

## 5. Warp divergence

### Divergence sources in explicit kernels

#### `sampling_kernel`
- Boundary check: threads with IDs beyond `in.lookups` return.
- Material sampling has data-dependent control flow inside `pick_mat`.
- `fast_forward_LCG` has a loop with data-dependent iteration behavior based on the lookup index and a conditional on the low bit of the exponent.

#### `xs_lookup_kernel_baseline`
- Boundary check on lookup ID.
- Material ID varies randomly across lanes.
- Loop bound in `calculate_macro_xs` depends on `num_nucs[mat]`, so lanes with different materials execute different numbers of nuclide iterations.
- The max-channel selection loop has a data-dependent comparison.
- Grid-search branches are data-dependent.

#### `xs_lookup_kernel_optimization_1`
- Boundary check on lookup ID.
- Material ID still varies randomly across lanes.
- Same `calculate_macro_xs`, `calculate_micro_xs`, and max-selection divergence as baseline.

#### `xs_lookup_kernel_optimization_2`
- Boundary check on lookup ID.
- Material filter causes early return for nonmatching material.
- Within a launch, active lanes have uniform material, but many lanes may be inactive.
- Same grid-search and max-selection divergence among active lanes.

#### `xs_lookup_kernel_optimization_3`
- Boundary check on lookup ID.
- Fuel/non-fuel predicate creates divergent active/inactive lanes.
- Fuel launch is uniform among active lanes.
- Non-fuel launch still has multiple material types and therefore variable loop bounds.
- Same grid-search and max-selection divergence among active lanes.

#### `xs_lookup_kernel_optimization_4`
- Boundary check on per-material lookup count.
- Material mismatch check remains, although after sorting it should normally be false for valid segments.
- Material loop bound is uniform within each material kernel.
- Grid-search divergence remains unless energies are also sorted.
- Max-selection comparison remains data-dependent.

#### `xs_lookup_kernel_optimization_5`
- Boundary check on segment length.
- Fuel segment has uniform material.
- Non-fuel segment still has mixed materials and variable material loop bounds.
- Grid-search and max-selection divergence remain.

### Divergence sources in device functions

#### `calculate_macro_xs`
- Branch on `grid_type`.
- Loop over `num_nucs[mat]`; this is a major divergence source when materials differ within a warp.
- Inner accumulation loop over five channels is fixed and not a major divergence source.

#### `calculate_micro_xs`
- Branch on `grid_type`.
- In nuclide mode:
  - binary search branch decisions depend on energy.
  - edge-case branch for the last grid point.
- In unionized mode:
  - branch for whether the indexed value is the last grid point.
- In hash mode:
  - branch for last hash bin.
  - branches for energy below/above hash-bin bounds.
  - binary search over a bounded nuclide-grid range.
  - edge-case branch for last grid point.
- Interpolation itself is branch-free after the bounding points are selected.

#### `grid_search` and `grid_search_nuclide`
- The loop length is mostly uniform for a fixed range, but the branch direction is data-dependent on energy.
- Different lanes follow different binary-search paths, causing warp divergence and scattered memory access.

#### `pick_mat`
- Data-dependent return inside the material-selection loop.
- Different lanes may exit at different iterations.
- Contains an unusual cumulative-probability loop, flagged below as intentional.

#### `fast_forward_LCG`
- Loop depends on `n`.
- Conditional on `n & 1` is lane-dependent.
- For consecutive lookup IDs, lanes may follow different paths through exponentiation-by-squaring.

### Candidate conversions to float
If physics tolerance and verification requirements permit, the following are candidates for single precision:
- energy values,
- cross-section values,
- concentrations,
- sampled particle energies,
- interpolation factor,
- temporary microscopic and macroscopic cross-section vectors,
- material probability distribution values.

### Energy benefits of float
- Halves memory footprint for cross-section and energy arrays.
- Reduces memory bandwidth demand.
- Improves cache residency.
- Reduces register footprint for some temporaries.
- Reduces FP64 instruction energy.

### Caution
- Replacing double with float will likely change the verification checksum.
- The random-number generator uses 64-bit integer state and converts to double. Changing the generated random value precision can change material/energy samples.
- Any precision change should be treated as an algorithmic change unless the benchmark validation criteria explicitly allow it.

### Mixed-precision opportunity
- A practical compromise would be:
  - retain RNG integer state exactly,
  - store energies and cross sections as float,
  - perform interpolation in float or mixed float/double,
  - accumulate macro cross sections in float or double depending on required accuracy.
- Accumulating in float may be acceptable for energy efficiency, but accumulating in double may preserve more numerical stability while still reducing grid-memory traffic if the grid is stored as float.

## 7. Synchronization overhead

### Device-side synchronization
- Number of explicit `__syncthreads()` calls: 0.
- There is no block-level synchronization inside any custom kernel.
- There are no shared-memory synchronization barriers.

### Host/device synchronization
Although there are no `__syncthreads()` calls, the host code uses frequent device-wide synchronization:
- After moving data to the GPU.
- After each custom kernel or group of kernels in the run functions.
- After Thrust reductions.
- After some Thrust-dependent phases indirectly through ordered default-stream execution.

### Energy implication
- Some `cudaDeviceSynchronize()` calls are useful for timing and error isolation, but they serialize execution and prevent overlap.
- Since kernels are launched in the default stream, explicit synchronization between dependent kernels is often unnecessary for correctness.
- Removing nonessential synchronizations or replacing them with CUDA events for timing can reduce idle GPU time and host/device coordination overhead.

## 8. Unusual loop bounds or comparison operators — INTENTIONAL, preserve verbatim

The following constructs appear unusual or easy to “fix” accidentally. They should be treated as INTENTIONAL and MUST be preserved verbatim unless the benchmark’s numerical behavior and checksum are intentionally changed.

### Material sampling cumulative loop
- INTENTIONAL — MUST be preserved verbatim:
  - `for( int j = i; j > 0; j-- )`
- This loop excludes `dist[0]` from the cumulative sum.
- Combined with the final fallback return of material 0, this produces a non-obvious material distribution.
- Do not change the bound to include zero unless intentionally changing the benchmark behavior.

### Material sampling comparison
- INTENTIONAL — MUST be preserved verbatim:
  - `if( roll < running )`
- Changing this to `<=` or changing the accumulation order can alter material sampling and verification.

### Fuel/non-fuel predicate in Optimization 3
- INTENTIONAL — MUST be preserved verbatim:
  - `((is_fuel == 1) && (mat == 0)) || ((is_fuel == 0) && (mat != 0 ))`
- The host launches Optimization 3 with both values of `is_fuel`.
- The exact mapping of launch argument to fuel/non-fuel work must be preserved.

### Hash-grid lower-bound edge handling
- INTENTIONAL — MUST be preserved verbatim:
  - `if( p_energy <= e_low )`
  - `else if( p_energy >= e_high )`
- These comparisons determine edge handling for hash-grid searches.
- Changing them to strict comparisons or changing the selected fallback indices can alter interpolation behavior.

### Last-grid-point edge handling
- INTENTIONAL — MUST be preserved verbatim:
  - checks comparing an index to `n_gridpoints - 1`
  - fallback to the previous grid point when the selected index is the last point

## 9. Main energy-efficiency recommendations

### Highest-impact recommendations
1. Prefer grouped lookup execution.
   - Material grouping reduces divergent loop lengths.
   - Energy sorting or binning improves cache reuse.
   - Optimization 6 is the strongest locality-oriented variant, while Optimization 5 is a lower-overhead compromise.

2. Replace 32-thread blocks with larger blocks where possible.
   - 32-thread blocks cap theoretical A100 occupancy at about 50%.
   - 128- or 256-thread blocks would improve latency hiding and reduce block scheduling overhead.

3. Avoid repeated full-array scans.
   - Optimization 2 scans all lookups 12 times.
   - Optimization 3 scans all lookups twice.
   - Compaction, partitioning, or prefix-sum based work queues are more energy-efficient.

4. Evaluate single precision or mixed precision.
   - Cross-section grids dominate memory traffic.
   - Storing grid data as float could significantly reduce memory-system energy.
   - This must be validated against benchmark accuracy and checksum requirements.

5. Use constant or read-only storage for small tables.
   - Material distributions, nuclide counts, and material composition data are small and heavily reused.
   - Broadcast-friendly memory is especially valuable after material sorting.

6. Reduce nonessential synchronization.
   - There are no `__syncthreads()` barriers, but there are several host-level device synchronizations.
   - Removing unnecessary `cudaDeviceSynchronize()` calls can reduce idle time and energy.

7. Consider energy-aware sorting tradeoffs.
   - Full material and energy sorting improves lookup efficiency but costs extra global-memory traffic.
   - For short runs, sorting may not pay off.
   - For large runs, sorting/bucketing is likely beneficial.

8. Improve data layout only with care.
   - The current AoS `NuclideGridPoint` layout is reasonable because both bounding grid points and all five cross-section channels are read together.
   - However, if only subsets of channels are needed in future variants, a structure-of-arrays layout could reduce memory traffic.
   - Alignment and vectorized loads may also help.

		}
		// hash bins (-h)
		else if( strcmp(arg, "-h") == 0 )
		{
			if( ++i < argc )
				input.hash_bins = atoi(argv[i]);
			else
				print_CLI_error();
		}
		// particles (-p)
		else if( strcmp(arg, "-p") == 0 )
		{
			if( ++i < argc )
			{
				input.particles = atoi(argv[i]);
				default_particles = 0;
			}
			else
				print_CLI_error();
		}
		// HM (-s)
		else if( strcmp(arg, "-s") == 0 )
		{	
			if( ++i < argc )
				input.HM = argv[i];
			else
				print_CLI_error();
		}
		// grid type (-G)
		else if( strcmp(arg, "-G") == 0 )
		{
			char * grid_type;
			if( ++i < argc )
				grid_type = argv[i];
			else
				print_CLI_error();

			if( strcmp(grid_type, "unionized") == 0 )
				input.grid_type = UNIONIZED;
			else if( strcmp(grid_type, "nuclide") == 0 )
				input.grid_type = NUCLIDE;
			else if( strcmp(grid_type, "hash") == 0 )
				input.grid_type = HASH;
			else
				print_CLI_error();
		}
		// binary mode (-b)
		else if( strcmp(arg, "-b") == 0 )
		{
			char * binary_mode;
			if( ++i < argc )
				binary_mode = argv[i];
			else
				print_CLI_error();

			if( strcmp(binary_mode, "read") == 0 )
				input.binary_mode = READ;
			else if( strcmp(binary_mode, "write") == 0 )
				input.binary_mode = WRITE;
			else
				print_CLI_error();
		}
		// kernel optimization selection (-k)
		else if( strcmp(arg, "-k") == 0 )
		{
			if( ++i < argc )
			{
				input.kernel_id = atoi(argv[i]);
			}
			else
				print_CLI_error();
		}
		else
			print_CLI_error();
	}

	// Validate Input
	
	// Validate nthreads
	if( input.nthreads < 1 )
		print_CLI_error();
	
	// Validate n_isotopes
	if( input.n_isotopes < 1 )
		print_CLI_error();
	
	// Validate n_gridpoints
	if( input.n_gridpoints < 1 )
		print_CLI_error();

	// Validate lookups
	if( input.lookups < 1 )
		print_CLI_error();

	// Validate Hash Bins 
	if( input.hash_bins < 1 )
		print_CLI_error();
	
	// Validate HM size
	if( strcasecmp(input.HM, "small") != 0 &&
		strcasecmp(input.HM, "large") != 0 &&
		strcasecmp(input.HM, "XL") != 0 &&
		strcasecmp(input.HM, "XXL") != 0 )
		print_CLI_error();
	
	// Set HM size specific parameters
	// (defaults to large)
	if( strcasecmp(input.HM, "small") == 0 )
		input.n_isotopes = 68;
	else if( strcasecmp(input.HM, "XL") == 0 && user_g == 0 )
		input.n_gridpoints = 238847; // sized to make 120 GB XS data
	else if( strcasecmp(input.HM, "XXL") == 0 && user_g == 0 )
		input.n_gridpoints = 238847 * 2.1; // 252 GB XS data

	// Return input struct
	return input;
}

	FILE * fp = fopen(fname, "w");

	fclose(fp);
}

	SD.index_grid = (int *) malloc( SD.length_index_grid * sizeof(int));
	SD.unionized_energy_array = (double *) malloc( SD.length_unionized_energy_array * sizeof(double));

	// Read heap arrays into SimulationData Object
	fread(SD.num_nucs,       sizeof(int), SD.length_num_nucs, fp);
	fread(SD.concs,          sizeof(double), SD.length_concs, fp);
	fread(SD.mats,           sizeof(int), SD.length_mats, fp);
	fread(SD.nuclide_grid,   sizeof(NuclideGridPoint), SD.length_nuclide_grid, fp); 
	fread(SD.index_grid, sizeof(int), SD.length_index_grid, fp);
	fread(SD.unionized_energy_array, sizeof(double), SD.length_unionized_energy_array, fp);

	fclose(fp);

	return SD;
}

// Moves all required data structures to the GPU's memory space
SimulationData move_simulation_data_to_device( Inputs in, int mype, SimulationData SD )
{
	if(mype == 0) printf("Allocating and moving simulation data to GPU memory space...\n");

	////////////////////////////////////////////////////////////////////////////////
	// SUMMARY: Simulation Data Structure Manifest for "SD" Object
	// Here we list all heap arrays (and lengths) in SD that would need to be
	// offloaded manually if using an accelerator with a seperate memory space
	////////////////////////////////////////////////////////////////////////////////
	// int * num_nucs;                     // Length = length_num_nucs;
	// double * concs;                     // Length = length_concs
	// int * mats;                         // Length = length_mats
	// double * unionized_energy_array;    // Length = length_unionized_energy_array
	// int * index_grid;                   // Length = length_index_grid
	// NuclideGridPoint * nuclide_grid;    // Length = length_nuclide_grid
	// 
	// Note: "unionized_energy_array" and "index_grid" can be of zero length
	//        depending on lookup method.
	//
	// Note: "Lengths" are given as the number of objects in the array, not the
	//       number of bytes.
	////////////////////////////////////////////////////////////////////////////////
	size_t sz;
	size_t total_sz = 0;

	// Shallow copy of CPU simulation data to GPU simulation data
	SimulationData GSD = SD;

	// Move data to GPU memory space
	sz = GSD.length_num_nucs * sizeof(int);
	gpuErrchk( cudaMalloc((void **) &GSD.num_nucs, sz) );
	gpuErrchk( cudaMemcpy(GSD.num_nucs, SD.num_nucs, sz, cudaMemcpyHostToDevice) );
	total_sz += sz;

	sz = GSD.length_concs * sizeof(double);
	gpuErrchk( cudaMalloc((void **) &GSD.concs, sz) );
	gpuErrchk( cudaMemcpy(GSD.concs, SD.concs, sz, cudaMemcpyHostToDevice) );
	total_sz += sz;

	sz = GSD.length_mats * sizeof(int);
	gpuErrchk( cudaMalloc((void **) &GSD.mats, sz) );
	gpuErrchk( cudaMemcpy(GSD.mats, SD.mats, sz, cudaMemcpyHostToDevice) );
	total_sz += sz;
	
	sz = GSD.length_unionized_energy_array * sizeof(double);
	gpuErrchk( cudaMalloc((void **) &GSD.unionized_energy_array, sz) );
	gpuErrchk( cudaMemcpy(GSD.unionized_energy_array, SD.unionized_energy_array, sz, cudaMemcpyHostToDevice) );
	total_sz += sz;

	sz = GSD.length_index_grid * sizeof(int);
	gpuErrchk( cudaMalloc((void **) &GSD.index_grid, sz) );
	gpuErrchk( cudaMemcpy(GSD.index_grid, SD.index_grid, sz, cudaMemcpyHostToDevice) );
	total_sz += sz;

	sz = GSD.length_nuclide_grid * sizeof(NuclideGridPoint);
	gpuErrchk( cudaMalloc((void **) &GSD.nuclide_grid, sz) );
	gpuErrchk( cudaMemcpy(GSD.nuclide_grid, SD.nuclide_grid, sz, cudaMemcpyHostToDevice) );
	total_sz += sz;
	
	// Allocate verification array on device. This structure is not needed on CPU, so we don't
	// have to copy anything over.
	sz = in.lookups * sizeof(unsigned long);
	gpuErrchk( cudaMalloc((void **) &GSD.verification, sz) );
	total_sz += sz;
	GSD.length_verification = in.lookups;
	
	// Synchronize
	gpuErrchk( cudaPeekAtLastError() );
	gpuErrchk( cudaDeviceSynchronize() );
	
	if(mype == 0 ) printf("GPU Intialization complete. Allocated %.0lf MB of data on GPU.\n", total_sz/1024.0/1024.0 );

	return GSD;

}

// Release device memory
void release_device_memory(SimulationData GSD) {
	cudaFree(GSD.num_nucs);
	cudaFree(GSD.concs);
	cudaFree(GSD.mats);
	cudaFree(GSD.unionized_energy_array);
	cudaFree(GSD.nuclide_grid);
	cudaFree(GSD.verification);
}

SimulationData grid_init_do_not_profile( Inputs in, int mype )
{
	// Structure to hold all allocated simuluation data arrays
	SimulationData SD;

	// Keep track of how much data we're allocating
	size_t nbytes = 0;
	
	// Set the initial seed value
	uint64_t seed = 42;	

	////////////////////////////////////////////////////////////////////
	// Initialize Nuclide Grids
	////////////////////////////////////////////////////////////////////
	
	if(mype == 0) printf("Intializing nuclide grids...\n");

	// First, we need to initialize our nuclide grid. This comes in the form
	// of a flattened 2D array that hold all the information we need to define
	// the cross sections for all isotopes in the simulation. 
	// The grid is composed of "NuclideGridPoint" structures, which hold the
	// energy level of the grid point and all associated XS data at that level.
	// An array of structures (AOS) is used instead of
	// a structure of arrays, as the grid points themselves are accessed in 
	// a random order, but all cross section interaction channels and the
	// energy level are read whenever the gridpoint is accessed, meaning the
	// AOS is more cache efficient.
	
	// Initialize Nuclide Grid
	SD.length_nuclide_grid = in.n_isotopes * in.n_gridpoints;
	SD.nuclide_grid     = (NuclideGridPoint *) malloc( SD.length_nuclide_grid * sizeof(NuclideGridPoint));
	assert(SD.nuclide_grid != NULL);
	nbytes += SD.length_nuclide_grid * sizeof(NuclideGridPoint);
	for( int i = 0; i < SD.length_nuclide_grid; i++ )
	{
		SD.nuclide_grid[i].energy        = LCG_random_double(&seed);
		SD.nuclide_grid[i].total_xs      = LCG_random_double(&seed);
		SD.nuclide_grid[i].elastic_xs    = LCG_random_double(&seed);
		SD.nuclide_grid[i].absorbtion_xs = LCG_random_double(&seed);
		SD.nuclide_grid[i].fission_xs    = LCG_random_double(&seed);
		SD.nuclide_grid[i].nu_fission_xs = LCG_random_double(&seed);
	}

	// Sort so that each nuclide has data stored in ascending energy order.
	for( int i = 0; i < in.n_isotopes; i++ )
		qsort( &SD.nuclide_grid[i*in.n_gridpoints], in.n_gridpoints, sizeof(NuclideGridPoint), NGP_compare);
	
	// error debug check
	/*
	for( int i = 0; i < in.n_isotopes; i++ )
	{
		printf("NUCLIDE %d ==============================\n", i);
		for( int j = 0; j < in.n_gridpoints; j++ )
			printf("E%d = %lf\n", j, SD.nuclide_grid[i * in.n_gridpoints + j].energy);
	}
	*/
	

	////////////////////////////////////////////////////////////////////
	// Initialize Acceleration Structure
	////////////////////////////////////////////////////////////////////
	
	if( in.grid_type == NUCLIDE )
	{
		SD.length_unionized_energy_array = 0;
		SD.length_index_grid = 0;
	}
	
	if( in.grid_type == UNIONIZED )
	{
		if(mype == 0) printf("Intializing unionized grid...\n");

		// Allocate space to hold the union of all nuclide energy data
		SD.length_unionized_energy_array = in.n_isotopes * in.n_gridpoints;
		SD.unionized_energy_array = (double *) malloc( SD.length_unionized_energy_array * sizeof(double));
		assert(SD.unionized_energy_array != NULL );
		nbytes += SD.length_unionized_energy_array * sizeof(double);

		// Copy energy data over from the nuclide energy grid
		for( int i = 0; i < SD.length_unionized_energy_array; i++ )
			SD.unionized_energy_array[i] = SD.nuclide_grid[i].energy;

		// Sort unionized energy array
		qsort( SD.unionized_energy_array, SD.length_unionized_energy_array, sizeof(double), double_compare);

		// Allocate space to hold the acceleration grid indices
		SD.length_index_grid = SD.length_unionized_energy_array * in.n_isotopes;
		SD.index_grid = (int *) malloc( SD.length_index_grid * sizeof(int));
		assert(SD.index_grid != NULL);
		nbytes += SD.length_index_grid * sizeof(int);

		// Generates the double indexing grid
		int * idx_low = (int *) calloc( in.n_isotopes, sizeof(int));
		assert(idx_low != NULL );
		double * energy_high = (double *) malloc( in.n_isotopes * sizeof(double));
		assert(energy_high != NULL );

		for( int i = 0; i < in.n_isotopes; i++ )
			energy_high[i] = SD.nuclide_grid[i * in.n_gridpoints + 1].energy;

		for( long e = 0; e < SD.length_unionized_energy_array; e++ )
		{
			double unionized_energy = SD.unionized_energy_array[e];
			for( long i = 0; i < in.n_isotopes; i++ )
			{
				if( unionized_energy < energy_high[i]  )
					SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
				else if( idx_low[i] == in.n_gridpoints - 2 )
					SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
				else
				{
					idx_low[i]++;
					SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
					energy_high[i] = SD.nuclide_grid[i * in.n_gridpoints + idx_low[i] + 1].energy;	
				}
			}
		}

		free(idx_low);
		free(energy_high);
	}

	if( in.grid_type == HASH )
	{
		if(mype == 0) printf("Intializing hash grid...\n");
		SD.length_unionized_energy_array = 0;
		SD.length_index_grid  = in.hash_bins * in.n_isotopes;
		SD.index_grid = (int *) malloc( SD.length_index_grid * sizeof(int)); 
		assert(SD.index_grid != NULL);
		nbytes += SD.length_index_grid * sizeof(int);

		double du = 1.0 / in.hash_bins;

		// For each energy level in the hash table
		for( long e = 0; e < in.hash_bins; e++ )
		{
			double energy = e * du;

			// We need to determine the bounding energy levels for all isotopes
			for( long i = 0; i < in.n_isotopes; i++ )
			{
				SD.index_grid[e * in.n_isotopes + i] = grid_search_nuclide( in.n_gridpoints, energy, SD.nuclide_grid + i * in.n_gridpoints, 0, in.n_gridpoints-1);
			}
		}
	}

	////////////////////////////////////////////////////////////////////
	// Initialize Materials and Concentrations
	////////////////////////////////////////////////////////////////////
	if(mype == 0) printf("Intializing material data...\n");
	
	// Set the number of nuclides in each material
	SD.num_nucs  = load_num_nucs(in.n_isotopes);
	SD.length_num_nucs = 12; // There are always 12 materials in XSBench

	// Intialize the flattened 2D grid of material data. The grid holds
	// a list of nuclide indices for each of the 12 material types. The
	// grid is allocated as a full square grid, even though not all
	// materials have the same number of nuclides.
	SD.mats = load_mats(SD.num_nucs, in.n_isotopes, &SD.max_num_nucs);
	SD.length_mats = SD.length_num_nucs * SD.max_num_nucs;

	// Intialize the flattened 2D grid of nuclide concentration data. The grid holds
	// a list of nuclide concentrations for each of the 12 material types. The
	// grid is allocated as a full square grid, even though not all
	// materials have the same number of nuclides.
	SD.concs = load_concs(SD.num_nucs, SD.max_num_nucs);
	SD.length_concs = SD.length_mats;

	if(mype == 0) printf("Intialization complete. Allocated %.0lf MB of data on CPU.\n", nbytes/1024.0/1024.0 );

	return SD;
}

// Material data is hard coded into the functions in this file.
// Note that there are 12 materials present in H-M (large or small)

// num_nucs represents the number of nuclides that each material contains
int * load_num_nucs(long n_isotopes)
{
	int * num_nucs = (int*)malloc(12*sizeof(int));
	
	// Material 0 is a special case (fuel). The H-M small reactor uses
	// 34 nuclides, while H-M larges uses 300.
	if( n_isotopes == 68 )
		num_nucs[0]  = 34; // HM Small is 34, H-M Large is 321
	else
		num_nucs[0]  = 321; // HM Small is 34, H-M Large is 321

	num_nucs[1]  = 5;
	num_nucs[2]  = 4;
	num_nucs[3]  = 4;
	num_nucs[4]  = 27;
	num_nucs[5]  = 21;
	num_nucs[6]  = 21;
	num_nucs[7]  = 21;
	num_nucs[8]  = 21;
	num_nucs[9]  = 21;
	num_nucs[10] = 9;
	num_nucs[11] = 9;

	return num_nucs;
}

// Assigns an array of nuclide ID's to each material
int * load_mats( int * num_nucs, long n_isotopes, int * max_num_nucs )
{
	*max_num_nucs = 0;
	int num_mats = 12;
	for( int m = 0; m < num_mats; m++ )
	{
		if( num_nucs[m] > *max_num_nucs )
			*max_num_nucs = num_nucs[m];
	}
	int * mats = (int *) malloc( num_mats * (*max_num_nucs) * sizeof(int) );

	// Small H-M has 34 fuel nuclides
	int mats0_Sml[] =  { 58, 59, 60, 61, 40, 42, 43, 44, 45, 46, 1, 2, 3, 7,
	                 8, 9, 10, 29, 57, 47, 48, 0, 62, 15, 33, 34, 52, 53, 
	                 54, 55, 56, 18, 23, 41 }; //fuel
	// Large H-M has 300 fuel nuclides
	int mats0_Lrg[321] =  { 58, 59, 60, 61, 40, 42, 43, 44, 45, 46, 1, 2, 3, 7,
	                 8, 9, 10, 29, 57, 47, 48, 0, 62, 15, 33, 34, 52, 53,
	                 54, 55, 56, 18, 23, 41 }; //fuel
	for( int i = 0; i < 321-34; i++ )
		mats0_Lrg[34+i] = 68 + i; // H-M large adds nuclides to fuel only
	
	// These are the non-fuel materials	
	int mats1[] =  { 63, 64, 65, 66, 67 }; // cladding
	int mats2[] =  { 24, 41, 4, 5 }; // cold borated water
	int mats3[] =  { 24, 41, 4, 5 }; // hot borated water
	int mats4[] =  { 19, 20, 21, 22, 35, 36, 37, 38, 39, 25, 27, 28, 29,
	                 30, 31, 32, 26, 49, 50, 51, 11, 12, 13, 14, 6, 16,
	                 17 }; // RPV
	int mats5[] =  { 24, 41, 4, 5, 19, 20, 21, 22, 35, 36, 37, 38, 39, 25,
	                 49, 50, 51, 11, 12, 13, 14 }; // lower radial reflector
	int mats6[] =  { 24, 41, 4, 5, 19, 20, 21, 22, 35, 36, 37, 38, 39, 25,
	                 49, 50, 51, 11, 12, 13, 14 }; // top reflector / plate
	int mats7[] =  { 24, 41, 4, 5, 19, 20, 21, 22, 35, 36, 37, 38, 39, 25,
	                 49, 50, 51, 11, 12, 13, 14 }; // bottom plate
	int mats8[] =  { 24, 41, 4, 5, 19, 20, 21, 22, 35, 36, 37, 38, 39, 25,
	                 49, 50, 51, 11, 12, 13, 14 }; // bottom nozzle
	int mats9[] =  { 24, 41, 4, 5, 19, 20, 21, 22, 35, 36, 37, 38, 39, 25,
	                 49, 50, 51, 11, 12, 13, 14 }; // top nozzle
	int mats10[] = { 24, 41, 4, 5, 63, 64, 65, 66, 67 }; // top of FA's
	int mats11[] = { 24, 41, 4, 5, 63, 64, 65, 66, 67 }; // bottom FA's
	
	// H-M large v small dependency
	if( n_isotopes == 68 )
		memcpy( mats,  mats0_Sml,  num_nucs[0]  * sizeof(int) );	
	else
		memcpy( mats,  mats0_Lrg,  num_nucs[0]  * sizeof(int) );
	
	// Copy other materials
	memcpy( mats + *max_num_nucs * 1,  mats1,  num_nucs[1]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 2,  mats2,  num_nucs[2]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 3,  mats3,  num_nucs[3]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 4,  mats4,  num_nucs[4]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 5,  mats5,  num_nucs[5]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 6,  mats6,  num_nucs[6]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 7,  mats7,  num_nucs[7]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 8,  mats8,  num_nucs[8]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 9,  mats9,  num_nucs[9]  * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 10, mats10, num_nucs[10] * sizeof(int) );	
	memcpy( mats + *max_num_nucs * 11, mats11, num_nucs[11] * sizeof(int) );	

	return mats;
}

// Randomizes the concentrations of all nuclides in a variety of materials
double * load_concs( int * num_nucs, int max_num_nucs )
{
	uint64_t seed = STARTING_SEED * STARTING_SEED;
	double * concs = (double *) malloc( 12 * max_num_nucs * sizeof( double ) );
	
	for( int i = 0; i < 12; i++ )
		for( int j = 0; j < num_nucs[i]; j++ )
			concs[i * max_num_nucs + j] = LCG_random_double(&seed);

	// test
	/*
	for( int i = 0; i < 12; i++ )
		for( int j = 0; j < num_nucs[i]; j++ )
			printf("concs[%d][%d] = %lf\n", i, j, concs[i][j] );
	*/

	return concs;
}

unsigned long long run_event_based_simulation_baseline(Inputs in, SimulationData GSD, int mype)
{
	////////////////////////////////////////////////////////////////////////////////
	// Configure & Launch Simulation Kernel
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Running baseline event-based simulation...\n");

	int nthreads = 256;
	int nblocks = ceil( (double) in.lookups / (double) nthreads);

	xs_lookup_kernel_baseline<<<nblocks, nthreads>>>( in, GSD );
	gpuErrchk( cudaPeekAtLastError() );
	gpuErrchk( cudaDeviceSynchronize() );
	
	////////////////////////////////////////////////////////////////////////////////
	// Reduce Verification Results
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Reducing verification results...\n");

	unsigned long verification_scalar = thrust::reduce(thrust::device, GSD.verification, GSD.verification + in.lookups, 0);
	gpuErrchk( cudaPeekAtLastError() );
	gpuErrchk( cudaDeviceSynchronize() );

	return verification_scalar;
}

// In this kernel, we perform a single lookup with each thread. Threads within a warp
// do not really have any relation to each other, and divergence due to high nuclide count fuel
// material lookups are costly. This kernel constitutes baseline performance.
__global__ void xs_lookup_kernel_baseline(Inputs in, SimulationData GSD )
{
	// The lookup ID. Used to set the seed, and to store the verification value
	const int i = blockIdx.x *blockDim.x + threadIdx.x;

	if( i >= in.lookups )
		return;

	// Set the initial seed value
	uint64_t seed = STARTING_SEED;	

	// Forward seed to lookup index (we need 2 samples per lookup)
	seed = fast_forward_LCG(seed, 2*i);

	// Randomly pick an energy and material for the particle
	double p_energy = LCG_random_double(&seed);
	int mat         = pick_mat(&seed); 
		
	double macro_xs_vector[5] = {0};
		
	// Perform macroscopic Cross Section Lookup
	calculate_macro_xs(
			p_energy,        // Sampled neutron energy (in lethargy)
			mat,             // Sampled material type index neutron is in
			in.n_isotopes,   // Total number of isotopes in simulation
			in.n_gridpoints, // Number of gridpoints per isotope in simulation
			GSD.num_nucs,     // 1-D array with number of nuclides per material
			GSD.concs,        // Flattened 2-D array with concentration of each nuclide in each material
			GSD.unionized_energy_array, // 1-D Unionized energy array
			GSD.index_grid,   // Flattened 2-D grid holding indices into nuclide grid for each unionized energy level
			GSD.nuclide_grid, // Flattened 2-D grid holding energy levels and XS_data for all nuclides in simulation
			GSD.mats,         // Flattened 2-D array with nuclide indices defining composition of each type of material
			macro_xs_vector, // 1-D array with result of the macroscopic cross section (5 different reaction channels)
			in.grid_type,    // Lookup type (nuclide, hash, or unionized)
			in.hash_bins,    // Number of hash bins used (if using hash lookup type)
			GSD.max_num_nucs  // Maximum number of nuclides present in any material
			);

	// For verification, and to prevent the compiler from optimizing
	// all work out, we interrogate the returned macro_xs_vector array
	// to find its maximum value index, then increment the verification
	// value by that index. In this implementation, we have each thread
	// write to its thread_id index in an array, which we will reduce
	// with a thrust reduction kernel after the main simulation kernel.
	double max = -1.0;
	int max_idx = 0;
	for(int j = 0; j < 5; j++ )
	{
		if( macro_xs_vector[j] > max )
		{
			max = macro_xs_vector[j];
			max_idx = j;
		}
	}
	GSD.verification[i] = max_idx+1;
}

// Calculates the microscopic cross section for a given nuclide & energy
__device__ void calculate_micro_xs(   double p_energy, int nuc, long n_isotopes,
                           long n_gridpoints,
                           double * __restrict__ egrid, int * __restrict__ index_data,
                           NuclideGridPoint * __restrict__ nuclide_grids,
                           long idx, double * __restrict__ xs_vector, int grid_type, int hash_bins ){
	// Variables
	double f;
	NuclideGridPoint * low, * high;

	// If using only the nuclide grid, we must perform a binary search
	// to find the energy location in this particular nuclide's grid.
	if( grid_type == NUCLIDE )
	{
		// Perform binary search on the Nuclide Grid to find the index
		idx = grid_search_nuclide( n_gridpoints, p_energy, &nuclide_grids[nuc*n_gridpoints], 0, n_gridpoints-1);

		// pull ptr from nuclide grid and check to ensure that
		// we're not reading off the end of the nuclide's grid
		if( idx == n_gridpoints - 1 )
			low = &nuclide_grids[nuc*n_gridpoints + idx - 1];
		else
			low = &nuclide_grids[nuc*n_gridpoints + idx];
	}
	else if( grid_type == UNIONIZED) // Unionized Energy Grid - we already know the index, no binary search needed.
	{
		// pull ptr from energy grid and check to ensure that
		// we're not reading off the end of the nuclide's grid
		if( index_data[idx * n_isotopes + nuc] == n_gridpoints - 1 )
			low = &nuclide_grids[nuc*n_gridpoints + index_data[idx * n_isotopes + nuc] - 1];
		else
			low = &nuclide_grids[nuc*n_gridpoints + index_data[idx * n_isotopes + nuc]];
	}
	else // Hash grid
	{
		// load lower bounding index
		int u_low = index_data[idx * n_isotopes + nuc];

		// Determine higher bounding index
		int u_high;
		if( idx == hash_bins - 1 )
			u_high = n_gridpoints - 1;
		else
			u_high = index_data[(idx+1)*n_isotopes + nuc] + 1;

		// Check edge cases to make sure energy is actually between these
		// Then, if things look good, search for gridpoint in the nuclide grid
		// within the lower and higher limits we've calculated.
		double e_low  = nuclide_grids[nuc*n_gridpoints + u_low].energy;
		double e_high = nuclide_grids[nuc*n_gridpoints + u_high].energy;
		int lower;
		if( p_energy <= e_low )
			lower = 0;
		else if( p_energy >= e_high )
			lower = n_gridpoints - 1;
		else
			lower = grid_search_nuclide( n_gridpoints, p_energy, &nuclide_grids[nuc*n_gridpoints], u_low, u_high);

		if( lower == n_gridpoints - 1 )
			low = &nuclide_grids[nuc*n_gridpoints + lower - 1];
		else
			low = &nuclide_grids[nuc*n_gridpoints + lower];
	}
	
	high = low + 1;
	
	// calculate the re-useable interpolation factor
	f = (high->energy - p_energy) / (high->energy - low->energy);

	// Total XS
	xs_vector[0] = high->total_xs - f * (high->total_xs - low->total_xs);
	
	// Elastic XS
	xs_vector[1] = high->elastic_xs - f * (high->elastic_xs - low->elastic_xs);
	
	// Absorbtion XS
	xs_vector[2] = high->absorbtion_xs - f * (high->absorbtion_xs - low->absorbtion_xs);
	
	// Fission XS
	xs_vector[3] = high->fission_xs - f * (high->fission_xs - low->fission_xs);
	
	// Nu Fission XS
	xs_vector[4] = high->nu_fission_xs - f * (high->nu_fission_xs - low->nu_fission_xs);
}

// Calculates macroscopic cross section based on a given material & energy 
__device__ void calculate_macro_xs( double p_energy, int mat, long n_isotopes,
                         long n_gridpoints, int * __restrict__ num_nucs,
                         double * __restrict__ concs,
                         double * __restrict__ egrid, int * __restrict__ index_data,
                         NuclideGridPoint * __restrict__ nuclide_grids,
                         int * __restrict__ mats,
                         double * __restrict__ macro_xs_vector, int grid_type, int hash_bins, int max_num_nucs ){
	int p_nuc; // the nuclide we are looking up
	long idx = -1;	
	double conc; // the concentration of the nuclide in the material

	// cleans out macro_xs_vector
	for( int k = 0; k < 5; k++ )
		macro_xs_vector[k] = 0;

	// If we are using the unionized energy grid (UEG), we only
	// need to perform 1 binary search per macroscopic lookup.
	// If we are using the nuclide grid search, it will have to be
	// done inside of the "calculate_micro_xs" function for each different
	// nuclide in the material.
	if( grid_type == UNIONIZED )
		idx = grid_search( n_isotopes * n_gridpoints, p_energy, egrid);	
	else if( grid_type == HASH )
	{
		double du = 1.0 / hash_bins;
		idx = p_energy / du;
	}
	
	// Once we find the pointer array on the UEG, we can pull the data
	// from the respective nuclide grids, as well as the nuclide
	// concentration data for the material
	// Each nuclide from the material needs to have its micro-XS array
	// looked up & interpolatied (via calculate_micro_xs). Then, the
	// micro XS is multiplied by the concentration of that nuclide
	// in the material, and added to the total macro XS array.
	// (Independent -- though if parallelizing, must use atomic operations
	//  or otherwise control access to the xs_vector and macro_xs_vector to
	//  avoid simulataneous writing to the same data structure)
	for( int j = 0; j < num_nucs[mat]; j++ )
	{
		double xs_vector[5];
		p_nuc = mats[mat*max_num_nucs + j];
		conc = concs[mat*max_num_nucs + j];
		calculate_micro_xs( p_energy, p_nuc, n_isotopes,
		                    n_gridpoints, egrid, index_data,
		                    nuclide_grids, idx, xs_vector, grid_type, hash_bins );
		for( int k = 0; k < 5; k++ )
			macro_xs_vector[k] += xs_vector[k] * conc;
	}
}


// binary search for energy on unionized energy grid
// returns lower index
__device__ long grid_search( long n, double quarry, double * __restrict__ A)
{
	long lowerLimit = 0;
	long upperLimit = n-1;
	long examinationPoint;
	long length = upperLimit - lowerLimit;

	while( length > 1 )
	{
		examinationPoint = lowerLimit + ( length / 2 );
		
		if( A[examinationPoint] > quarry )
			upperLimit = examinationPoint;
		else
			lowerLimit = examinationPoint;
		
		length = upperLimit - lowerLimit;
	}
	
	return lowerLimit;
}

// binary search for energy on nuclide energy grid
__host__ __device__ long grid_search_nuclide( long n, double quarry, NuclideGridPoint * A, long low, long high)
{
	long lowerLimit = low;
	long upperLimit = high;
	long examinationPoint;
	long length = upperLimit - lowerLimit;

	while( length > 1 )
	{
		examinationPoint = lowerLimit + ( length / 2 );
		
		if( A[examinationPoint].energy > quarry )
			upperLimit = examinationPoint;
		else
			lowerLimit = examinationPoint;
		
		length = upperLimit - lowerLimit;
	}
	
	return lowerLimit;
}

// picks a material based on a probabilistic distribution
__device__ int pick_mat( uint64_t * seed )
{
	// I have a nice spreadsheet supporting these numbers. They are
	// the fractions (by volume) of material in the core. Not a 
	// *perfect* approximation of where XS lookups are going to occur,
	// but this will do a good job of biasing the system nonetheless.

	// Also could be argued that doing fractions by weight would be 
	// a better approximation, but volume does a good enough job for now.

	double dist[12];
	dist[0]  = 0.140;	// fuel
	dist[1]  = 0.052;	// cladding
	dist[2]  = 0.275;	// cold, borated water
	dist[3]  = 0.134;	// hot, borated water
	dist[4]  = 0.154;	// RPV
	dist[5]  = 0.064;	// Lower, radial reflector
	dist[6]  = 0.066;	// Upper reflector / top plate
	dist[7]  = 0.055;	// bottom plate
	dist[8]  = 0.008;	// bottom nozzle
	dist[9]  = 0.015;	// top nozzle
	dist[10] = 0.025;	// top of fuel assemblies
	dist[11] = 0.013;	// bottom of fuel assemblies
	
	double roll = LCG_random_double(seed);

	// makes a pick based on the distro
	for( int i = 0; i < 12; i++ )
	{
		double running = 0;
		for( int j = i; j > 0; j-- )
			running += dist[j];
		if( roll < running )
			return i;
	}

	return 0;
}

__host__ __device__ double LCG_random_double(uint64_t * seed)
{
	// LCG parameters
	const uint64_t m = 9223372036854775808ULL; // 2^63
	const uint64_t a = 2806196910506780709ULL;
	const uint64_t c = 1ULL;
	*seed = (a * (*seed) + c) % m;
	return (double) (*seed) / (double) m;
}	

__device__ uint64_t fast_forward_LCG(uint64_t seed, uint64_t n)
{
	// LCG parameters
	const uint64_t m = 9223372036854775808ULL; // 2^63
	uint64_t a = 2806196910506780709ULL;
	uint64_t c = 1ULL;

	n = n % m;

	uint64_t a_new = 1;
	uint64_t c_new = 0;

	while(n > 0) 
	{
		if(n & 1)
		{
			a_new *= a;
			c_new = c_new * a + c;
		}
		c *= (a + 1);
		a *= a;

		n >>= 1;
	}

	return (a_new * seed + c_new) % m;
}

__global__ void sampling_kernel(Inputs in, SimulationData GSD )
{
	// The lookup ID.
	const int i = blockIdx.x *blockDim.x + threadIdx.x;

	if( i >= in.lookups )
		return;

	// Set the initial seed value
	uint64_t seed = STARTING_SEED;	

	// Forward seed to lookup index (we need 2 samples per lookup)
	seed = fast_forward_LCG(seed, 2*i);

	// Randomly pick an energy and material for the particle
	double p_energy = LCG_random_double(&seed);
	int mat         = pick_mat(&seed); 

	// Store sample data in state array
	GSD.p_energy_samples[i] = p_energy;
	GSD.mat_samples[i] = mat;
}

			macro_xs_vector, // 1-D array with result of the macroscopic cross section (5 different reaction channels)
			in.grid_type,    // Lookup type (nuclide, hash, or unionized)
			in.hash_bins,    // Number of hash bins used (if using hash lookup type)

////////////////////////////////////////////////////////////////////////////////////
// Optimization 2 -- Kernel Splitting + Material-Specific Lookup Kernels
////////////////////////////////////////////////////////////////////////////////////
// This one builds on the first optimization. It uses multiple kernels, one
// for each material type, to better balance the workload across threads within
// a warp. This works because each material will have a different number of 
// isotopes, with some having a ton, meaning that SIMD efficiency can be rather
// low by default. Better efficiency may be gained in further optimizations by
// sorting the lookups first.
////////////////////////////////////////////////////////////////////////////////////
unsigned long long run_event_based_simulation_optimization_2(Inputs in, SimulationData GSD, int mype)
{
	const char * optimization_name = "Optimization 2 - Material Lookup Kernels";
	
	if( mype == 0)	printf("Simulation Kernel:\"%s\"\n", optimization_name);
	
	////////////////////////////////////////////////////////////////////////////////
	// Allocate Additional Data Structures Needed by Optimized Kernel
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Allocating additional device data required by kernel...\n");
	size_t sz;
	size_t total_sz = 0;

	sz = in.lookups * sizeof(double);
	gpuErrchk( cudaMalloc((void **) &GSD.p_energy_samples, sz) );
	total_sz += sz;
	GSD.length_p_energy_samples = in.lookups;

	sz = in.lookups * sizeof(int);
	gpuErrchk( cudaMalloc((void **) &GSD.mat_samples, sz) );
	total_sz += sz;
	GSD.length_mat_samples = in.lookups;
	
	if( mype == 0)	printf("Allocated an additional %.0lf MB of data on GPU.\n", total_sz/1024.0/1024.0);

	////////////////////////////////////////////////////////////////////////////////
	// Configure & Launch Simulation Kernel
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Beginning optimized simulation...\n");

	int nthreads = 32;
	int nblocks = ceil( (double) in.lookups / 32.0);
	
	sampling_kernel<<<nblocks, nthreads>>>( in, GSD );

	gpuErrchk( cudaDeviceSynchronize() );

			macro_xs_vector, // 1-D array with result of the macroscopic cross section (5 different reaction channels)
			in.grid_type,    // Lookup type (nuclide, hash, or unionized)

////////////////////////////////////////////////////////////////////////////////////
// Optimization 3 -- Kernel Splitting + Fuel or Not-Fuel Lookups
////////////////////////////////////////////////////////////////////////////////////
// This optimization alters Optimization 2. Instead of executing a kernel call for
// ALL different material types, only two different calls are made. One for fuel,
// and one for all the other materials. As the fuel material has by far the most
// isotopes, it takes much longer than the rest.
////////////////////////////////////////////////////////////////////////////////////
unsigned long long run_event_based_simulation_optimization_3(Inputs in, SimulationData GSD, int mype)
{
	const char * optimization_name = "Optimization 3 - Fuel or Other Lookup Kernels";
	
	if( mype == 0)	printf("Simulation Kernel:\"%s\"\n", optimization_name);
	
	////////////////////////////////////////////////////////////////////////////////
	// Allocate Additional Data Structures Needed by Optimized Kernel
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Allocating additional device data required by kernel...\n");
	size_t sz;
	size_t total_sz = 0;

	sz = in.lookups * sizeof(double);
	gpuErrchk( cudaMalloc((void **) &GSD.p_energy_samples, sz) );
	total_sz += sz;
	GSD.length_p_energy_samples = in.lookups;

__global__ void xs_lookup_kernel_optimization_3(Inputs in, SimulationData GSD, int is_fuel )
{
	// The lookup ID. Used to set the seed, and to store the verification value
	const int i = blockIdx.x *blockDim.x + threadIdx.x;

	if( i >= in.lookups )
		return;
	
	int mat = GSD.mat_samples[i];

	// If this is the fuel kernel, AND this is a fuel lookup, then perform a lookup
	// OR if this is not the fuel kernel, AND this is not a fuel lookup, then perform the lookup
	if( ((is_fuel == 1) && (mat == 0)) || ((is_fuel == 0) && (mat != 0 ) ))
	{
		double macro_xs_vector[5] = {0};
			
		// Perform macroscopic Cross Section Lookup
		calculate_macro_xs(
				GSD.p_energy_samples[i],        // Sampled neutron energy (in lethargy)
				mat,             // Sampled material type index neutron is in
				in.n_isotopes,   // Total number of isotopes in simulation
				in.n_gridpoints, // Number of gridpoints per isotope in simulation
				GSD.num_nucs,     // 1-D array with number of nuclides per material
				GSD.concs,        // Flattened 2-D array with concentration of each nuclide in each material
				GSD.unionized_energy_array, // 1-D Unionized energy array
				GSD.index_grid,   // Flattened 2-D grid holding indices into nuclide grid for each unionized energy level
				GSD.nuclide_grid, // Flattened 2-D grid holding energy levels and XS_data for all nuclides in simulation
				GSD.mats,         // Flattened 2-D array with nuclide indices defining composition of each type of material
				macro_xs_vector, // 1-D array with result of the macroscopic cross section (5 different reaction channels)
				in.grid_type,    // Lookup type (nuclide, hash, or unionized)
				in.hash_bins,    // Number of hash bins used (if using hash lookup type)
				GSD.max_num_nucs  // Maximum number of nuclides present in any material
				);

		// For verification, and to prevent the compiler from optimizing
		// all work out, we interrogate the returned macro_xs_vector array
		// to find its maximum value index, then increment the verification
		// value by that index. In this implementation, we have each thread
		// write to its thread_id index in an array, which we will reduce
		// with a thrust reduction kernel after the main simulation kernel.
		double max = -1.0;
		int max_idx = 0;
		for(int j = 0; j < 5; j++ )
		{
			if( macro_xs_vector[j] > max )
			{
				max = macro_xs_vector[j];
				max_idx = j;
			}
		}
		GSD.verification[i] = max_idx+1;
	}
}

////////////////////////////////////////////////////////////////////////////////////
// Optimization 6 -- Kernel Splitting + All Material Lookups + Full Sort
//                   + Energy Sort
////////////////////////////////////////////////////////////////////////////////////
// This optimization builds on optimization 4, adding in a second sort by energy.
// It is extremely fast, as now most of the threads within a warp will be hitting
// the same indices in the lookup grids. This greatly reduces thread divergence and
// greatly improves cache efficiency and re-use.
//
// However, it is unlikely that this exact optimization would be possible in a real
// application like OpenMC. One major difference is that particle objects are quite
// large, often having 50+ variable fields, such that sorting them in memory becomes
// rather expensive. Instead, the best possible option would probably be to create
// intermediate indexing (per Hamilton et. al 2019), and run the kernels indirectly.
////////////////////////////////////////////////////////////////////////////////////
unsigned long long run_event_based_simulation_optimization_6(Inputs in, SimulationData GSD, int mype)
{
	const char * optimization_name = "Optimization 6 - Material & Energy Sorts + Material-specific Kernels";
	
	if( mype == 0)	printf("Simulation Kernel:\"%s\"\n", optimization_name);
	
	////////////////////////////////////////////////////////////////////////////////
	// Allocate Additional Data Structures Needed by Optimized Kernel
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Allocating additional device data required by kernel...\n");
	size_t sz;
	size_t total_sz = 0;

	sz = in.lookups * sizeof(double);
	gpuErrchk( cudaMalloc((void **) &GSD.p_energy_samples, sz) );
	total_sz += sz;
	GSD.length_p_energy_samples = in.lookups;

	sz = in.lookups * sizeof(int);
	gpuErrchk( cudaMalloc((void **) &GSD.mat_samples, sz) );
	total_sz += sz;
	GSD.length_mat_samples = in.lookups;
	
	if( mype == 0)	printf("Allocated an additional %.0lf MB of data on GPU.\n", total_sz/1024.0/1024.0);

	////////////////////////////////////////////////////////////////////////////////
	// Configure & Launch Simulation Kernel
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Beginning optimized simulation...\n");

	int nthreads = 32;
	int nblocks = ceil( (double) in.lookups / 32.0);
	
	sampling_kernel<<<nblocks, nthreads>>>( in, GSD );
	gpuErrchk( cudaPeekAtLastError() );
	gpuErrchk( cudaDeviceSynchronize() );

	// Count the number of fuel material lookups that need to be performed (fuel id = 0)
	int n_lookups_per_material[12];
	for( int m = 0; m < 12; m++ )
		n_lookups_per_material[m] = thrust::count(thrust::device, GSD.mat_samples, GSD.mat_samples + in.lookups, m);

	// Sort by material first
	thrust::sort_by_key(thrust::device, GSD.mat_samples, GSD.mat_samples + in.lookups, GSD.p_energy_samples);

	// Now, sort each material by energy
	int offset = 0;
	for( int m = 0; m < 12; m++ )
	{
		thrust::sort_by_key(thrust::device, GSD.p_energy_samples + offset, GSD.p_energy_samples + offset + n_lookups_per_material[m], GSD.mat_samples + offset);
		offset += n_lookups_per_material[m];
	}
	
	// Launch all material kernels individually
	offset = 0;
	for( int m = 0; m < 12; m++ )
	{
		nthreads = 32;
		nblocks = ceil((double) n_lookups_per_material[m] / (double) nthreads);
		xs_lookup_kernel_optimization_4<<<nblocks, nthreads>>>( in, GSD, m, n_lookups_per_material[m], offset );
		offset += n_lookups_per_material[m];
	}
	gpuErrchk( cudaPeekAtLastError() );
	gpuErrchk( cudaDeviceSynchronize() );
	
	////////////////////////////////////////////////////////////////////////////////
	// Reduce Verification Results
	////////////////////////////////////////////////////////////////////////////////
	if( mype == 0)	printf("Reducing verification results...\n");

	unsigned long verification_scalar = thrust::reduce(thrust::device, GSD.verification, GSD.verification + in.lookups, 0);
	gpuErrchk( cudaPeekAtLastError() );
	gpuErrchk( cudaDeviceSynchronize() );

	return verification_scalar;
}

int double_compare(const void * a, const void * b)
{
	double A = *((double *) a);
	double B = *((double *) b);

	if( A > B )
		return 1;
	else if( A < B )
		return -1;
	else
		return 0;
}

	NuclideGridPoint B = *((NuclideGridPoint *) b);

	if( A.energy > B.energy )

	else if( A.energy < B.energy )
		return -1;
	else
		return 0;
}


// RNG Used for Verification Option.
// This one has a static seed (must be set manually in source).
// Park & Miller Multiplicative Conguential Algorithm
// From "Numerical Recipes" Second Edition
double rn_v(void)
{
	static unsigned long seed = 1337;
	double ret;
	unsigned long n1;
	unsigned long a = 16807;
	unsigned long m = 2147483647;
	n1 = ( a * (seed) ) % m;
	seed = n1;
	ret = (double) n1 / m;
	return ret;
}


size_t estimate_mem_usage( Inputs in )
{
	size_t single_nuclide_grid = in.n_gridpoints * sizeof( NuclideGridPoint );
	size_t all_nuclide_grids   = in.n_isotopes * single_nuclide_grid;
	size_t size_UEG            = in.n_isotopes*in.n_gridpoints*sizeof(double) + in.n_isotopes*in.n_gridpoints*in.n_isotopes*sizeof(int);
	size_t size_hash_grid      = in.hash_bins * in.n_isotopes * sizeof(int);
	size_t memtotal;

	if( in.grid_type == UNIONIZED )
		memtotal          = all_nuclide_grids + size_UEG;
	else if( in.grid_type == NUCLIDE )
		memtotal          = all_nuclide_grids;
	else
		memtotal          = all_nuclide_grids + size_hash_grid;

	memtotal          = ceil(memtotal / (1024.0*1024.0));
	return memtotal;
}

double get_time(void)
{
	#ifdef MPI
	return MPI_Wtime();
	#endif

	#ifdef OPENMP
	return omp_get_wtime();
	#endif

	// If using C++, we can do this:
	unsigned long us_since_epoch = std::chrono::high_resolution_clock::now().time_since_epoch() / std::chrono::microseconds(1);
	return (double) us_since_epoch / 1.0e6;
}
