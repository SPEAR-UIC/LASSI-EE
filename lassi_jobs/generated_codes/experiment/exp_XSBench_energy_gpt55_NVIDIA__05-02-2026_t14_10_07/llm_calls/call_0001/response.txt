- **Memory access coalescing**: Arrange data so adjacent threads in a warp access adjacent global-memory addresses. Prefer Struct-of-Arrays over Array-of-Structs for per-field access, and avoid strided patterns such as `arr[threadIdx.x * N + j]`. On A100, this is one of the highest-impact optimizations for memory-bound kernels because it reduces HBM2e transactions, execution time, and DRAM energy.

- **Shared memory use**: Use shared memory to stage data that is reused by multiple threads in a block, especially tiles or lookup data with spatial/local reuse. Load from global memory once, reuse from on-chip SRAM, and avoid shared-memory bank conflicts by ensuring access strides do not map many threads to the same bank. Most impactful when global data is reused within a block and when the alternative is repeated HBM2e loads.

- **Occupancy optimization**: Choose block sizes that expose enough active warps to hide latency, typically 128–256 threads per block on A100. Watch limits from registers, shared memory per block, and block size. Use the CUDA occupancy calculator or `cudaOccupancyMaxPotentialBlockSize`, and avoid register spilling because spilled “local” memory often goes to DRAM. Most impactful for latency-bound or memory-bound kernels that need many resident warps to cover memory latency.

- **Warp divergence reduction**: Reduce branches where threads in the same warp take different paths. Use branchless selection, short predicated code, or group/sort work so threads in a warp follow similar control flow. Most impactful when branch bodies are nontrivial or data-dependent control flow causes warps to serialize multiple paths.

- **Kernel fusion**: Merge consecutive kernels that operate on the same data so intermediate values remain in registers or shared memory instead of being written to and reread from global memory. This also reduces kernel launch overhead. Most impactful when kernels are memory-bound, use temporary arrays, or perform simple producer-consumer stages with compatible launch configurations and dependencies.

- **Read-only cache / `__ldg` / `const __restrict__`**: Mark read-only arrays as `const __restrict__` and, where useful, use `__ldg()` to route loads through the read-only/texture cache path. This can reduce L2 and DRAM pressure for repeated or spatially local reads. Most impactful for large read-only tables, lookup data, coefficients, and input arrays that are never written inside the kernel.

- **Arithmetic precision tradeoffs**: Use the lowest precision that preserves correctness. Prefer `float` over `double` when acceptable, use FMA where possible, and consider fast-math intrinsics such as `__expf`, `__logf`, or `__fdividef` only if reduced precision is allowed. Most impactful for compute-bound kernels, and also for memory-bound kernels when lower precision halves memory traffic.

- **Synchronization minimization**: Remove unnecessary `__syncthreads()`, move barriers out of loops when possible, and use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or warp reductions when only intra-warp coordination is required. Reduce high-contention atomics by aggregating within a block and issuing one atomic per block. Most impactful when barriers or atomics occur inside hot loops or cause many warps to stall.

- **Prefetching and transfer control**: Keep data resident on the GPU across kernels, use explicit `cudaMalloc`/`cudaMemcpy` when possible, pinned host memory for transfers, and `cudaMemcpyAsync` with streams to overlap transfers with computation. If using managed memory, prefetch data to the GPU before kernels to avoid costly page migrations. Most impactful when host-device transfers or unified-memory migrations are a significant fraction of runtime or when data is reused across multiple kernels.
