## Key actionable CUDA energy-efficiency techniques for NVIDIA A100

### 1. Coalesce global memory accesses
Make consecutive threads in a warp access consecutive memory locations. Prefer layouts such as Struct-of-Arrays over Array-of-Structs when each thread reads the same field from different elements.

- Aim for warp thread `i` to access `base + i`.
- Avoid strided patterns like `arr[threadIdx.x * N + j]`.
- Reorganize data or transpose arrays so accesses are contiguous across the warp.

**Most impactful when:** the kernel is memory-bound or performs large global-memory reads/writes. On A100, reducing unnecessary HBM2e transactions can significantly reduce both runtime and DRAM energy.

---

### 2. Use shared memory for reused data
Load data cooperatively from global memory into shared memory when multiple threads in a block reuse the same or nearby data.

- Use shared memory tiling to reduce repeated HBM2e accesses.
- Avoid shared-memory bank conflicts; do not use access strides that map many threads to the same bank.
- On A100, up to about 164 KB shared memory per SM is available, but high shared-memory usage can reduce occupancy.

**Most impactful when:** data has block-level spatial or temporal reuse, such as stencil codes, tiled matrix operations, reductions, or repeated access to common lookup data.

---

### 3. Tune occupancy without over-optimizing it
Choose block sizes and resource usage so enough warps are active to hide memory latency, but avoid excessive register or shared-memory pressure.

- Typical starting point: 128–256 threads per block.
- Keep block size a multiple of 32.
- Watch register count per thread and shared memory per block.
- Avoid register spilling, because spilled registers go to local memory, which often resides in DRAM.
- Use tools such as the CUDA Occupancy Calculator or `cudaOccupancyMaxPotentialBlockSize`.

**Most impactful when:** kernels are latency-bound or memory-bound and need enough active warps to hide HBM2e latency. It is also important when register pressure or shared-memory allocation limits active blocks per SM.

---

### 4. Reduce warp divergence
Minimize branches where threads in the same warp take different paths.

- Replace short divergent branches with predication or branchless expressions when appropriate.
- Keep branch bodies small so the compiler can predicate them.
- Group or sort input data so threads in the same warp follow similar control flow.
- Avoid data-dependent branches inside hot loops when possible.

**Most impactful when:** branch-heavy kernels process irregular data, such as particle simulations, graph workloads, Monte Carlo codes, or lookup-heavy kernels where threads follow different paths.

---

### 5. Fuse kernels when it avoids global-memory round trips
Combine consecutive kernels that operate on the same data so intermediate values remain in registers or shared memory instead of being written to and reread from global memory.

- Fuse only when launch configurations and dependencies are compatible.
- Be careful not to increase register pressure so much that occupancy collapses or spills occur.

**Most impactful when:** multiple small kernels are launched back-to-back, or when intermediate arrays are written to HBM2e only to be consumed immediately by the next kernel.

---

### 6. Use read-only cache paths with `__ldg` or `const __restrict__`
Mark input arrays as read-only so the compiler and hardware can use efficient read-only/cache paths.

- Use `const __restrict__` on kernel pointer arguments when arrays are not modified.
- Use `__ldg(&arr[i])` for explicit read-only loads when appropriate.
- This can reduce L2 pressure and repeated DRAM traffic.

**Most impactful when:** arrays are read-only and have spatial or temporal locality. It can also help irregular lookup workloads by routing loads through the read-only/texture cache path.

---

### 7. Choose arithmetic precision carefully
Use the lowest precision that preserves required correctness.

- Prefer `float` over `double` when numerical accuracy allows.
- Use FP16, BF16, Tensor Cores, or mixed precision only when the algorithm tolerates it.
- Use fused multiply-add where applicable.
- Use fast math intrinsics such as `__expf`, `__logf`, `__sinf`, or `__fdividef` only if their reduced precision is acceptable.

**Most impactful when:** the kernel is compute-bound, uses many floating-point operations, or stores/loads large floating-point arrays. Reducing precision can lower instruction cost, register pressure, memory bandwidth, and energy.

---

### 8. Minimize synchronization and atomics
Remove unnecessary barriers and reduce high-contention atomics.

- Use `__syncthreads()` only when required for correctness.
- Move barriers out of loops when possible.
- Use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or warp reductions when synchronization is only needed within a warp.
- For reductions, accumulate per thread or per block first, then issue fewer global atomics.

**Most impactful when:** kernels have frequent barriers, shared-memory phases inside loops, or many threads contending for the same atomic address.

---

### 9. Prefetch data and overlap transfers where possible
Move data early enough that computation can overlap with memory transfer or migration.

- Keep data resident on the GPU across multiple kernels.
- Prefer explicit `cudaMalloc`/`cudaMemcpy` over unmanaged implicit migrations when possible.
- Use pinned host memory and `cudaMemcpyAsync` with streams for host-device transfers.
- For Unified Memory, use prefetching to move data to the GPU before kernels access it.

**Most impactful when:** the program performs repeated host-device transfers, uses Unified Memory, or has predictable data movement that can be overlapped with computation.

## 1. Overall Algorithm and GPU Resource Utilization Profile

### Algorithm Summary

This is a CUDA implementation of the XSBench event-based macroscopic cross-section lookup workload. Each lookup performs the following high-level steps:

1. Generate a deterministic random neutron energy and material ID using an LCG random number generator.
2. For the sampled material, iterate over all nuclides in that material.
3. For each nuclide:
   - Locate the bounding energy grid points using one of three lookup modes:
     - `UNIONIZED`: one binary search in the unionized energy grid, followed by indexed lookup into each nuclide grid.
     - `NUCLIDE`: binary search directly in each nuclide’s energy grid.
     - `HASH`: approximate location using a hash bin, then bounded binary search in the nuclide grid.
   - Interpolate five microscopic cross-section values.
   - Accumulate them into a five-element macroscopic cross-section vector using the nuclide concentration.
4. Select the maximum cross-section channel and write a small verification value.
5. A final Thrust reduction sums the verification array.

### Resource Utilization Profile

The main lookup kernels are predominantly **memory-bound and latency-bound**, not compute-bound.

Reasons:

- The dominant data structure, `nuclide_grid`, is large and accessed with irregular, energy-dependent indices.
- The lookup path involves many global memory reads of `NuclideGridPoint` records.
- Binary searches generate divergent and scattered memory access patterns.
- The arithmetic per loaded byte is modest: mostly interpolation and accumulation of five double-precision values.
- The workload uses double precision throughout, increasing bandwidth demand and register pressure.
- Random material and energy sampling causes poor spatial locality in the baseline and early optimization kernels.

### Access Locality

- Baseline and optimization 1 have mostly random access to the nuclide grid and index structures.
- Optimization 2 and 3 reduce some warp-level workload imbalance by separating material classes, but still scan many inactive threads.
- Optimization 4 improves energy efficiency by sorting by material before launching material-specific kernels.
- Optimization 5 reduces sorting cost by partitioning only fuel vs non-fuel.
- Optimization 6 is the most locality-oriented variant: it sorts by material and then by energy, improving cache reuse and reducing divergent binary-search paths.

### Energy Efficiency Opportunities

- Favor material/energy grouping, as in optimization 6, for large lookup counts because it improves cache locality and reduces wasted execution.
- Avoid optimization 2 for energy efficiency: launching 12 full-grid kernels over all lookups causes most threads to exit early in each kernel.
- Avoid unnecessary double precision where verification and physics tolerance allow.
- Reduce global memory footprint by converting appropriate data from `double` to `float`.
- Move small read-only tables to constant memory or shared memory.
- Avoid excessive kernel launch overhead for small lookup counts.
- Avoid repeated host-device synchronization after every phase unless required for correctness.
- Free all allocated device arrays, including temporary optimized arrays, to avoid memory leakage across repeated runs.

## 2. CUDA Kernel Launch Configurations and Expected A100 Occupancy

### Baseline

#### `xs_lookup_kernel_baseline`

- Threads per block: `256`
- Blocks: `ceil(in.lookups / 256.0)`

Occupancy expectation on A100:

- 256-thread blocks are generally a good size for A100.
- Theoretical occupancy can be high: up to 8 such blocks per SM, or 64 warps per SM, if register usage allows.
- Actual occupancy may be limited by:
  - Register pressure from double-precision local arrays.
  - Inlined device functions.
  - Local arrays such as `macro_xs_vector[5]` and `xs_vector[5]`.
  - Long call chains and binary-search state.
- No shared memory limits occupancy.

Likely outcome:

- Occupancy is likely reasonable to high, but effective utilization is reduced by memory latency, scattered access, and warp divergence.

---

### Optimization 1

#### `sampling_kernel`

- Threads per block: `32`
- Blocks: `ceil(in.lookups / 32.0)`

#### `xs_lookup_kernel_optimization_1`

- Threads per block: `32`
- Blocks: `ceil(in.lookups / 32.0)`

Occupancy expectation on A100:

- A 32-thread block contains only one warp.
- A100 supports at most 32 resident blocks per SM, so this configuration can reach at most 32 resident warps per SM, or roughly 50% of the 64-warp theoretical maximum.
- This may still be sufficient for some latency hiding, but it is weaker than the 256-thread baseline configuration.
- Kernel launch overhead doubles relative to baseline because sampling and lookup are split.

Energy implication:

- Sampling writes are coalesced, but the extra global memory traffic for storing and reloading sampled energy/material can increase energy unless later kernels exploit the stored structure.

---

### Optimization 2

#### `sampling_kernel`

- Threads per block: `32`
- Blocks: `ceil(in.lookups / 32.0)`

#### `xs_lookup_kernel_optimization_2`

- Launched 12 times, once per material.
- Threads per block: `32`
- Blocks per launch: `ceil(in.lookups / 32.0)`

Occupancy expectation on A100:

- Same one-warp block limitation as optimization 1.
- Each material-specific launch scans the entire lookup array.
- Most threads return early because their sampled material does not match the kernel material.
- The GPU may have many resident blocks, but useful occupancy is low due to inactive threads.

Energy implication:

- Poor energy efficiency: 12 full passes over the lookup space cause significant wasted scheduling, memory reads, and control-flow overhead.

---

### Optimization 3

#### `sampling_kernel`

- Threads per block: `32`
- Blocks: `ceil(in.lookups / 32.0)`

#### `xs_lookup_kernel_optimization_3`

- Launched twice:
  - One launch for non-fuel.
  - One launch for fuel.
- Threads per block: `32`
- Blocks per launch: `ceil(in.lookups / 32.0)`

Occupancy expectation on A100:

- Same one-warp block limitation.
- Better than optimization 2 because only two full scans are performed instead of twelve.
- Still has many inactive threads in each launch.
- The non-fuel launch still contains materials with different nuclide counts, so warp divergence remains.

Energy implication:

- More energy-efficient than optimization 2.
- Still wastes energy due to full-array scanning and branch-based filtering.

---

### Optimization 4

#### `sampling_kernel`

- Threads per block: `32`
- Blocks: `ceil(in.lookups / 32.0)`

#### Thrust operations

- `thrust::count` called 12 times.
- `thrust::sort_by_key` called once to sort by material.
- Internal launch configurations are controlled by Thrust and are not explicitly visible in this source.

#### `xs_lookup_kernel_optimization_4`

- Launched 12 times, once per material.
- Threads per block: `32`
- Blocks per material: `ceil(n_lookups_per_material[m] / 32.0)`

Occupancy expectation on A100:

- Each material kernel uses one-warp blocks, limiting theoretical occupancy to about 50%.
- Unlike optimization 2, each launch processes only the compacted region for that material.
- For common materials, enough blocks should exist to fill the GPU.
- For rare materials, the number of blocks may be small, causing underutilization.
- Sorting overhead may be substantial but can pay off for large lookup counts.

Energy implication:

- More energy-efficient than optimization 2 because it avoids scanning the full lookup array for each material.
- Sorting cost is worthwhile only if the number of lookups is large enough.

---

### Optimization 5

#### `sampling_kernel`

- Threads per block: `32`
- Blocks: `ceil(in.lookups / 32.0)`

#### Thrust operations

- `thrust::count` for fuel lookups.
- `thrust::partition` to group fuel first.
- Internal launch configurations are controlled by Thrust.

#### `xs_lookup_kernel_optimization_5`

- Launched twice:
  - Fuel region:
    - Threads per block: `32`
    - Blocks: `ceil(n_fuel_lookups / 32.0)`
  - Non-fuel region:
    - Threads per block: `32`
    - Blocks: `ceil((in.lookups - n_fuel_lookups) / 32.0)`

Occupancy expectation on A100:

- Same one-warp block limitation.
- Fuel launch should have a moderate number of blocks for large workloads.
- Non-fuel launch should have enough blocks for most realistic lookup counts.
- Less sorting overhead than optimization 4.

Energy implication:

- Often a good compromise between sorting overhead and reduced warp divergence.
- Non-fuel material diversity still causes loop-length divergence.

---

### Optimization 6

#### `sampling_kernel`

- Threads per block: `32`
- Blocks: `ceil(in.lookups / 32.0)`

#### Thrust operations

- `thrust::count` called 12 times.
- `thrust::sort_by_key` once by material.
- Then 12 additional `thrust::sort_by_key` operations, one per material region, sorting by energy.
- Internal launch configurations are controlled by Thrust.

#### Lookup kernels

- Reuses `xs_lookup_kernel_optimization_4`.
- Launched 12 times.
- Threads per block: `32`
- Blocks per material: `ceil(n_lookups_per_material[m] / 32.0)`

Occupancy expectation on A100:

- Same one-warp block limitation for explicit kernels.
- Material-specific kernels avoid most material divergence.
- Energy sorting improves cache locality and branch coherence.
- Rare material kernels may underutilize the GPU.
- Thrust sorting can dominate runtime and energy for small to medium lookup counts.

Energy implication:

- Best lookup-kernel locality and likely best energy per useful lookup for very large workloads.
- May be less energy-efficient for small workloads because sorting overhead is high.

## 3. Global Memory Access Patterns by Kernel

### `xs_lookup_kernel_baseline`

Coalesced accesses:

- `GSD.verification[i]` writes are coalesced because consecutive threads write consecutive indices.

Mostly scattered accesses:

- `nuclide_grid` reads are highly scattered because each thread has a random energy and potentially different material.
- `index_grid` reads are scattered because `idx` depends on random energy.
- `unionized_energy_array` binary search is divergent and becomes scattered after the first few search levels.
- `mats` and `concs` accesses are partially structured within a thread but divergent across a warp because material IDs differ.

Energy impact:

- Poor coalescing and weak cache locality increase memory-system energy and stall time.

---

### `sampling_kernel`

Coalesced accesses:

- `GSD.p_energy_samples[i]` writes are coalesced.
- `GSD.mat_samples[i]` writes are coalesced.

Other behavior:

- No large random global reads.
- Mostly compute/register work from LCG and material sampling.

Energy impact:

- Relatively efficient memory behavior.
- Uses double-precision random generation and local material distribution logic, which could be simplified.

---

### `xs_lookup_kernel_optimization_1`

Coalesced accesses:

- Reads of `GSD.p_energy_samples[i]` are coalesced.
- Reads of `GSD.mat_samples[i]` are coalesced.
- Writes to `GSD.verification[i]` are coalesced.

Mostly scattered accesses:

- Same scattered `nuclide_grid`, `index_grid`, and search accesses as baseline.

Energy impact:

- Extra global memory traffic from storing and reloading sampled values.
- No major locality improvement over baseline.

---

### `xs_lookup_kernel_optimization_2`

Coalesced accesses:

- Reads of `GSD.mat_samples[i]` are coalesced.
- For active threads, reads of `GSD.p_energy_samples[i]` are coalesced.
- Writes to `GSD.verification[i]` are coalesced for active threads.

Scattered accesses:

- Lookup data accesses remain scattered.
- Only threads matching the material proceed.

Energy impact:

- Inefficient because each of 12 kernels reads the material array for all lookups.
- Many threads exit early, wasting instruction issue and memory bandwidth.

---

### `xs_lookup_kernel_optimization_3`

Coalesced accesses:

- Reads of `GSD.mat_samples[i]` are coalesced.
- Reads of `GSD.p_energy_samples[i]` are coalesced for active threads.
- Writes to `GSD.verification[i]` are coalesced for active threads.

Scattered accesses:

- Lookup data remain scattered.
- Fuel and non-fuel paths reduce some workload imbalance, but non-fuel materials still differ in nuclide count.

Energy impact:

- Better than optimization 2, but still performs full-array scans twice.

---

### `xs_lookup_kernel_optimization_4`

Coalesced accesses:

- After sorting by material, `GSD.mat_samples[i]` and `GSD.p_energy_samples[i]` are accessed contiguously.
- `GSD.verification[i]` writes are contiguous within the sorted layout.
- Within each material-specific kernel, all threads tend to access the same material row in `mats` and `concs`.

Partially improved accesses:

- `mats[mat * max_num_nucs + j]` and `concs[mat * max_num_nucs + j]` are uniform across threads in a warp for a fixed material and loop index `j`.
- This is good for cache or constant-memory broadcast.

Still scattered accesses:

- `nuclide_grid` accesses remain random with respect to energy.
- `index_grid` accesses remain energy-dependent and scattered.

Energy impact:

- Better energy efficiency than optimization 2 and 3 for large workloads.
- Sorting cost must be amortized.

---

### `xs_lookup_kernel_optimization_5`

Coalesced accesses:

- Partitioned regions make fuel and non-fuel ranges contiguous.
- Reads of sampled arrays and writes to verification are coalesced.

Partially improved accesses:

- Fuel region has uniform material and therefore uniform nuclide loop length.
- Non-fuel region still mixes materials, so material-dependent loop divergence remains.

Still scattered accesses:

- Energy-dependent lookup structures are still random.

Energy impact:

- Good compromise between reduced divergence and lower sorting overhead.
- Less locality improvement than optimization 4 or 6.

---

### Optimization 6 Lookup Phase

Coalesced accesses:

- Material and energy arrays are contiguous within each material.
- Verification writes are contiguous.
- Material-specific `mats` and `concs` accesses are highly cache-friendly.

Improved spatial locality:

- Energy sorting means neighboring threads are more likely to search nearby grid regions.
- `unionized_energy_array`, `index_grid`, and `nuclide_grid` accesses become more clustered.
- Binary-search branches become more coherent within a warp.

Energy impact:

- Most favorable memory behavior among the explicit variants.
- Sorting overhead is substantial and should be justified by large lookup counts.

## 4. Shared Memory Usage

### Current Shared Memory Usage

There is no explicit shared memory usage.

- No `__shared__` arrays are declared.
- No dynamic shared memory is requested in any kernel launch.
- Occupancy is therefore not limited by shared memory.

### Local Memory / Register Pressure

Several per-thread arrays may reside in registers or spill to local memory depending on compiler decisions:

- `macro_xs_vector[5]`
- `xs_vector[5]`
- `dist[12]` inside `pick_mat`

Double precision increases register pressure. If spilling occurs, local memory traffic will further reduce energy efficiency.

### Potential Shared or Constant Memory Opportunities

#### Material metadata

The following are small and read-only during kernels:

- `num_nucs`
- `mats`
- `concs`
- Material probability distribution in `pick_mat`

Energy-efficient alternatives:

- Place material distribution constants in `__constant__` memory.
- Place `num_nucs`, `mats`, and possibly `concs` in constant memory if size constraints allow.
- For material-specific kernels, load the material’s `mats` and `concs` row into shared memory once per block.

#### Suitability

- For material-specific kernels, all threads in a warp often access the same `mats` and `concs` element for loop index `j`, so constant memory broadcast could be very efficient.
- For baseline and mixed-material kernels, constant memory is less ideal when threads access different material rows.
- Shared memory is less useful for the large `nuclide_grid` because accesses are random and too large to tile effectively.
- Energy sorting in optimization 6 makes caching of `nuclide_grid` more effective, but explicit shared-memory tiling would still be difficult.

## 5. Warp Divergence

### Common Divergence Sources

#### Kernel bounds checks

Present in all explicit kernels:

- `if (i >= in.lookups) return;`
- `if (i >= n_lookups) return;`

These only affect the final partial block and are minor.

---

### `pick_mat`

Divergent branches:

- Loop over material IDs.
- Nested accumulation loop.
- `if (roll < running) return i;`

Because each thread has a different random `roll`, material selection diverges within a warp.

Energy opportunity:

- Replace the nested loop with a fixed cumulative distribution table.
- Store the cumulative distribution in constant memory.
- Use a straight-line or binary-search style selection.

The existing behavior contains unusual comparison and loop bounds; see Section 8.

---

### `calculate_macro_xs`

Divergence sources:

- `if (grid_type == UNIONIZED)`
- `else if (grid_type == HASH)`

These are uniform for the whole kernel because `grid_type` comes from the input configuration, so they should not cause warp divergence in practice.

Major divergence source:

- `for (int j = 0; j < num_nucs[mat]; j++)`

The number of nuclides depends on material. Fuel has many more nuclides than other materials.

Impact:

- Baseline and optimization 1 suffer severe loop-length divergence.
- Optimization 2 and 4 reduce this by using material-specific kernels.
- Optimization 3 and 5 reduce fuel/non-fuel imbalance but retain divergence among non-fuel materials.

---

### `calculate_micro_xs`

Divergence sources:

- `if (grid_type == NUCLIDE)`
- `else if (grid_type == UNIONIZED)`
- `else`

These are uniform for a given run, so usually not warp-divergent.

Within lookup modes:

#### NUCLIDE mode

- Binary search branch:
  - `if (A[examinationPoint].energy > quarry)`
- Boundary check:
  - `if (idx == n_gridpoints - 1)`

The binary search diverges because `quarry` differs by thread.

#### UNIONIZED mode

- Boundary check:
  - `if (index_data[idx * n_isotopes + nuc] == n_gridpoints - 1)`

This may diverge depending on energy and nuclide.

#### HASH mode

Divergent branches:

- `if (idx == hash_bins - 1)`
- `if (p_energy <= e_low)`
- `else if (p_energy >= e_high)`
- `else`
- `if (lower == n_gridpoints - 1)`

These are energy-dependent and likely divergent.

---

### `grid_search` and `grid_search_nuclide`

Divergence sources:

- Binary-search loop branch:
  - `if (A[examinationPoint] > quarry)`
  - `if (A[examinationPoint].energy > quarry)`

The loop count is mostly fixed by search range length, but branch direction diverges across threads with different sampled energies.

Energy opportunity:

- Energy sorting, as in optimization 6, improves branch coherence and cache locality.
- For fixed-size grids, specialized search strategies may reduce branch overhead.

---

### Verification Max Selection

Divergent branch:

- `if (macro_xs_vector[j] > max)`

This is a short fixed loop of length 5. Divergence cost is minor.

---

### Optimization-Specific Divergence

#### `xs_lookup_kernel_optimization_2`

- `if (mat != m) return;`

This causes heavy divergence and many inactive threads.

#### `xs_lookup_kernel_optimization_3`

- Outer branch:
  - `if (((is_fuel == 1) && (mat == 0)) || ((is_fuel == 0) && (mat != 0)))`

This causes divergence because some threads perform the lookup and others skip.

#### `xs_lookup_kernel_optimization_4`

- `if (mat != m) return;`

After sorting by material, this check should almost always be false for valid ranges. It is mostly redundant but preserves correctness.

#### `xs_lookup_kernel_optimization_5`

- Main divergence comes from mixed non-fuel materials and from search logic.

### Float-Replacement Candidates

If physics tolerance and verification requirements allow, the following are strong candidates for conversion to `float`:

- Cross-section values in `NuclideGridPoint`.
- Concentration values in `concs`.
- `xs_vector[5]`.
- `macro_xs_vector[5]`.
- Interpolation factor `f`.
- `p_energy`.
- `p_energy_samples`.
- `unionized_energy_array`.
- Material probability constants in `pick_mat`.
- `dist[12]`.
- `roll`.

### Energy Efficiency Benefits of Float

Using `float` would:

- Halve memory bandwidth for energy and cross-section arrays.
- Reduce cache footprint.
- Reduce register pressure.
- Potentially improve occupancy if registers are currently limiting.
- Reduce instruction energy, especially outside A100-class GPUs where FP64 throughput is much lower.

### Caution

Changing energy values or interpolation precision can change:

- Binary-search outcomes near grid boundaries.
- Interpolated cross-section values.
- Verification checksum.

Therefore, float conversion should be validated carefully. If the benchmark requires exact checksum preservation, wholesale conversion to float may not be acceptable.

### Integer/RNG Types

The LCG uses 64-bit unsigned integer arithmetic:

- `uint64_t`
- 64-bit multiply and modulo behavior

These should not be changed casually because they define the deterministic sampling sequence.

    input.hash_bins = 10000;
    input.binary_mode = NONE;
    input.kernel_id = 0;
    input.HM = (char *) malloc(6 * sizeof(char));
    input.HM[0] = 'l';
    input.HM[1] = 'a';
    input.HM[2] = 'r';
    input.HM[3] = 'g';
    input.HM[4] = 'e';
    input.HM[5] = '\0';

    int user_g = 0;
    int default_lookups = 1;
    int default_particles = 1;

    for (int i = 1; i < argc; i++)
    {
        char * arg = argv[i];

        if (strcmp(arg, "-g") == 0)
        {
            if (++i < argc)
            {
                user_g = 1;
                input.n_gridpoints = atol(argv[i]);
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-m") == 0)
        {
            char * sim_type;

            if (++i < argc)
            {
                sim_type = argv[i];
            }
            else
            {
                print_CLI_error();
            }

            if (strcmp(sim_type, "history") == 0)
            {
                input.simulation_method = HISTORY_BASED;
            }
            else if (strcmp(sim_type, "event") == 0)
            {
                input.simulation_method = EVENT_BASED;

                if (default_lookups && default_particles)
                {
                    input.lookups = input.lookups * input.particles;
                    input.particles = 0;
                }
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-l") == 0)
        {
            if (++i < argc)
            {
                input.lookups = atoi(argv[i]);
                default_lookups = 0;
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-h") == 0)
        {
            if (++i < argc)
            {
                input.hash_bins = atoi(argv[i]);
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-p") == 0)
        {
            if (++i < argc)
            {
                input.particles = atoi(argv[i]);
                default_particles = 0;
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-s") == 0)
        {
            if (++i < argc)
            {
                input.HM = argv[i];
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-G") == 0)
        {
            char * grid_type;

            if (++i < argc)
            {
                grid_type = argv[i];
            }
            else
            {
                print_CLI_error();
            }

            if (strcmp(grid_type, "unionized") == 0)
            {
                input.grid_type = UNIONIZED;
            }
            else if (strcmp(grid_type, "nuclide") == 0)
            {
                input.grid_type = NUCLIDE;
            }
            else if (strcmp(grid_type, "hash") == 0)
            {
                input.grid_type = HASH;
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-b") == 0)
        {
            char * binary_mode;

            if (++i < argc)
            {
                binary_mode = argv[i];
            }
            else
            {
                print_CLI_error();
            }

            if (strcmp(binary_mode, "read") == 0)
            {
                input.binary_mode = READ;
            }
            else if (strcmp(binary_mode, "write") == 0)
            {
                input.binary_mode = WRITE;
            }
            else
            {
                print_CLI_error();
            }
        }
        else if (strcmp(arg, "-k") == 0)
        {
            if (++i < argc)
            {
                input.kernel_id = atoi(argv[i]);
            }
            else
            {
                print_CLI_error();
            }
        }
        else
        {
            print_CLI_error();
        }
    }

    if (input.nthreads < 1)
    {
        print_CLI_error();
    }

    if (input.n_isotopes < 1)
    {
        print_CLI_error();
    }

    if (input.n_gridpoints < 1)
    {
        print_CLI_error();
    }

    if (input.lookups < 1)
    {
        print_CLI_error();
    }

    if (input.hash_bins < 1)
    {
        print_CLI_error();
    }

    if (strcasecmp(input.HM, "small") != 0 && strcasecmp(input.HM, "large") != 0 && strcasecmp(input.HM, "XL") != 0 && strcasecmp(input.HM, "XXL") != 0)
    {
        print_CLI_error();
    }

    if (strcasecmp(input.HM, "small") == 0)
    {
        input.n_isotopes = 68;
    }
    else if (strcasecmp(input.HM, "XL") == 0 && user_g == 0)
    {
        input.n_gridpoints = 238847;
    }
    else if (strcasecmp(input.HM, "XXL") == 0 && user_g == 0)
    {
        input.n_gridpoints = 238847 * 2.1;
    }

    return input;
}

    gpuErrchk(cudaMalloc((void **) &GSD.mats, sz));
    gpuErrchk(cudaMemcpy(GSD.mats, SD.mats, sz, cudaMemcpyHostToDevice));
    gpuErrchk(cudaMemcpyToSymbol(c_mats, SD.mats, sz, 0, cudaMemcpyHostToDevice));
    total_sz += sz;

    sz = GSD.length_unionized_energy_array * sizeof(double);
    gpuErrchk(cudaMalloc((void **) &GSD.unionized_energy_array, sz));
    gpuErrchk(cudaMemcpy(GSD.unionized_energy_array, SD.unionized_energy_array, sz, cudaMemcpyHostToDevice));

    gpuErrchk(cudaMalloc((void **) &GSD.index_grid, sz));
    gpuErrchk(cudaMemcpy(GSD.index_grid, SD.index_grid, sz, cudaMemcpyHostToDevice));

    gpuErrchk(cudaMemcpy(GSD.nuclide_grid, SD.nuclide_grid, sz, cudaMemcpyHostToDevice));

    if (mype == 0)

SimulationData grid_init_do_not_profile(Inputs in, int mype)
{
    SimulationData SD;
    size_t nbytes = 0;
    uint64_t seed = 42;

    if (mype == 0)
    {
        printf("Intializing nuclide grids...\n");
    }

    SD.length_nuclide_grid = in.n_isotopes * in.n_gridpoints;
    SD.nuclide_grid = (NuclideGridPoint *) malloc(SD.length_nuclide_grid * sizeof(NuclideGridPoint));
    assert(SD.nuclide_grid != NULL);
    nbytes += SD.length_nuclide_grid * sizeof(NuclideGridPoint);

    for (int i = 0; i < SD.length_nuclide_grid; i++)
    {
        SD.nuclide_grid[i].energy = LCG_random_double(&seed);
        SD.nuclide_grid[i].total_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].elastic_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].absorbtion_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].fission_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].nu_fission_xs = LCG_random_double(&seed);
    }

    for (int i = 0; i < in.n_isotopes; i++)
    {
        qsort(&SD.nuclide_grid[i * in.n_gridpoints], in.n_gridpoints, sizeof(NuclideGridPoint), NGP_compare);
    }

    if (in.grid_type == NUCLIDE)
    {
        SD.length_unionized_energy_array = 0;
        SD.length_index_grid = 0;
        SD.unionized_energy_array = NULL;
        SD.index_grid = NULL;
    }

    if (in.grid_type == UNIONIZED)
    {
        if (mype == 0)
        {
            printf("Intializing unionized grid...\n");
        }

        SD.length_unionized_energy_array = in.n_isotopes * in.n_gridpoints;
        SD.unionized_energy_array = (double *) malloc(SD.length_unionized_energy_array * sizeof(double));
        assert(SD.unionized_energy_array != NULL);
        nbytes += SD.length_unionized_energy_array * sizeof(double);

        for (int i = 0; i < SD.length_unionized_energy_array; i++)
        {
            SD.unionized_energy_array[i] = SD.nuclide_grid[i].energy;
        }

        qsort(SD.unionized_energy_array, SD.length_unionized_energy_array, sizeof(double), double_compare);

        SD.length_index_grid = SD.length_unionized_energy_array * in.n_isotopes;
        SD.index_grid = (int *) malloc(SD.length_index_grid * sizeof(int));
        assert(SD.index_grid != NULL);
        nbytes += SD.length_index_grid * sizeof(int);

        int * idx_low = (int *) calloc(in.n_isotopes, sizeof(int));
        assert(idx_low != NULL);
        double * energy_high = (double *) malloc(in.n_isotopes * sizeof(double));
        assert(energy_high != NULL);

        for (int i = 0; i < in.n_isotopes; i++)
        {
            energy_high[i] = SD.nuclide_grid[i * in.n_gridpoints + 1].energy;
        }

        for (long e = 0; e < SD.length_unionized_energy_array; e++)
        {
            double unionized_energy = SD.unionized_energy_array[e];

            for (long i = 0; i < in.n_isotopes; i++)
            {
                if (unionized_energy < energy_high[i])
                {
                    SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
                }
                else if (idx_low[i] == in.n_gridpoints - 2)
                {
                    SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
                }
                else
                {
                    idx_low[i]++;
                    SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
                    energy_high[i] = SD.nuclide_grid[i * in.n_gridpoints + idx_low[i] + 1].energy;
                }
            }
        }

        free(idx_low);
        free(energy_high);
    }

    if (in.grid_type == HASH)
    {
        if (mype == 0)
        {
            printf("Intializing hash grid...\n");
        }

        SD.length_unionized_energy_array = 0;
        SD.unionized_energy_array = NULL;
        SD.length_index_grid = in.hash_bins * in.n_isotopes;
        SD.index_grid = (int *) malloc(SD.length_index_grid * sizeof(int));
        assert(SD.index_grid != NULL);
        nbytes += SD.length_index_grid * sizeof(int);

        double du = 1.0 / in.hash_bins;

        for (long e = 0; e < in.hash_bins; e++)
        {
            double energy = e * du;

            for (long i = 0; i < in.n_isotopes; i++)
            {
                SD.index_grid[e * in.n_isotopes + i] = grid_search_nuclide(in.n_gridpoints, energy, SD.nuclide_grid + i * in.n_gridpoints, 0, in.n_gridpoints - 1);
            }
        }
    }

    if (mype == 0)
    {
        printf("Intializing material data...\n");
    }

    SD.num_nucs = load_num_nucs(in.n_isotopes);
    SD.length_num_nucs = 12;
    SD.mats = load_mats(SD.num_nucs, in.n_isotopes, &SD.max_num_nucs);
    SD.length_mats = SD.length_num_nucs * SD.max_num_nucs;
    SD.concs = load_concs(SD.num_nucs, SD.max_num_nucs);
    SD.length_concs = SD.length_mats;
    SD.verification = NULL;
    SD.length_verification = 0;
    SD.p_energy_samples = NULL;
    SD.length_p_energy_samples = 0;
    SD.mat_samples = NULL;
    SD.length_mat_samples = 0;

    if (mype == 0)
    {
        printf("Intialization complete. Allocated %.0lf MB of data on CPU.\n", nbytes / 1024.0 / 1024.0);
    }

    return SD;
}

unsigned long long run_event_based_simulation_baseline(Inputs in, SimulationData GSD, int mype)
{
    if (mype == 0)
    {
        printf("Running baseline event-based simulation...\n");
    }

    int nthreads = 256;
    int nblocks = div_round_up_int(in.lookups, nthreads);

    xs_lookup_kernel_baseline<<<nblocks, nthreads>>>(in, GSD);
    gpuErrchk(cudaPeekAtLastError());

    unsigned long verification_scalar = reduce_verification(in, GSD, mype);

    return verification_scalar;
}

__global__ void xs_lookup_kernel_baseline(Inputs in, SimulationData GSD)
{
    const int i = blockIdx.x * blockDim.x + threadIdx.x;

    if (i >= in.lookups)
    {
        return;
    }

    uint64_t seed = STARTING_SEED;
    seed = fast_forward_LCG(seed, 2 * i);

    double p_energy = LCG_random_double(&seed);
    int mat = pick_mat(&seed);

    double macro_xs_vector[5] = {0};

    calculate_macro_xs(p_energy, mat, in.n_isotopes, in.n_gridpoints, GSD.num_nucs, GSD.concs, GSD.unionized_energy_array, GSD.index_grid, GSD.nuclide_grid, GSD.mats, macro_xs_vector, in.grid_type, in.hash_bins, GSD.max_num_nucs);

    double max = -1.0;
    int max_idx = 0;

    #pragma unroll
    for (int j = 0; j < 5; j++)
    {
        if (macro_xs_vector[j] > max)
        {
            max = macro_xs_vector[j];
            max_idx = j;
        }
    }

    GSD.verification[i] = max_idx + 1;
}

__device__ void calculate_micro_xs(double p_energy, int nuc, long n_isotopes, long n_gridpoints, double * __restrict__ egrid, int * __restrict__ index_data, NuclideGridPoint * __restrict__ nuclide_grids, long idx, double * __restrict__ xs_vector, int grid_type, int hash_bins)
{
    double f;
    NuclideGridPoint * low;
    NuclideGridPoint * high;

    if (grid_type == NUCLIDE)
    {
        idx = grid_search_nuclide(n_gridpoints, p_energy, &nuclide_grids[nuc * n_gridpoints], 0, n_gridpoints - 1);

        if (idx == n_gridpoints - 1)
        {
            low = &nuclide_grids[nuc * n_gridpoints + idx - 1];
        }
        else
        {
            low = &nuclide_grids[nuc * n_gridpoints + idx];
        }
    }
    else if (grid_type == UNIONIZED)
    {
        int index_value = __ldg(&index_data[idx * n_isotopes + nuc]);

        if (index_value == n_gridpoints - 1)
        {
            low = &nuclide_grids[nuc * n_gridpoints + index_value - 1];
        }
        else
        {
            low = &nuclide_grids[nuc * n_gridpoints + index_value];
        }
    }
    else
    {
        int u_low = __ldg(&index_data[idx * n_isotopes + nuc]);
        int u_high;

        if (idx == hash_bins - 1)
        {
            u_high = n_gridpoints - 1;
        }
        else
        {
            u_high = __ldg(&index_data[(idx + 1) * n_isotopes + nuc]) + 1;
        }

        double e_low = __ldg(&nuclide_grids[nuc * n_gridpoints + u_low].energy);
        double e_high = __ldg(&nuclide_grids[nuc * n_gridpoints + u_high].energy);
        int lower;

        if (p_energy <= e_low)
        {
            lower = 0;
        }
        else if (p_energy >= e_high)
        {
            lower = n_gridpoints - 1;
        }
        else
        {
            lower = grid_search_nuclide(n_gridpoints, p_energy, &nuclide_grids[nuc * n_gridpoints], u_low, u_high);
        }

        if (lower == n_gridpoints - 1)
        {
            low = &nuclide_grids[nuc * n_gridpoints + lower - 1];
        }
        else
        {
            low = &nuclide_grids[nuc * n_gridpoints + lower];
        }
    }

    high = low + 1;

    double high_energy = __ldg(&high->energy);
    double low_energy = __ldg(&low->energy);

    f = (high_energy - p_energy) / (high_energy - low_energy);

    xs_vector[0] = __ldg(&high->total_xs) - f * (__ldg(&high->total_xs) - __ldg(&low->total_xs));
    xs_vector[1] = __ldg(&high->elastic_xs) - f * (__ldg(&high->elastic_xs) - __ldg(&low->elastic_xs));
    xs_vector[2] = __ldg(&high->absorbtion_xs) - f * (__ldg(&high->absorbtion_xs) - __ldg(&low->absorbtion_xs));
    xs_vector[3] = __ldg(&high->fission_xs) - f * (__ldg(&high->fission_xs) - __ldg(&low->fission_xs));
    xs_vector[4] = __ldg(&high->nu_fission_xs) - f * (__ldg(&high->nu_fission_xs) - __ldg(&low->nu_fission_xs));
}

__device__ void calculate_macro_xs(double p_energy, int mat, long n_isotopes, long n_gridpoints, int * __restrict__ num_nucs, double * __restrict__ concs, double * __restrict__ egrid, int * __restrict__ index_data, NuclideGridPoint * __restrict__ nuclide_grids, int * __restrict__ mats, double * __restrict__ macro_xs_vector, int grid_type, int hash_bins, int max_num_nucs)
{
    int p_nuc;
    long idx = -1;
    double conc;

    #pragma unroll
    for (int k = 0; k < 5; k++)
    {
        macro_xs_vector[k] = 0;
    }

    if (grid_type == UNIONIZED)
    {
        idx = grid_search(n_isotopes * n_gridpoints, p_energy, egrid);
    }
    else if (grid_type == HASH)
    {
        double du = 1.0 / hash_bins;
        idx = p_energy / du;
    }

    if (max_num_nucs <= MAX_CONSTANT_MAT_NUCS)
    {
        for (int j = 0; j < c_num_nucs[mat]; j++)
        {
            double xs_vector[5];
            p_nuc = c_mats[mat * max_num_nucs + j];
            conc = c_concs[mat * max_num_nucs + j];

            calculate_micro_xs(p_energy, p_nuc, n_isotopes, n_gridpoints, egrid, index_data, nuclide_grids, idx, xs_vector, grid_type, hash_bins);

            #pragma unroll
            for (int k = 0; k < 5; k++)
            {
                macro_xs_vector[k] += xs_vector[k] * conc;
            }
        }
    }
    else
    {
        for (int j = 0; j < num_nucs[mat]; j++)
        {
            double xs_vector[5];
            p_nuc = mats[mat * max_num_nucs + j];
            conc = concs[mat * max_num_nucs + j];

            calculate_micro_xs(p_energy, p_nuc, n_isotopes, n_gridpoints, egrid, index_data, nuclide_grids, idx, xs_vector, grid_type, hash_bins);

            #pragma unroll
            for (int k = 0; k < 5; k++)
            {
                macro_xs_vector[k] += xs_vector[k] * conc;
            }
        }
    }
}

__device__ long grid_search(long n, double quarry, double * __restrict__ A)
{
    long lowerLimit = 0;
    long upperLimit = n - 1;
    long examinationPoint;
    long length = upperLimit - lowerLimit;

    while (length > 1)
    {
        examinationPoint = lowerLimit + (length / 2);

        if (__ldg(&A[examinationPoint]) > quarry)
        {
            upperLimit = examinationPoint;
        }
        else
        {
            lowerLimit = examinationPoint;
        }

        length = upperLimit - lowerLimit;
    }

    return lowerLimit;
}

__host__ __device__ long grid_search_nuclide(long n, double quarry, NuclideGridPoint * A, long low, long high)
{
    long lowerLimit = low;
    long upperLimit = high;
    long examinationPoint;
    long length = upperLimit - lowerLimit;

    while (length > 1)
    {
        examinationPoint = lowerLimit + (length / 2);

#ifdef __CUDA_ARCH__
        if (__ldg(&A[examinationPoint].energy) > quarry)
#else
        if (A[examinationPoint].energy > quarry)
#endif
        {
            upperLimit = examinationPoint;
        }
        else
        {

        }

        length = upperLimit - lowerLimit;
    }

    return lowerLimit;
}

__device__ int pick_mat(uint64_t * seed)
{
    double roll = LCG_random_double(seed);

    for (int i = 0; i < 12; i++)
    {
        double running = 0;

        for (int j = i; j > 0; j--)
        {
            running += c_pick_dist[j];
        }

        if (roll < running)

        }
    }

    return 0;
}

__host__ __device__ double LCG_random_double(uint64_t * seed)
{
    const uint64_t m = 9223372036854775808ULL;
    const uint64_t a = 2806196910506780709ULL;
    const uint64_t c = 1ULL;
    *seed = (a * (*seed) + c) % m;
    return (double) (*seed) / (double) m;
}

__device__ uint64_t fast_forward_LCG(uint64_t seed, uint64_t n)
{
    const uint64_t m = 9223372036854775808ULL;
    uint64_t a = 2806196910506780709ULL;
    uint64_t c = 1ULL;

    n = n % m;

    uint64_t a_new = 1;
    uint64_t c_new = 0;

    while (n > 0)
    {
        if (n & 1)
        {
            a_new *= a;
            c_new = c_new * a + c;
        }

        c *= (a + 1);
        a *= a;
        n >>= 1;
    }

    return (a_new * seed + c_new) % m;
}

size_t estimate_mem_usage(Inputs in)
{
    size_t single_nuclide_grid = in.n_gridpoints * sizeof(NuclideGridPoint);
    size_t all_nuclide_grids = in.n_isotopes * single_nuclide_grid;
    size_t size_UEG = in.n_isotopes * in.n_gridpoints * sizeof(double) + in.n_isotopes * in.n_gridpoints * in.n_isotopes * sizeof(int);
    size_t size_hash_grid = in.hash_bins * in.n_isotopes * sizeof(int);
    size_t memtotal;

    if (in.grid_type == UNIONIZED)
    {
        memtotal = all_nuclide_grids + size_UEG;
    }
    else if (in.grid_type == NUCLIDE)
    {
        memtotal = all_nuclide_grids;
    }
    else
    {
        memtotal = all_nuclide_grids + size_hash_grid;
    }

    memtotal = ceil(memtotal / (1024.0 * 1024.0));

    return memtotal;
}
