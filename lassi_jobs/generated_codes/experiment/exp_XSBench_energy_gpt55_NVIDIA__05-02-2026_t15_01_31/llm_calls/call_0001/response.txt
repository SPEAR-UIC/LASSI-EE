- **Coalesce global memory accesses:** Arrange data and indexing so consecutive threads in a warp access consecutive memory locations. Prefer structure-of-arrays layouts over array-of-structs when each thread reads the same field from different elements. This reduces the number of HBM2e transactions and is usually the highest-impact optimization for memory-bound A100 kernels.

- **Use shared memory for reused data:** Load data cooperatively from global memory into shared memory when multiple threads in a block reuse the same or nearby values. Avoid shared-memory bank conflicts by choosing access strides that do not map many threads to the same bank. This is most impactful when there is spatial or temporal reuse within a thread block and global-memory traffic can be replaced by on-chip SRAM accesses.

- **Tune occupancy, but avoid over-optimizing it:** Use block sizes that are multiples of 32; 128–256 threads per block are often good starting points on A100. Watch register count and shared-memory allocation because both can limit active warps per SM. Use occupancy tools or `cudaOccupancyMaxPotentialBlockSize`, and avoid register spilling to local memory. This is most impactful when latency hiding is poor, memory stalls are high, or excessive registers/shared memory reduce active warps.

- **Reduce warp divergence:** Restructure control flow so threads in the same warp follow the same path when possible. Use branchless selection or short predicated code for small branches, and group/sort work items with similar behavior if practical. This is most impactful in kernels with data-dependent branches, irregular workloads, or table lookups where different threads take different execution paths.

- **Fuse kernels when possible:** Combine consecutive kernels that operate on the same data so intermediate values stay in registers or shared memory instead of being written to and reread from global memory. This also reduces launch overhead. This is most impactful when kernels are small, memory-bound, or connected by temporary arrays that exist only between kernel stages.

- **Use read-only cache paths with `__ldg` or `const __restrict__`:** Mark read-only input arrays as `const __restrict__`, and use `__ldg()` explicitly where appropriate. This can route loads through the read-only/texture cache path and reduce L2 and DRAM pressure. This is most impactful for read-only arrays with spatial or temporal locality, and can still help for irregular read-heavy workloads by improving cache utilization.

- **Choose arithmetic precision deliberately:** Use `float` instead of `double` when the application’s accuracy and verification requirements allow it. Lower precision reduces memory traffic, register pressure, and arithmetic energy. Use FMA where possible, and consider fast-math intrinsics only when their reduced precision is acceptable. This is most impactful in compute-bound kernels, kernels with high register pressure, or memory-bound kernels where using smaller data types reduces HBM2e traffic.

- **Minimize synchronization and atomics:** Avoid unnecessary `__syncthreads()`, especially inside loops. Use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or warp reductions when synchronization is only needed within a warp. Replace high-contention atomics with block-level reductions in shared memory followed by one atomic per block. This is most impactful in reduction-heavy kernels, shared-memory tiled kernels, and workloads with frequent barriers or many threads updating the same global address.

- **Prefetch and manage data movement explicitly:** Keep data resident on the GPU across multiple kernels, avoid unnecessary host-device transfers, use pinned memory and asynchronous copies when transfers are required, and overlap transfers with computation using streams. For Unified Memory, prefetch data to the GPU or use explicit `cudaMalloc`/`cudaMemcpy` to avoid costly page migrations. This is most impactful when the application frequently transfers data between CPU and GPU or uses Unified Memory with irregular access patterns.
