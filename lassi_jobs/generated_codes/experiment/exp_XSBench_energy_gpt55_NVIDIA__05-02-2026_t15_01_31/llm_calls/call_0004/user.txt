[CONTEXT KNOWLEDGE]
- **Coalesce global memory accesses:** Arrange data and indexing so consecutive threads in a warp access consecutive memory locations. Prefer structure-of-arrays layouts over array-of-structs when each thread reads the same field from different elements. This reduces the number of HBM2e transactions and is usually the highest-impact optimization for memory-bound A100 kernels.

- **Use shared memory for reused data:** Load data cooperatively from global memory into shared memory when multiple threads in a block reuse the same or nearby values. Avoid shared-memory bank conflicts by choosing access strides that do not map many threads to the same bank. This is most impactful when there is spatial or temporal reuse within a thread block and global-memory traffic can be replaced by on-chip SRAM accesses.

- **Tune occupancy, but avoid over-optimizing it:** Use block sizes that are multiples of 32; 128–256 threads per block are often good starting points on A100. Watch register count and shared-memory allocation because both can limit active warps per SM. Use occupancy tools or `cudaOccupancyMaxPotentialBlockSize`, and avoid register spilling to local memory. This is most impactful when latency hiding is poor, memory stalls are high, or excessive registers/shared memory reduce active warps.

- **Reduce warp divergence:** Restructure control flow so threads in the same warp follow the same path when possible. Use branchless selection or short predicated code for small branches, and group/sort work items with similar behavior if practical. This is most impactful in kernels with data-dependent branches, irregular workloads, or table lookups where different threads take different execution paths.

- **Fuse kernels when possible:** Combine consecutive kernels that operate on the same data so intermediate values stay in registers or shared memory instead of being written to and reread from global memory. This also reduces launch overhead. This is most impactful when kernels are small, memory-bound, or connected by temporary arrays that exist only between kernel stages.

- **Use read-only cache paths with `__ldg` or `const __restrict__`:** Mark read-only input arrays as `const __restrict__`, and use `__ldg()` explicitly where appropriate. This can route loads through the read-only/texture cache path and reduce L2 and DRAM pressure. This is most impactful for read-only arrays with spatial or temporal locality, and can still help for irregular read-heavy workloads by improving cache utilization.

- **Choose arithmetic precision deliberately:** Use `float` instead of `double` when the application’s accuracy and verification requirements allow it. Lower precision reduces memory traffic, register pressure, and arithmetic energy. Use FMA where possible, and consider fast-math intrinsics only when their reduced precision is acceptable. This is most impactful in compute-bound kernels, kernels with high register pressure, or memory-bound kernels where using smaller data types reduces HBM2e traffic.

- **Minimize synchronization and atomics:** Avoid unnecessary `__syncthreads()`, especially inside loops. Use warp-level primitives such as `__syncwarp`, `__ballot_sync`, or warp reductions when synchronization is only needed within a warp. Replace high-contention atomics with block-level reductions in shared memory followed by one atomic per block. This is most impactful in reduction-heavy kernels, shared-memory tiled kernels, and workloads with frequent barriers or many threads updating the same global address.

- **Prefetch and manage data movement explicitly:** Keep data resident on the GPU across multiple kernels, avoid unnecessary host-device transfers, use pinned memory and asynchronous copies when transfers are required, and overlap transfers with computation using streams. For Unified Memory, prefetch data to the GPU or use explicit `cudaMalloc`/`cudaMemcpy` to avoid costly page migrations. This is most impactful when the application frequently transfers data between CPU and GPU or uses Unified Memory with irregular access patterns.

## 1. Overall algorithm and GPU resource-utilization profile

### Algorithm summary

This is a CUDA implementation of the XSBench event-based macroscopic cross-section lookup workload.

For each lookup:

1. A deterministic random seed is generated from the lookup index.
2. A particle energy is sampled.
3. A material ID is sampled.
4. For that material, the code loops over all nuclides in the material.
5. For each nuclide, it locates the bounding energy grid points using one of three lookup modes:
   - `UNIONIZED`: one binary search in the global unionized energy grid, then indexed lookup into each nuclide grid.
   - `NUCLIDE`: binary search directly in each nuclide’s energy grid.
   - `HASH`: hash-bin lookup followed by a bounded nuclide-grid search.
6. It interpolates five cross-section values.
7. It accumulates the material-weighted macroscopic cross-section vector.
8. It writes a small verification value to global memory.
9. A Thrust reduction computes the final verification checksum.

### Resource-utilization profile

The main lookup kernels are primarily memory-latency-bound and cache-efficiency-bound, not arithmetic-throughput-bound.

Reasons:

- Each lookup performs many irregular global-memory reads from:
  - `nuclide_grid`
  - `index_grid`
  - `unionized_energy_array`
  - `mats`
  - `concs`
  - `num_nucs`
- Accesses are driven by random particle energies and randomly selected materials.
- Binary searches create data-dependent memory access patterns.
- The arithmetic intensity is low: each microscopic lookup reads two `NuclideGridPoint` entries and performs a small number of floating-point interpolation operations.
- `NuclideGridPoint` contains six `double` fields, so each grid point is 48 bytes. A low/high interpolation pair is roughly 96 bytes before considering index-grid and metadata traffic.
- The large unionized index grid can be very large and can dominate memory footprint.
- Warp lanes often process different materials and different energy locations, reducing cache reuse and memory coalescing.

### Compute-bound portions

Some parts have nontrivial compute cost:

- `fast_forward_LCG()` uses 64-bit integer arithmetic and a data-dependent loop.
- `LCG_random_double()` performs 64-bit integer operations and double conversion.
- Binary searches perform repeated comparisons and pointer-chasing.
- The interpolation uses double-precision arithmetic.

However, the overall kernel behavior is still dominated by irregular memory traffic, branch divergence, and poor locality.

### Energy-efficiency opportunities

The largest energy-efficiency opportunities are:

1. Improve locality by grouping lookups by material and energy.
   - Optimization 6 is the most locality-friendly variant because it sorts by material and then by energy.
   - This improves cache reuse and reduces random memory traffic.

2. Reduce wasted work from sparse material-filter kernels.
   - Optimization 2 launches 12 full-range kernels where most threads return early.
   - This wastes instruction issue, scheduling, memory reads of `mat_samples`, and launch overhead.

3. Replace double precision with single precision where numerically acceptable.
   - This would reduce memory bandwidth, cache footprint, register pressure, and FP energy per operation.

4. Move small read-only tables to constant memory or shared memory.
   - `num_nucs`, `mats`, `concs`, and the material probability distribution are small or moderately small and repeatedly read.

5. Avoid per-thread reconstruction of constant data.
   - `pick_mat()` builds a local `double dist[12]` per thread. This is inefficient.

6. Reduce excessive kernel launches and global synchronization.
   - Variants using many Thrust calls and many small kernels may save lookup work but add launch/synchronization overhead.

## 2. CUDA kernel launch configurations and likely A100 occupancy

### Baseline

#### `xs_lookup_kernel_baseline`

Launch configuration:

- Blocks: `ceil((double) in.lookups / 256.0)`
- Threads per block: `256`

Occupancy assessment on A100:

- 256 threads per block = 8 warps per block.
- This is generally a good block size for A100 occupancy.
- Theoretical occupancy could be high if register usage is moderate.
- Actual occupancy may be reduced by:
  - Large inlined call chain.
  - Per-thread local arrays:
    - `macro_xs_vector[5]`
    - `xs_vector[5]`
    - `dist[12]` inside `pick_mat()`
  - Many live variables in interpolation and search routines.
- Likely better occupancy than the 32-thread-block optimized variants.
- Energy concern: high occupancy does not fully compensate for random memory access and warp divergence.

---

### Optimization 1

#### `sampling_kernel`

Launch configuration:

- Blocks: `ceil((double) in.lookups / 32.0)`
- Threads per block: `32`

Occupancy assessment on A100:

- 32 threads per block = 1 warp per block.
- A100 supports a maximum number of resident blocks per SM, commonly 32.
- With 1 warp per block, block-count limits cap occupancy at roughly 32 resident warps per SM, i.e. about 50% of the 64-warp theoretical maximum, before considering registers.
- Likely not maximum occupancy.
- The kernel is relatively lightweight and writes coalesced sample arrays, so full occupancy may not be essential.

#### `xs_lookup_kernel_optimization_1`

Launch configuration:

- Blocks: `ceil((double) in.lookups / 32.0)`
- Threads per block: `32`

Occupancy assessment:

- Same 1-warp-per-block issue.
- Maximum theoretical occupancy likely capped below full A100 occupancy by block residency limits.
- Register pressure may further reduce occupancy.
- Splitting sampling from lookup increases global-memory traffic because sampled energies and materials are written and then read back.

---

### Optimization 2

#### `sampling_kernel`

Same as Optimization 1:

- Blocks: `ceil((double) in.lookups / 32.0)`
- Threads per block: `32`

#### `xs_lookup_kernel_optimization_2`

Launch configuration:

- Launched 12 times, once for each material `m = 0..11`.
- Each launch:
  - Blocks: `ceil((double) in.lookups / 32.0)`
  - Threads per block: `32`

Occupancy assessment:

- Each launch uses 1-warp blocks, so theoretical occupancy is likely capped around 50% by resident-block limits.
- More importantly, useful occupancy is poor because each material-specific kernel scans all lookups and most threads return early when `mat != m`.
- This creates significant wasted instruction issue and launch overhead.
- Energy efficiency is likely poor unless the reduction in material-loop divergence outweighs the 12 full-array passes.

---

### Optimization 3

#### `sampling_kernel`

Same as Optimization 1:

- Blocks: `ceil((double) in.lookups / 32.0)`
- Threads per block: `32`

#### `xs_lookup_kernel_optimization_3`

Launch configuration:

- Launched twice:
  - One launch with `is_fuel = 0`
  - One launch with `is_fuel = 1`
- Each launch:
  - Blocks: `ceil((double) in.lookups / 32.0)`
  - Threads per block: `32`

Occupancy assessment:

- Same 1-warp-per-block occupancy limitation.
- Better than Optimization 2 in launch count and full-array scan count.
- Still scans the full lookup array twice.
- In each launch, some threads return without doing lookup work.
- Useful occupancy depends on the fuel/non-fuel distribution.
- More energy-efficient than Optimization 2, but still wastes work.

---

### Optimization 4

#### `sampling_kernel`

Same as Optimization 1:

- Blocks: `ceil((double) in.lookups / 32.0)`
- Threads per block: `32`

#### Thrust operations

Additional GPU work:

- 12 calls to `thrust::count`
- 1 call to `thrust::sort_by_key`
- 1 final `thrust::reduce`

These launch internal CUDA kernels with implementation-defined configurations.

#### `xs_lookup_kernel_optimization_4`

Launch configuration:

- Launched once per material, 12 launches total.
- For material `m`:
  - Threads per block: `32`
  - Blocks: `ceil((double) n_lookups_per_material[m] / 32.0)`

Occupancy assessment:

- 1-warp blocks again limit theoretical occupancy on A100.
- Unlike Optimization 2, each material kernel processes only the compacted range for that material.
- This improves useful occupancy and reduces early-return waste.
- Some material-specific kernels may be very small, producing low device occupancy and poor launch efficiency.
- The full material sort adds substantial global-memory traffic but can reduce divergence and improve cache locality in the lookup phase.

---

### Optimization 5

#### `sampling_kernel`

Same as Optimization 1:

- Blocks: `ceil((double) in.lookups / 32.0)`
- Threads per block: `32`

#### Thrust operations

Additional GPU work:

- 1 call to `thrust::count`
- 1 call to `thrust::partition`
- 1 final `thrust::reduce`

#### `xs_lookup_kernel_optimization_5`

Launch configuration:

- Launched twice:
  1. Fuel segment:
     - Blocks: `ceil((double) n_fuel_lookups / 32.0)`
     - Threads per block: `32`
  2. Non-fuel segment:
     - Blocks: `ceil((double) (in.lookups - n_fuel_lookups) / 32.0)`
     - Threads per block: `32`

Occupancy assessment:

- 1-warp blocks cap theoretical occupancy below full A100 occupancy.
- Better useful occupancy than Optimization 3 because the data is partitioned and each launch processes a compact segment.
- Non-fuel segment still contains multiple materials, so material-dependent loop divergence remains.
- Lower sorting/partitioning overhead than full material sort, but less locality improvement than Optimization 4 or 6.

---

### Optimization 6

#### `sampling_kernel`

Same as Optimization 1:

- Blocks: `ceil((double) in.lookups / 32.0)`
- Threads per block: `32`

#### Thrust operations

Additional GPU work:

- 12 calls to `thrust::count`
- 1 material `thrust::sort_by_key`
- 12 energy-local `thrust::sort_by_key` calls, one per material segment
- 1 final `thrust::reduce`

#### Lookup kernel

Optimization 6 reuses `xs_lookup_kernel_optimization_4`.

Launch configuration:

- Launched once per material, 12 launches total.
- For material `m`:
  - Threads per block: `32`
  - Blocks: `ceil((double) n_lookups_per_material[m] / 32.0)`

Occupancy assessment:

- Same 1-warp-block theoretical occupancy limitation.
- Lookup phase has the best memory locality and lowest divergence among the implemented variants because particles are grouped by material and sorted by energy.
- The sort overhead is substantial.
- Energy efficiency depends heavily on the number of lookups:
  - For small lookup counts, sorting overhead may dominate.
  - For large lookup counts, better locality and lower divergence may justify the extra work.

---

### General launch-configuration energy observations

- The baseline uses 256-thread blocks and is more likely to achieve high hardware occupancy.
- Optimized variants use 32-thread blocks, which are warp-sized but can cap occupancy due to the maximum-resident-block limit.
- A better compromise may be 128 or 256 threads per block while still preserving warp-level grouping behavior.
- Many optimized variants use multiple kernel launches and Thrust operations, increasing launch overhead and synchronization cost.
- Material-specific kernels with very small `n_lookups_per_material[m]` may underutilize the A100.

## 3. Global-memory access patterns in each kernel

### `xs_lookup_kernel_baseline`

#### Coalesced accesses

- `GSD.verification[i] = max_idx + 1`
  - Consecutive threads write consecutive verification entries.
  - This is coalesced.

#### Scattered or irregular accesses

- `unionized_energy_array` in `grid_search`
  - Binary search indices are energy-dependent.
  - Different warp lanes search for different random energies.
  - Accesses are scattered and generally not coalesced.

- `index_grid[idx * n_isotopes + nuc]`
  - `idx` varies by thread.
  - `nuc` varies with material and loop iteration.
  - Accesses are mostly scattered.
  - If multiple lanes process the same material and nearby energy, locality improves, but baseline does not enforce this.

- `nuclide_grid[nuc * n_gridpoints + index]`
  - Random energy and material cause scattered accesses.
  - Each interpolation reads adjacent `low` and `high` points, so there is local per-thread spatial locality.
  - Across warp lanes, accesses are generally not coalesced.

- `mats[mat * max_num_nucs + j]`
  - If warp lanes have different `mat`, accesses diverge.
  - If lanes share the same material and same `j`, accesses may be broadcast/cache-friendly.

- `concs[mat * max_num_nucs + j]`
  - Similar behavior to `mats`.

- `num_nucs[mat]`
  - Small array; likely cache-resident, but material IDs differ across lanes.

Energy-efficiency implication:

- Baseline wastes energy on memory transactions with low coalescing efficiency and poor cache reuse.

---

### `sampling_kernel`

#### Coalesced accesses

- `GSD.p_energy_samples[i] = p_energy`
  - Consecutive threads write consecutive `double` entries.
  - Coalesced.

- `GSD.mat_samples[i] = mat`
  - Consecutive threads write consecutive `int` entries.
  - Coalesced.

#### Scattered or irregular accesses

- No major global-memory reads besides kernel parameters.
- RNG and material selection are compute/control-flow dominated.

Energy-efficiency implication:

- This kernel is mostly efficient from a memory-coalescing perspective.
- However, `pick_mat()` uses per-thread local distribution setup and divergent control flow.

---

### `xs_lookup_kernel_optimization_1`

#### Coalesced accesses

- `GSD.p_energy_samples[i]`
  - Consecutive threads read consecutive energies.
  - Coalesced.

- `GSD.mat_samples[i]`
  - Consecutive threads read consecutive material IDs.
  - Coalesced.

- `GSD.verification[i]`
  - Consecutive writes.
  - Coalesced.

#### Scattered or irregular accesses

- Same lookup-table accesses as baseline:
  - `unionized_energy_array`
  - `index_grid`
  - `nuclide_grid`
  - `mats`
  - `concs`
  - `num_nucs`

Energy-efficiency implication:

- Adds extra global-memory traffic for sample storage and reload.
- Does not by itself improve lookup locality.

---

### `xs_lookup_kernel_optimization_2`

#### Coalesced accesses

- `GSD.mat_samples[i]`
  - Read coalesced during the material filter.
- `GSD.p_energy_samples[i]`
  - Read coalesced only by active lanes.
- `GSD.verification[i]`
  - Coalesced among active lanes, but active lanes may be sparse.

#### Scattered or irregular accesses

- Lookup-table access remains scattered.
- Because each launch targets one material, active lanes within a warp are more likely to have the same material only if the original sample order happens to cluster that material.
- Since the input is not sorted, active lanes are sparse and irregular.

Energy-efficiency implication:

- Poor energy efficiency due to 12 full passes over `mat_samples` and many early returns.

---

### `xs_lookup_kernel_optimization_3`

#### Coalesced accesses

- `GSD.mat_samples[i]`
  - Coalesced filter read.
- `GSD.p_energy_samples[i]`
  - Coalesced for active lanes.
- `GSD.verification[i]`
  - Coalesced among active lanes, but active lanes may be sparse.

#### Scattered or irregular accesses

- Fuel launch has uniform material for active work.
- Non-fuel launch still mixes 11 materials, so `num_nucs`, `mats`, `concs`, and loop lengths remain divergent.
- Energy-table accesses remain random.

Energy-efficiency implication:

- Less waste than Optimization 2, but still performs full-array scans and has sparse active lanes.

---

### `xs_lookup_kernel_optimization_4`

#### Coalesced accesses

- `GSD.p_energy_samples[i]`
  - Material-sorted, compact segment; reads are consecutive.
- `GSD.mat_samples[i]`
  - Reads are consecutive and should all equal the material `m`.
- `GSD.verification[i]`
  - Consecutive writes within each material segment.

#### Scattered or irregular accesses

- Energies are not sorted within each material in Optimization 4.
- `unionized_energy_array`, `index_grid`, and `nuclide_grid` accesses remain energy-random.
- `mats` and `concs` accesses become much more coherent because all active lanes process the same material.

Energy-efficiency implication:

- Better than baseline and Optimization 1–3 for reducing material-loop divergence.
- Still limited by random energy-grid accesses.

---

### `xs_lookup_kernel_optimization_5`

#### Coalesced accesses

- `GSD.p_energy_samples[i]`
  - Partitioned into fuel and non-fuel compact segments.
- `GSD.mat_samples[i]`
  - Consecutive reads.
- `GSD.verification[i]`
  - Consecutive writes.

#### Scattered or irregular accesses

- Fuel segment has uniform material and better loop uniformity.
- Non-fuel segment still mixes materials and loop bounds.
- Energy-grid accesses remain random.

Energy-efficiency implication:

- Good compromise if fuel dominates cost.
- Less sorting overhead than full material sorting.
- Less locality improvement than Optimization 4 and 6.

---

### `xs_lookup_kernel_optimization_4` as used by Optimization 6

#### Coalesced accesses

- `GSD.p_energy_samples[i]`
  - Sorted by material and then by energy.
  - Consecutive threads read consecutive energy samples.
- `GSD.mat_samples[i]`
  - Consecutive and uniform within each material segment.
- `GSD.verification[i]`
  - Consecutive writes.

#### Improved locality

- Energy sorting means warp lanes process nearby energies.
- Binary searches tend to traverse similar regions.
- `index_grid` and `nuclide_grid` accesses are more likely to hit nearby or identical cache lines.
- This is the best implemented variant for cache efficiency.

#### Remaining scattered accesses

- Nuclide-grid accesses are still indexed by material nuclide composition and energy.
- Perfect coalescing is not guaranteed because grid indices may still differ by lane.

Energy-efficiency implication:

- Potentially the most energy-efficient lookup phase.
- Must be balanced against the high energy and time cost of multiple sorts.

## 4. Shared-memory usage

### Current shared-memory usage

There is no explicit CUDA shared memory usage.

- No `__shared__` allocations.
- No dynamic shared memory in kernel launches.
- No use of `__syncthreads()`.

### Current local/register usage relevant to shared memory

Per-thread local arrays include:

- `double macro_xs_vector[5]`
- `double xs_vector[5]`
- `double dist[12]` in `pick_mat()`

These are likely held in registers if possible, but may spill to local memory depending on compiler decisions and register pressure.

### Potential shared-memory or constant-memory opportunities

#### Material metadata

The following are small or moderately small read-mostly structures:

- `num_nucs`
- `mats`
- `concs`

Possible improvements:

- Place `num_nucs` in constant memory.
- Place material composition `mats` in constant memory if size permits and access patterns are broadcast-like.
- Place concentration data `concs` in constant memory or shared memory per material-specific kernel.
- For material-specific kernels, preload the material’s `mats` and `concs` into shared memory once per block.

Energy benefit:

- Reduces repeated global-memory reads.
- Improves cache locality.
- Reduces memory-system energy.

#### Material probability distribution

`pick_mat()` initializes a 12-element `double dist[12]` per thread.

Possible improvement:

- Store this distribution in `__constant__` memory.
- Or hard-code cumulative thresholds as constants.

Energy benefit:

- Avoids redundant per-thread initialization.
- Reduces register/local-memory pressure.

#### Nuclide grid and energy grid

Shared memory is less obviously useful for the full `nuclide_grid` or `unionized_energy_array` because accesses are random.

However:

- In Optimization 6, after energy sorting, nearby threads may access similar grid regions.
- A block-level cache of a small energy window could be beneficial, but this would require careful tiling and is nontrivial.
- Hardware L1/L2 may already capture much of this benefit if energy sorting is effective.

## 5. Warp divergence

### Major divergence sources

#### Bounds checks in kernels

Present in:

- `xs_lookup_kernel_baseline`
- `sampling_kernel`
- `xs_lookup_kernel_optimization_1`
- `xs_lookup_kernel_optimization_2`
- `xs_lookup_kernel_optimization_3`
- `xs_lookup_kernel_optimization_4`
- `xs_lookup_kernel_optimization_5`

Pattern:

- `if (i >= limit) return;`

Impact:

- Only affects the final partial block.
- Minor divergence.

---

### Material filtering divergence

#### `xs_lookup_kernel_optimization_2`

Branch:

- `if (mat != m) return;`

Impact:

- Severe divergence and wasted work.
- Each of 12 kernels scans all lookups.
- Most threads return early in each launch.

#### `xs_lookup_kernel_optimization_3`

Branch:

- Fuel/non-fuel condition:
  - `if (((is_fuel == 1) && (mat == 0)) || ((is_fuel == 0) && (mat != 0)))`

Impact:

- Divergence depends on fuel/non-fuel distribution within each warp.
- Still scans all lookups twice.
- Better than 12-way material scanning but still inefficient.

#### `xs_lookup_kernel_optimization_4`

Branch:

- `if (mat != m) return;`

Impact:

- After sorting by material, this should almost always be false.
- Mostly a safety check.
- Minimal divergence if sorting and counts are correct.

---

### Material-dependent loop divergence

In `calculate_macro_xs()`:

- Loop bound: `j < num_nucs[mat]`

Impact:

- Very important divergence source in baseline, Optimization 1, and the non-fuel part of Optimization 5.
- Materials have very different nuclide counts:
  - Fuel can have 34 or 321 nuclides.
  - Other materials have as few as 4 or 5 nuclides.
- Warp lanes processing different materials execute different loop lengths.
- This causes severe SIMD inefficiency.

Mitigation:

- Material grouping in Optimizations 4 and 6.
- Fuel/non-fuel grouping in Optimization 5 partially mitigates it.

---

### Lookup-mode branch divergence

In `calculate_macro_xs()`:

- `if (grid_type == UNIONIZED)`
- `else if (grid_type == HASH)`

In `calculate_micro_xs()`:

- `if (grid_type == NUCLIDE)`
- `else if (grid_type == UNIONIZED)`
- `else`

Impact:

- `grid_type` is an input parameter common to the whole kernel launch.
- This branch is uniform across all threads.
- It causes branch overhead but not warp divergence.

Energy opportunity:

- Compile separate specialized kernels for each grid type.
- This would remove runtime branches and allow better compiler optimization.

---

### Binary-search divergence

In `grid_search()`:

- `while (length > 1)`
- `if (A[examinationPoint] > quarry)`

In `grid_search_nuclide()`:

- `while (length > 1)`
- `if (A[examinationPoint].energy > quarry)`

Impact:

- The number of iterations is mostly fixed for a given search range, but the branch direction is data-dependent.
- Warp lanes search for different energies, so branch paths diverge.
- Memory addresses differ by lane, causing scattered loads.

Optimization 6 reduces this divergence by sorting by energy.

---

### Hash-grid edge-case divergence

In `calculate_micro_xs()` hash path:

- `if (idx == hash_bins - 1)`
- `if (p_energy <= e_low)`
- `else if (p_energy >= e_high)`
- `else`

Impact:

- Data-dependent.
- Can diverge within a warp.

---

### Nuclide-grid edge-case divergence

In `calculate_micro_xs()`:

- `if (idx == n_gridpoints - 1)`
- `if (index_data[...] == n_gridpoints - 1)`
- `if (lower == n_gridpoints - 1)`

Impact:

- Data-dependent but likely rare.
- Minor relative to material-loop divergence and binary-search divergence.

---

### Verification maximum selection divergence

In all lookup kernels:

- Loop over 5 entries.
- Branch:
  - `if (macro_xs_vector[j] > max)`

Impact:

- Small, fixed-size loop.
- Minor divergence and negligible compared with lookup work.

---

### RNG divergence

In `fast_forward_LCG()`:

- `while (n > 0)`
- `if (n & 1)`

Impact:

- `n` depends on lookup index.
- Different lanes may take different paths.
- This affects baseline and `sampling_kernel`.
- Splitting sampling isolates this cost from lookup kernels but does not eliminate it.

---

### Material sampling divergence

In `pick_mat()`:

- Loop over 12 materials.
- Branch:
  - `if (roll < running) return i;`

Impact:

- Data-dependent early returns.
- Causes warp divergence.
- Also performs redundant setup of `dist[12]` per thread.

---

## 9. Summary of energy-efficiency opportunities

### Highest-impact opportunities

1. Use material and energy grouping to improve locality.
   - Optimization 6 is the strongest existing example.
   - It reduces divergence and improves cache reuse.

2. Avoid full-array rescans with sparse active lanes.
   - Optimization 2 is especially energy-inefficient because it launches 12 full-range kernels.

3. Consider larger thread blocks for optimized variants.
   - 32-thread blocks may cap A100 occupancy.
   - 128 or 256 threads per block may improve occupancy while preserving warp-level behavior.

4. Reduce precision where acceptable.
   - Replacing large `double` arrays with `float` can significantly reduce memory traffic and energy.

5. Move small read-only tables to constant memory.
   - Especially material metadata and probability distributions.

6. Specialize kernels by grid type.
   - Remove runtime `grid_type` branches.
   - Improve compiler optimization.

7. Reduce synchronization and launch overhead.
   - Avoid unnecessary `cudaDeviceSynchronize()`.
   - Reduce the number of small kernels.
   - Be cautious with many Thrust calls.

8. Rework `pick_mat()` for energy efficiency while preserving exact behavior if required.
   - Current implementation repeatedly initializes a local distribution array and uses divergent early exits.

void fancy_int(long a)
{
    if (a < 1000)
    {
        printf("%ld\n", a);
    }
    else if (a >= 1000 && a < 1000000)
    {
        printf("%ld,%03ld\n", a / 1000, a % 1000);
    }
    else if (a >= 1000000 && a < 1000000000)
    {
        printf("%ld,%03ld,%03ld\n", a / 1000000, (a % 1000000) / 1000, a % 1000);
    }
    else if (a >= 1000000000)
    {
        printf("%ld,%03ld,%03ld,%03ld\n", a / 1000000000, (a % 1000000000) / 1000000, (a % 1000000) / 1000, a % 1000);
    }
    else
    {
        printf("%ld\n", a);
    }
}

            }

                input.grid_type = HASH;

        }
        else if (strcmp(arg, "-b") == 0)

SimulationData move_simulation_data_to_device(Inputs in, int mype, SimulationData SD)
{
    if (mype == 0)
    {
        printf("Allocating and moving simulation data to GPU memory space...\n");
    }

    size_t sz;
    size_t total_sz = 0;
    SimulationData GSD = SD;

    sz = GSD.length_num_nucs * sizeof(int);
    gpuErrchk(cudaMalloc((void **)&GSD.num_nucs, sz));
    gpuErrchk(cudaMemcpy(GSD.num_nucs, SD.num_nucs, sz, cudaMemcpyHostToDevice));
    total_sz += sz;

    sz = GSD.length_concs * sizeof(double);
    gpuErrchk(cudaMalloc((void **)&GSD.concs, sz));
    gpuErrchk(cudaMemcpy(GSD.concs, SD.concs, sz, cudaMemcpyHostToDevice));
    total_sz += sz;

    sz = GSD.length_mats * sizeof(int);
    gpuErrchk(cudaMalloc((void **)&GSD.mats, sz));
    gpuErrchk(cudaMemcpy(GSD.mats, SD.mats, sz, cudaMemcpyHostToDevice));
    total_sz += sz;

    sz = GSD.length_unionized_energy_array * sizeof(double);
    gpuErrchk(cudaMalloc((void **)&GSD.unionized_energy_array, sz));
    gpuErrchk(cudaMemcpy(GSD.unionized_energy_array, SD.unionized_energy_array, sz, cudaMemcpyHostToDevice));
    total_sz += sz;

    sz = GSD.length_index_grid * sizeof(int);
    gpuErrchk(cudaMalloc((void **)&GSD.index_grid, sz));
    gpuErrchk(cudaMemcpy(GSD.index_grid, SD.index_grid, sz, cudaMemcpyHostToDevice));
    total_sz += sz;

    sz = GSD.length_nuclide_grid * sizeof(NuclideGridPoint);
    gpuErrchk(cudaMalloc((void **)&GSD.nuclide_grid, sz));
    gpuErrchk(cudaMemcpy(GSD.nuclide_grid, SD.nuclide_grid, sz, cudaMemcpyHostToDevice));
    total_sz += sz;

    sz = in.lookups * sizeof(unsigned long);
    gpuErrchk(cudaMalloc((void **)&GSD.verification, sz));
    total_sz += sz;
    GSD.length_verification = in.lookups;
    GSD.p_energy_samples = NULL;
    GSD.mat_samples = NULL;
    GSD.length_p_energy_samples = 0;
    GSD.length_mat_samples = 0;

    gpuErrchk(cudaPeekAtLastError());
    gpuErrchk(cudaDeviceSynchronize());

    if (mype == 0)
    {
        printf("GPU Intialization complete. Allocated %.0lf MB of data on GPU.\n", total_sz / 1024.0 / 1024.0);
    }

    return GSD;
}

SimulationData grid_init_do_not_profile(Inputs in, int mype)
{
    SimulationData SD;
    size_t nbytes = 0;
    uint64_t seed = 42;

    if (mype == 0)
    {
        printf("Intializing nuclide grids...\n");
    }

    SD.length_nuclide_grid = in.n_isotopes * in.n_gridpoints;
    SD.nuclide_grid = (NuclideGridPoint *)malloc(SD.length_nuclide_grid * sizeof(NuclideGridPoint));
    assert(SD.nuclide_grid != NULL);
    nbytes += SD.length_nuclide_grid * sizeof(NuclideGridPoint);

    for (int i = 0; i < SD.length_nuclide_grid; i++)
    {
        SD.nuclide_grid[i].energy = LCG_random_double(&seed);
        SD.nuclide_grid[i].total_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].elastic_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].absorbtion_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].fission_xs = LCG_random_double(&seed);
        SD.nuclide_grid[i].nu_fission_xs = LCG_random_double(&seed);
    }

    for (int i = 0; i < in.n_isotopes; i++)
    {
        qsort(&SD.nuclide_grid[i * in.n_gridpoints], in.n_gridpoints, sizeof(NuclideGridPoint), NGP_compare);
    }

    SD.unionized_energy_array = NULL;
    SD.index_grid = NULL;

    if (in.grid_type == NUCLIDE)
    {
        SD.length_unionized_energy_array = 0;
        SD.length_index_grid = 0;
    }

    if (in.grid_type == UNIONIZED)
    {
        if (mype == 0)
        {
            printf("Intializing unionized grid...\n");
        }

        SD.length_unionized_energy_array = in.n_isotopes * in.n_gridpoints;
        SD.unionized_energy_array = (double *)malloc(SD.length_unionized_energy_array * sizeof(double));
        assert(SD.unionized_energy_array != NULL);
        nbytes += SD.length_unionized_energy_array * sizeof(double);

        for (int i = 0; i < SD.length_unionized_energy_array; i++)
        {
            SD.unionized_energy_array[i] = SD.nuclide_grid[i].energy;
        }

        qsort(SD.unionized_energy_array, SD.length_unionized_energy_array, sizeof(double), double_compare);

        SD.length_index_grid = SD.length_unionized_energy_array * in.n_isotopes;
        SD.index_grid = (int *)malloc(SD.length_index_grid * sizeof(int));
        assert(SD.index_grid != NULL);
        nbytes += SD.length_index_grid * sizeof(int);

        int * idx_low = (int *)calloc(in.n_isotopes, sizeof(int));
        assert(idx_low != NULL);

        double * energy_high = (double *)malloc(in.n_isotopes * sizeof(double));
        assert(energy_high != NULL);

        for (int i = 0; i < in.n_isotopes; i++)
        {
            energy_high[i] = SD.nuclide_grid[i * in.n_gridpoints + 1].energy;
        }

        for (long e = 0; e < SD.length_unionized_energy_array; e++)
        {
            double unionized_energy = SD.unionized_energy_array[e];

            for (long i = 0; i < in.n_isotopes; i++)
            {
                if (unionized_energy < energy_high[i])
                {
                    SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
                }
                else if (idx_low[i] == in.n_gridpoints - 2)
                {
                    SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
                }
                else
                {
                    idx_low[i]++;
                    SD.index_grid[e * in.n_isotopes + i] = idx_low[i];
                    energy_high[i] = SD.nuclide_grid[i * in.n_gridpoints + idx_low[i] + 1].energy;
                }
            }
        }

        free(idx_low);
        free(energy_high);
    }

    if (in.grid_type == HASH)
    {
        if (mype == 0)
        {
            printf("Intializing hash grid...\n");
        }

        SD.length_unionized_energy_array = 0;
        SD.length_index_grid = in.hash_bins * in.n_isotopes;
        SD.index_grid = (int *)malloc(SD.length_index_grid * sizeof(int));
        assert(SD.index_grid != NULL);
        nbytes += SD.length_index_grid * sizeof(int);

        double du = 1.0 / in.hash_bins;

        for (long e = 0; e < in.hash_bins; e++)
        {
            double energy = e * du;

            for (long i = 0; i < in.n_isotopes; i++)
            {
                SD.index_grid[e * in.n_isotopes + i] = grid_search_nuclide(in.n_gridpoints, energy, SD.nuclide_grid + i * in.n_gridpoints, 0, in.n_gridpoints - 1);
            }
        }
    }

    if (mype == 0)
    {
        printf("Intializing material data...\n");
    }

    SD.num_nucs = load_num_nucs(in.n_isotopes);
    SD.length_num_nucs = 12;

    SD.mats = load_mats(SD.num_nucs, in.n_isotopes, &SD.max_num_nucs);
    SD.length_mats = SD.length_num_nucs * SD.max_num_nucs;

    SD.concs = load_concs(SD.num_nucs, SD.max_num_nucs);
    SD.length_concs = SD.length_mats;

    if (mype == 0)
    {
        printf("Intialization complete. Allocated %.0lf MB of data on CPU.\n", nbytes / 1024.0 / 1024.0);
    }

    return SD;
}

unsigned long long run_event_based_simulation_baseline(Inputs in, SimulationData GSD, int mype)
{
    if (mype == 0)
    {
        printf("Running baseline event-based simulation...\n");
    }

    int nthreads = 256;
    int nblocks = div_up_int(in.lookups, nthreads);

    xs_lookup_kernel_baseline<<<nblocks, nthreads>>>(in, GSD);
    gpuErrchk(cudaPeekAtLastError());
    gpuErrchk(cudaDeviceSynchronize());

    if (mype == 0)
    {
        printf("Reducing verification results...\n");
    }

    unsigned long verification_scalar = thrust::reduce(thrust::device, GSD.verification, GSD.verification + in.lookups, 0UL);
    gpuErrchk(cudaPeekAtLastError());
    gpuErrchk(cudaDeviceSynchronize());

    return verification_scalar;
}

__global__ void xs_lookup_kernel_baseline(Inputs in, SimulationData GSD)
{

__device__ void calculate_micro_xs(double p_energy, int nuc, long n_isotopes, long n_gridpoints, double * __restrict__ egrid, int * __restrict__ index_data, NuclideGridPoint * __restrict__ nuclide_grids, long idx, double * __restrict__ xs_vector, int grid_type, int hash_bins)
{
    double f;
    NuclideGridPoint * low;
    NuclideGridPoint * high;

    if (grid_type == NUCLIDE)
    {
        idx = grid_search_nuclide(n_gridpoints, p_energy, &nuclide_grids[nuc * n_gridpoints], 0, n_gridpoints - 1);

        if (idx == n_gridpoints - 1)
        {
            low = &nuclide_grids[nuc * n_gridpoints + idx - 1];
        }
        else
        {
            low = &nuclide_grids[nuc * n_gridpoints + idx];
        }
    }
    else if (grid_type == UNIONIZED)
    {
        int gidx = __ldg(&index_data[idx * n_isotopes + nuc]);

        if (gidx == n_gridpoints - 1)
        {
            low = &nuclide_grids[nuc * n_gridpoints + gidx - 1];
        }
        else
        {
            low = &nuclide_grids[nuc * n_gridpoints + gidx];
        }
    }
    else
    {
        int u_low = __ldg(&index_data[idx * n_isotopes + nuc]);

        int u_high;
        if (idx == hash_bins - 1)
        {
            u_high = n_gridpoints - 1;
        }
        else
        {
            u_high = __ldg(&index_data[(idx + 1) * n_isotopes + nuc]) + 1;
        }

        double e_low = __ldg(&nuclide_grids[nuc * n_gridpoints + u_low].energy);
        double e_high = __ldg(&nuclide_grids[nuc * n_gridpoints + u_high].energy);

        int lower;
        if (p_energy <= e_low)
        {
            lower = 0;
        }
        else if (p_energy >= e_high)
        {
            lower = n_gridpoints - 1;
        }
        else
        {
            lower = grid_search_nuclide(n_gridpoints, p_energy, &nuclide_grids[nuc * n_gridpoints], u_low, u_high);
        }

        if (lower == n_gridpoints - 1)
        {
            low = &nuclide_grids[nuc * n_gridpoints + lower - 1];
        }
        else
        {
            low = &nuclide_grids[nuc * n_gridpoints + lower];
        }
    }

    high = low + 1;

    double low_energy = __ldg(&low->energy);
    double high_energy = __ldg(&high->energy);
    f = (high_energy - p_energy) / (high_energy - low_energy);

    double high_total_xs = __ldg(&high->total_xs);
    double low_total_xs = __ldg(&low->total_xs);
    double high_elastic_xs = __ldg(&high->elastic_xs);
    double low_elastic_xs = __ldg(&low->elastic_xs);
    double high_absorbtion_xs = __ldg(&high->absorbtion_xs);
    double low_absorbtion_xs = __ldg(&low->absorbtion_xs);
    double high_fission_xs = __ldg(&high->fission_xs);
    double low_fission_xs = __ldg(&low->fission_xs);
    double high_nu_fission_xs = __ldg(&high->nu_fission_xs);
    double low_nu_fission_xs = __ldg(&low->nu_fission_xs);

    xs_vector[0] = high_total_xs - f * (high_total_xs - low_total_xs);
    xs_vector[1] = high_elastic_xs - f * (high_elastic_xs - low_elastic_xs);
    xs_vector[2] = high_absorbtion_xs - f * (high_absorbtion_xs - low_absorbtion_xs);
    xs_vector[3] = high_fission_xs - f * (high_fission_xs - low_fission_xs);
    xs_vector[4] = high_nu_fission_xs - f * (high_nu_fission_xs - low_nu_fission_xs);
}

__device__ void calculate_macro_xs(double p_energy, int mat, long n_isotopes, long n_gridpoints, int * __restrict__ num_nucs, double * __restrict__ concs, double * __restrict__ egrid, int * __restrict__ index_data, NuclideGridPoint * __restrict__ nuclide_grids, int * __restrict__ mats, double * __restrict__ macro_xs_vector, int grid_type, int hash_bins, int max_num_nucs)
{
    int p_nuc;
    long idx = -1;
    double conc;

#pragma unroll
    for (int k = 0; k < 5; k++)
    {
        macro_xs_vector[k] = 0;
    }

    if (grid_type == UNIONIZED)
    {
        idx = grid_search(n_isotopes * n_gridpoints, p_energy, egrid);
    }
    else if (grid_type == HASH)
    {
        double du = 1.0 / hash_bins;
        idx = p_energy / du;
    }

    for (int j = 0; j < num_nucs[mat]; j++)
    {
        double xs_vector[5];
        p_nuc = __ldg(&mats[mat * max_num_nucs + j]);
        conc = __ldg(&concs[mat * max_num_nucs + j]);

        calculate_micro_xs(p_energy, p_nuc, n_isotopes, n_gridpoints, egrid, index_data, nuclide_grids, idx, xs_vector, grid_type, hash_bins);

#pragma unroll
        for (int k = 0; k < 5; k++)
        {
            macro_xs_vector[k] += xs_vector[k] * conc;
        }
    }
}

__device__ long grid_search(long n, double quarry, double * __restrict__ A)
{
    long lowerLimit = 0;
    long upperLimit = n - 1;
    long examinationPoint;
    long length = upperLimit - lowerLimit;

    while (length > 1)
    {
        examinationPoint = lowerLimit + (length / 2);

        if (__ldg(&A[examinationPoint]) > quarry)
        {
            upperLimit = examinationPoint;
        }
        else
        {
            lowerLimit = examinationPoint;
        }

        length = upperLimit - lowerLimit;
    }

    return lowerLimit;
}

__host__ __device__ long grid_search_nuclide(long n, double quarry, NuclideGridPoint * A, long low, long high)
{
    long lowerLimit = low;
    long upperLimit = high;
    long examinationPoint;
    long length = upperLimit - lowerLimit;

    while (length > 1)
    {
        examinationPoint = lowerLimit + (length / 2);

#ifdef __CUDA_ARCH__
        if (__ldg(&A[examinationPoint].energy) > quarry)
#else
        if (A[examinationPoint].energy > quarry)
#endif
        {
            upperLimit = examinationPoint;
        }
        else
        {
            lowerLimit = examinationPoint;
        }

        length = upperLimit - lowerLimit;
    }

    return lowerLimit;
}

__device__ int pick_mat(uint64_t * seed)
{
    double roll = LCG_random_double(seed);

    for (int i = 0; i < 12; i++)
    {
        double running = 0;

        for (int j = i; j > 0; j--)
        {
            running += c_mat_dist[j];
        }

        if (roll < running)
        {
            return i;
        }
    }

    return 0;
}

__host__ __device__ double LCG_random_double(uint64_t * seed)
{
    const uint64_t m = 9223372036854775808ULL;
    const uint64_t a = 2806196910506780709ULL;
    const uint64_t c = 1ULL;

    *seed = (a * (*seed) + c) % m;

    return (double)(*seed) / (double)m;
}

__device__ uint64_t fast_forward_LCG(uint64_t seed, uint64_t n)
{
    const uint64_t m = 9223372036854775808ULL;
    uint64_t a = 2806196910506780709ULL;
    uint64_t c = 1ULL;

    n = n % m;

    uint64_t a_new = 1;
    uint64_t c_new = 0;

    while (n > 0)
    {
        if (n & 1)
        {
            a_new *= a;
            c_new = c_new * a + c;
        }

        c *= (a + 1);
        a *= a;

        n >>= 1;
    }

    return (a_new * seed + c_new) % m;
}

size_t estimate_mem_usage(Inputs in)
{
    size_t single_nuclide_grid = in.n_gridpoints * sizeof(NuclideGridPoint);
    size_t all_nuclide_grids = in.n_isotopes * single_nuclide_grid;
    size_t size_UEG = in.n_isotopes * in.n_gridpoints * sizeof(double) + in.n_isotopes * in.n_gridpoints * in.n_isotopes * sizeof(int);
    size_t size_hash_grid = in.hash_bins * in.n_isotopes * sizeof(int);
    size_t memtotal;

    if (in.grid_type == UNIONIZED)
    {
        memtotal = all_nuclide_grids + size_UEG;
    }
    else if (in.grid_type == NUCLIDE)
    {
        memtotal = all_nuclide_grids;
    }
    else
    {
        memtotal = all_nuclide_grids + size_hash_grid;
    }

    memtotal = ceil(memtotal / (1024.0 * 1024.0));

    return memtotal;
}
