**CUDA to SYCL 2020 Migration: Key Concepts**

1. **Memory Model and Unified Shared Memory (USM):**
   - SYCL supports USM allocations: `malloc_device`, `malloc_host`, and `malloc_shared`, similar to CUDA's `cudaMalloc`, `cudaMallocHost`, and unified memory (managed).
   - USM allows direct pointer manipulation, making it similar to CUDA for device-memory management.
   - SYCL memory is associated with a context and device; be careful not to mix allocations across contexts.
   - Device querying and allocation use SYCL APIs, not CUDA-specific calls.

2. **Queue and Device Setup:**
   - SYCL abstracts device and execution streams as `queue`.
   - Device selection can be explicit (`device_selector`) or default.
   - SYCL queues can be **in-order** (like CUDA streams) or **out-of-order** (default SYCL), affecting command execution ordering.
   - SYCL uses exceptions for error handling (not error codes).

3. **Kernel Dispatch:**
   - SYCL kernels are submitted with `queue.submit()` or `queue.parallel_for()`, using C++ lambdas (not `__global__` functions).
   - Kernel code uses standard C++ syntax—no language extensions (contrast with CUDA’s `__global__`).
   - `q.parallel_for(range, [=](auto id) { ... })` is analogous to launching a CUDA kernel.

4. **ND-Range and Thread Indexing:**
   - SYCL uses `nd_range` to express global and local (work-group) sizes, similar to CUDA's blocks and threads.
   - Dimensional conventions differ: SYCL's *last* dimension is the fastest-moving (unit stride), whereas CUDA's *first* (x) is.
   - Kernel arguments get an `nd_item` object (for index calculations): `item.get_global_id(d)`, `item.get_local_id(d)`, `item.get_group(d)` correspond to CUDA’s `threadIdx`, `blockIdx`, and so on.
   - Sub-groups in SYCL are like CUDA warps, but their size is device-dependent.

5. **Local (Shared) Memory:**
   - CUDA’s `__shared__` memory is mapped to SYCL’s `local_accessor`, which is passed as a kernel argument.
   - Local memory is allocated per work-group.

6. **Synchronization (Group Barriers):**
   - CUDA’s `__syncthreads()` or cooperative group `sync()` maps to SYCL's `group_barrier(item.get_group())`.
   - SYCL barriers require *all* work-items in a group to reach the barrier—unlike CUDA, early exits before a barrier can cause deadlocks.
   - Fence scopes in SYCL (`memory_scope`) can be specified but default is usually sufficient.

7. **Atomics:**
   - SYCL 2020 uses `atomic_ref<T, memory_order, memory_scope>` (based on C++20).
   - Use `memory_order::relaxed` and `memory_scope::device` for CUDA-like relaxed device-scoped atomics.
   - Not all atomic operations/scopes are supported by all SYCL devices—check device capabilities.

8. **Common Pitfalls:**
   - Multidimensional ranges: transpose dimensions between CUDA and SYCL to account for contiguous stride difference.
   - Synchronization: restructuring code to avoid early exits before `group_barrier` is necessary to prevent deadlocks.
   - Built-in variables: CUDA's `threadIdx`, `blockIdx`, etc., are replaced by SYCL's `nd_item` methods.
   - Error handling: SYCL throws exceptions, not return codes.
   - Device contexts: SYCL context management is more explicit, requiring awareness when using multiple devices.
   - Global variables: SYCL device code doesn’t support global variables as CUDA does.
   - Cooperative groups: SYCL’s group/sub-group model is less flexible than CUDA's (e.g., no dynamic partitioning).
   - Specialized hardware (e.g., tensor/matrix cores): SYCL support is evolving and may require vendor-specific extensions.

9. **Migration Tools:**
   - Tools like Intel’s `dpct` and open-source SYCLomatic automate much of the translation, handling memory, indexing, and kernel structure.
   - Manual review and adjustment are usually needed, especially for error handling, device-specific features, and performance tuning.

**In Summary:**
Migrating from CUDA to SYCL is structurally straightforward but requires careful handling of memory, indexing, synchronization, atomics, and error checking. Awareness of the subtle differences, especially in memory management and execution model semantics, is crucial for correctness and portability to Intel GPUs using SYCL 2020 and icpx. Use migration tools as a starting point, but expect to perform manual refactoring for idiomatic SYCL and device-specific optimizations.
