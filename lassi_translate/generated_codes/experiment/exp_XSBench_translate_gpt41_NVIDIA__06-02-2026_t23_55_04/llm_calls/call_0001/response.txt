**Summary: Key Concepts for Migrating CUDA C++ to SYCL 2020 (Intel GPUs, icpx)**

**Memory Model & Unified Shared Memory (USM):**
- SYCL and CUDA have similar weakly-ordered memory models.
- SYCL USM replaces CUDA’s malloc/cudaMalloc/cudaMallocHost with `malloc_device`, `malloc_shared`, and `malloc_host` (all require a SYCL queue for device association).
    - `malloc_device`: allocates memory only accessible from the device.
    - `malloc_shared`: allocates memory accessible from both host and device.
    - `malloc_host`: allocates host memory usable from both host and device (optimized for transfers).
- USM pointers are ordinary C++ pointers, simplifying migration from CUDA pointer usage.
- SYCL buffers/accessors provide an alternative managed-memory model but are less CUDA-like.

**Queue and Device Setup:**
- SYCL uses `queue` objects for kernel submission, whereas CUDA uses streams.
- SYCL queues are out-of-order by default, but `property::queue::in_order()` mimics CUDA’s in-order streams.
- Device selection can be explicit or based on default/device selectors. Use `q.get_device()` to obtain the running device.
- SYCL contexts manage device and memory state; most simple programs can ignore explicit context management.

**Kernel Dispatch:**
- SYCL submits kernels with `q.submit()` or directly with `q.parallel_for(...)`. The kernel is ordinarily a C++ lambda function.
- CUDA uses the __global__ qualifier and <<<grid, block>>> launch syntax; SYCL is standard C++ without language extensions.
- Inside a SYCL kernel, information about the work-item (thread/block) is passed via the `item` or `nd_item` argument; CUDA uses built-in variables (`threadIdx`, `blockIdx`).

**ND-Range and Thread Indexing:**
- SYCL uses `nd_range` to define total parallel item count and work-group size. CUDA uses grid/block dimensions.
- Multidimensional SYCL ranges correspond to CUDA grids/blocks but with a different stride: in SYCL, the last dimension is the fastest-moving (contiguous), opposite to CUDA’s first dimension (“x”).
- SYCL work-item index: `item.get_global_id(dim)`, local id: `item.get_local_id(dim)`, group id: `item.get_group(dim)`.
    - For migrations, map CUDA `threadIdx.x` to SYCL `item.get_local_id(highest_dim)` (not 0).
- `item.get_global_linear_id()` is equivalent to CUDA’s linearized thread index calculation.

**Local/Shared Memory:**
- CUDA’s `__shared__` memory variables are mapped to SYCL `local_accessor` objects (created and passed into kernels from the queue submit handler).
- Local memory is scoped to each work-group and used for intra-group communication.
- Kernel signature changes: you must pass the accessor or pointer to local memory explicitly into the kernel lambda/functor, unlike CUDA’s global `__shared__`.

**Synchronization (Barriers):**
- CUDA: `__syncthreads()`, `__syncwarp()`, or `cooperative_groups`.
- SYCL: `group_barrier(item.get_group())` or `group_barrier(item.get_sub_group())`.
    - SYCL barriers can specify fence scope (e.g., `memory_scope::device`), but usually local is sufficient.
    - In SYCL, **all work-items in the group must reach the barrier**; early exits (e.g., from inside `if` statements) can deadlock, unlike CUDA.

**Atomics:**
- SYCL atomics use `atomic_ref` (based on C++20), e.g., `atomic_ref<T, memory_order, memory_scope>`.
- For CUDA's device-scoped atomics (`atomicAdd` etc.), use SYCL `atomic_ref` with `memory_order::relaxed` and `memory_scope::device`.
- Not all SYCL devices support all atomic types and scopes—query device features as needed.

**Common Migration Pitfalls:**
- Dimension ordering: transposition may be required for multidimensional data (SYCL’s last dimension matches CUDA’s x).
- Early exits inside kernels: SYCL barriers require all work-items to reach the barrier, unlike CUDA’s more forgiving behavior.
- Kernel arguments: SYCL passes thread identification via item/nd_item; migrate CUDA kernels to accept this object.
- Device queries and error checking: SYCL uses exceptions rather than error codes. Error handling must be rewritten.
- Features not yet in SYCL: device-side global variables, flexible cooperative group types, explicit matrix multiply hardware access (like CUDA WMMA) may require workarounds or vendor extensions.
- Mixing SYCL objects from different contexts: avoid, as this can cause inefficiency or undefined behavior.
- Not all CUDA functionality has direct SYCL equivalents; manual tweaking may be needed after tool migration.

**Migration Tools:**
- Tools like dpct (DPC++ Compatibility Tool) or SYCLomatic can automate most syntactic migration. Manual review is required for error handling, context, and advanced CUDA features.

**Summary:**  
Migrating CUDA to SYCL for Intel GPUs is typically straightforward due to similar parallel and memory models. Take care with dimension ordering, kernel signature changes, local/shared memory, synchronization, atomics, and device selection. Use USM for memory allocation, `queue` for kernel dispatch, and adjust barriers and atomics for SYCL’s stricter semantic requirements. Automated migration tools aid the process, but careful hand-tweaking is needed for robustness and performance.
