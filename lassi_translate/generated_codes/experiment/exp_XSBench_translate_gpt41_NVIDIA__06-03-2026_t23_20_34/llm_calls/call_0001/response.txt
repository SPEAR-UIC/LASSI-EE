**Summary: Migrating CUDA C++ to SYCL 2020 for Intel GPUs**

**Memory Model and USM**
- In SYCL, Unified Shared Memory (USM) modes allow memory allocation for host, device, or shared access, similar to CUDA's malloc/mallocHost. Functions include `sycl::malloc_device`, `malloc_host`, and `malloc_shared`, all requiring a queue argument.
- SYCL’s weakly-ordered memory model matches CUDA’s. Synchronization and atomics have similar semantics, but be aware of subtle differences in default memory order and scope.

**Queue and Device Setup**
- SYCL uses queues (often out-of-order, can be set in-order with `property::queue::in_order`), whereas CUDA uses streams (always in-order).
- Device selection is explicit in SYCL; use device selectors or query device properties to target Intel GPUs.
- The SYCL context represents the execution environment and tracks device state—a concept mostly hidden from CUDA programmers but relevant when mixing multiple devices or contexts.

**Kernel Dispatch**
- SYCL kernels are launched via `q.submit()` or `q.parallel_for()` (for simple cases).
- Use standard C++ lambdas to define kernels—no need for CUDA syntax extensions.
- Kernel arguments usually include an item or nd_item, which provide access to parallel index space info.

**ND-Range and Thread Indexing**
- SYCL’s `nd_range` defines the global and local size of the execution grid, analogous to CUDA’s grid/block dimensions. 
- `item.get_global_id(dim)` and `item.get_local_id(dim)` replace CUDA’s `threadIdx`, `blockIdx`; note the highest SYCL dimension maps to CUDA's x, because SYCL's last dimension is the contiguous/fastest-moving one.
- Sub-group in SYCL is equivalent to CUDA's warp.

**Local/Shared Memory**
- CUDA’s `__shared__` memory is mapped to SYCL’s `local_accessor`, which must be passed into kernels and defined at kernel launch.
- Local memory is allocated per work-group, just as shared memory in CUDA blocks.

**Synchronization**
- SYCL provides `group_barrier(group)` and sub-group barriers for in-kernel synchronization, much like CUDA's `__syncthreads()` and `__syncwarp()`.
- All work-items must reach the barrier; conditional barriers (early exit) can cause deadlock in SYCL, whereas CUDA implicitly handles non-exited threads.

**Atomics**
- SYCL uses `atomic_ref`, patterned after C++20’s `std::atomic_ref`, to perform atomic operations. Specify memory order (`memory_order::relaxed`) and scope (`memory_scope::device`) for CUDA-like semantics.
- Not all devices may support all atomic types or scopes; always check device capabilities if portability is a concern.

**Common Pitfalls**
- SYCL’s dimension ordering is reversed relative to CUDA—transpose index calculations when converting multidimensional kernels.
- Conditional barriers and early exits can deadlock SYCL kernels.
- SYCL requires explicit passing of local/shared memory as kernel arguments; CUDA’s __shared__ memory is implicit.
- Error handling differs: SYCL throws exceptions, CUDA returns error codes. Adjust host-side error handling.
- SYCL omits some CUDA features: device global variables, flexible cooperative groups (eg. tiled_partition), low-level WMMA/tensor core access; vendor extensions may exist, but not portable.
- Some atomics, group algorithms, and kernel properties may not be available or behave differently on Intel vs. NVIDIA hardware.
- Context mixups: avoid using SYCL objects from different contexts.

**Tooling**
- Tools like dpct/SYCLomatic automate much of the migration, but manual cleanup is typically needed for dimension ordering, shared memory, indexing, and error handling patterns.

**Best Practices**
- Prefer SYCL-standard APIs for maintainability and portability.
- Check device capabilities and restrictions if targeting non-NVIDIA hardware.
- Review and refactor migrated code for kernel correctness (especially synchronization and memory allocation), dimension ordering, and host/device setup.

**Conclusion**
Migrating CUDA to SYCL is conceptually straightforward due to similar execution/memory models, though differences in terminology, syntax, and certain behaviors require careful handling. SYCL enables code portability across device vendors, but always review migrated kernels for nuances in thread indexing, synchronization, and memory management, especially when targeting Intel GPUs and compiling with icpx.
