### Summary: Key Concepts for Migrating CUDA Code to SYCL 2020 Targeting Intel GPUs

#### Memory Model and Unified Shared Memory (USM)
- **Unified Shared Memory (USM):** SYCL uses `malloc_device`, `malloc_shared`, and `malloc_host` for dynamic memory allocation similar to `cudaMalloc` and `cudaMallocHost`. USM provides unified allocation across the host and device, simplifying memory management for Intel GPUs.
- **Local Memory:** CUDA's `__shared__` variables are replaced by SYCL's `local_accessor`, which enables efficient local memory collaboration within workgroups.
- SYCL emphasizes a C++ memory model and `atomic_ref` for atomic operations, providing configurability for memory order and scope.

#### Queue and Device Setup
- SYCL queues manage kernel execution; they default to **out-of-order execution**, unlike CUDA streams which are strictly **in-order**. Adding the `property::queue::in_order()` ensures CUDA-like behavior.
- Device selection in SYCL is explicit through device selectors or queries, while CUDA defaults to device zero. Device properties like name and capabilities can be queried using `get_device()`.

#### Kernel Dispatch (`q.submit` and `parallel_for`)
- Both models use kernels for device execution. SYCL uses **standard C++ lambda functions** within the `parallel_for` method, whereas CUDA uses specialized syntax (`<<< >>>`) and annotations (`__global__`).
- SYCL kernels are launched via `q.submit` using an `nd_range` argument or simpler range-based constructs.

#### ND-Range and Thread Indexing
- **Mapping Dimensions:** SYCL uses C++ array alignment; the **last dimension is contiguous** (e.g., fastest moving), whereas in CUDA the **first dimension is contiguous**. This transposition must be accounted for when migrating multi-dimensional kernels.
- SYCL replaces CUDA built-in thread variables (`blockIdx`, `threadIdx`) with methods from `nd_item`. `get_global_id`, `get_local_id`, and `get_group_id` are used similarly to CUDA’s indexing constructs.

#### Synchronization (`group_barrier`)
- SYCL's `group_barrier(fence_scope)` synchronizes all work-items in a group, akin to CUDA's `__syncthreads()` for thread blocks. It enables memory consistency scoped to local memory or broader.
- Early exits around barriers (`group_barrier`) can cause **deadlocks** on SYCL devices, unlike CUDA's handling of exited threads. Kernels may need restructuring to avoid such pitfalls.

#### Atomics
- SYCL offers `atomic_ref` for atomic operations, which must explicitly specify memory order (`memory_order::relaxed`) and scope (`memory_scope::device`), compared to CUDA’s `atomicAdd` functions. Default behaviors differ (SYCL requires more explicit scope/type definitions).
- Flexibility in atomic scopes leads to potential device-specific support issues, so device capabilities should always be queried for portability.

#### Common Pitfalls When Migrating from CUDA
1. **Thread Indexing Differences:** Adjust multi-dimensional indexing due to transposed dimensions.
2. **Synchronization Deadlocks:** Ensure all work-items reach `group_barrier`; early exits near barriers can cause issues.
3. **Atomics Defaults:** SYCL atomics need explicit configuration (default CUDA atomics can assume relaxed order/device-scope).
4. **Independent Thread Scheduling:** CUDA’s independent thread scheduling can lead to device-dependent behavior in migrated SYCL kernels.
5. **Global Variables in CUDA:** SYCL lacks device-side global variables (`__device__` or `__shared__`), requiring explicit memory accessor usage.
6. **Error Checking:** CUDA’s error codes do not translate directly, as SYCL uses exceptions for synchronized and asynchronous errors.

#### Porting Tools and Techniques (dpct/SYCLomatic)
- **Automated Code Migration:** Tools like dpct and SYCLomatic assist in converting CUDA code to SYCL. They automate translation of CUDA-specific constructs (e.g., `__global__`, `__shared__`, indexing) to SYCL syntax.
- **Generated Code Quality:** dpct produces readable and functionally correct code, but manual review and editing are often necessary for complex applications.
- Tools handle device-specific queries, memory allocation, and kernel invocation but may require developer intervention for error handling and proprietary features.

#### Differences in Features
- CUDA features such as **cooperative groups** and access to **matrix multiplication hardware** (tensor cores) are evolving in SYCL but not fully standardized yet.
- SYCL has broader multi-platform support via an open standard, while CUDA is specific to NVIDIA GPUs.

#### Closing Advice
Migrating from CUDA to SYCL enables portability across GPU vendors, including Intel, and aligns with modern C++ standards. Automated tools streamline migration, but understanding subtle execution model and memory differences ensures robust, efficient migrated code. For maximum portability, query device capabilities and minimize platform-specific assumptions.
