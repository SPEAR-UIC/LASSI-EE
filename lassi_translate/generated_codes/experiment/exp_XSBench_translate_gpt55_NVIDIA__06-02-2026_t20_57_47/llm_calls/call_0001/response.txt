## 1. Overall purpose and algorithm

### Program purpose
This is a CUDA implementation of an XSBench-style continuous-energy Monte Carlo macroscopic cross-section lookup benchmark. It generates or reads nuclear cross-section data, transfers the relevant simulation data structures to the GPU, and performs many independent event-based cross-section lookups in parallel. The final result is a verification checksum derived from the lookup results.

The code supports only the event-based simulation path in CUDA. If the history-based method is selected, the program exits with an error.

### High-level workflow

1. Parse command-line options into an `Inputs` structure.
2. Initialize simulation data on the host, or read it from a binary file.
3. Build one of three lookup acceleration structures:
   - nuclide-only grid,
   - unionized energy grid,
   - hash grid.
4. Allocate corresponding device memory and copy host data to the GPU.
5. Select and run one of several event-based GPU kernel variants.
6. Reduce per-lookup verification values into a scalar checksum.
7. Free device memory.
8. Print timing and verification results.

### Physics / lookup algorithm

For each lookup:

1. A deterministic LCG random number generator is advanced to the lookup-specific state.
2. A sampled particle energy is generated.
3. A material is selected using a hard-coded probabilistic distribution.
4. A macroscopic cross-section vector of length 5 is computed for that material and energy.
5. The macroscopic cross section is computed by iterating over all nuclides in the material:
   - determine the relevant nuclide grid interval for the sampled energy,
   - linearly interpolate microscopic cross-section values between neighboring grid points,
   - multiply by the nuclide concentration,
   - accumulate into the 5-channel macroscopic vector.
6. The maximum channel index is used to produce a small verification value for that lookup.
7. All verification values are reduced on the device using Thrust.

The five cross-section channels are:

1. total,
2. elastic,
3. absorption,
4. fission,
5. nu-fission.

### Supported grid lookup modes

#### `NUCLIDE`
Each microscopic lookup performs a binary search directly in the selected nuclide’s energy grid.

#### `UNIONIZED`
A single binary search is performed in the unionized energy grid for the particle energy. The resulting unionized-grid index is then used to look up precomputed per-nuclide lower indices in `index_grid`.

#### `HASH`
The sampled energy is mapped to a hash bin. The hash bin provides a restricted search interval in the nuclide grid, and a bounded binary search is performed within that interval.

## 2. CUDA-specific constructs and their roles

### CUDA headers and runtime API

The code includes CUDA headers and uses CUDA runtime APIs directly:

- `#include <cuda.h>`
- `cudaMalloc`
- `cudaMemcpy`
- `cudaFree`
- `cudaDeviceSynchronize`
- `cudaPeekAtLastError`
- `cudaGetDevice`
- `cudaGetDeviceProperties`
- `cudaGetErrorString`

The program uses explicit device memory management rather than CUDA unified memory.

### CUDA error handling

The macro:

- `gpuErrchk(...)`

wraps CUDA runtime calls and invokes:

- `gpuAssert(cudaError_t code, const char *file, int line, bool abort=true)`

If a CUDA call fails, the code prints the CUDA error string, file, and line number, then exits.

### Device memory allocation: `cudaMalloc`

Device allocations occur primarily in:

- `move_simulation_data_to_device`
- each optimized simulation driver that needs sampled energy/material arrays.

Device allocations include:

- `GSD.num_nucs`
- `GSD.concs`
- `GSD.mats`
- `GSD.unionized_energy_array`
- `GSD.index_grid`
- `GSD.nuclide_grid`
- `GSD.verification`
- optionally `GSD.p_energy_samples`
- optionally `GSD.mat_samples`

The `SimulationData` structure itself is not allocated as a device object. Instead, a host-side shallow copy of `SimulationData` is made, its pointer fields are replaced with device pointers, and that structure is passed by value to kernels.

### Host-to-device copies: `cudaMemcpy`

`move_simulation_data_to_device` copies initialized host arrays to device arrays using `cudaMemcpyHostToDevice`.

Copied arrays include:

- number of nuclides per material,
- material concentrations,
- material-to-nuclide mapping,
- unionized energy grid,
- index grid,
- nuclide grid.

The verification array is allocated on the device but is not initialized by host-to-device copy.

### Device memory release: `cudaFree`

`release_device_memory` frees several device allocations:

- `GSD.num_nucs`
- `GSD.concs`
- `GSD.mats`
- `GSD.unionized_energy_array`
- `GSD.nuclide_grid`
- `GSD.verification`

Important preservation note: `GSD.index_grid` is allocated in `move_simulation_data_to_device` but is not freed in `release_device_memory`. The optimized temporary arrays `GSD.p_energy_samples` and `GSD.mat_samples` are also not freed by this function. This behavior should be noted and preserved unless intentionally correcting memory management.

### CUDA kernels: `__global__`

The program defines multiple CUDA device kernels:

- `xs_lookup_kernel_baseline`
- `sampling_kernel`
- `xs_lookup_kernel_optimization_1`
- `xs_lookup_kernel_optimization_2`
- `xs_lookup_kernel_optimization_3`
- `xs_lookup_kernel_optimization_4`
- `xs_lookup_kernel_optimization_5`

These are launched using CUDA triple-chevron syntax from host driver functions.

### Device functions: `__device__`

The following functions execute only on the GPU:

- `calculate_micro_xs`
- `calculate_macro_xs`
- `grid_search`
- `pick_mat`
- `fast_forward_LCG`

These functions are called from kernels or other device functions.

### Host/device functions: `__host__ __device__`

The following functions are callable from both host and device code:

- `grid_search_nuclide`
- `LCG_random_double`

They are used during host-side initialization and device-side lookup/sampling.

### Restrict-qualified device pointers

Several device functions use `__restrict__` pointer parameters, for example:

- `double * __restrict__ egrid`
- `int * __restrict__ index_data`
- `NuclideGridPoint * __restrict__ nuclide_grids`

These annotations indicate non-aliasing assumptions to the compiler and may affect optimization.

### Thrust device algorithms

The code uses Thrust algorithms with `thrust::device` execution policy:

- `thrust::reduce`
- `thrust::count`
- `thrust::sort_by_key`
- `thrust::partition`

Roles:

- `thrust::reduce` reduces the device verification array into a scalar checksum.
- `thrust::count` counts how many sampled lookups belong to each material or to fuel material.
- `thrust::sort_by_key` sorts sampled lookups by material, and in optimization 6 also sorts by energy within material groups.
- `thrust::partition` is used in optimization 5 to partition fuel and non-fuel lookups.

These Thrust calls launch device work internally and are CUDA-specific in this implementation.

### CUDA synchronization

The program uses:

- `cudaDeviceSynchronize`
- `cudaPeekAtLastError`

after kernel launches and Thrust operations. The synchronization ensures kernels and device algorithms complete before proceeding and before timing/reduction steps continue.

### CUDA device query

`print_inputs` uses:

- `cudaGetDevice`
- `cudaGetDeviceProperties`

to print the active CUDA device name.

### Shared memory

No explicit `__shared__` memory is used.

### Atomics

No CUDA atomic operations are used.

Although comments in `calculate_macro_xs` mention that atomics would be needed if the per-nuclide loop were parallelized across threads, this implementation performs the per-material nuclide accumulation privately within a single thread, so atomics are unnecessary.

### Streams and events

No explicit CUDA streams or CUDA events are used. All kernels and Thrust operations execute in the default stream semantics implied by the code.

### Constant memory / texture memory

No CUDA constant memory, texture memory, or surface memory is used.

## 3. GPU kernel structure and thread/block organization

### General indexing pattern

All kernels use a one-dimensional grid and one-dimensional block layout.

The global thread index is computed as:

- `i = blockIdx.x * blockDim.x + threadIdx.x`

Each thread generally handles one lookup or one sampled lookup entry.

Most kernels immediately return if the thread index is outside the active range:

- `if (i >= in.lookups) return;`
- or, for segmented kernels, `if (i >= n_lookups) return;`

### Baseline kernel

#### Kernel
`xs_lookup_kernel_baseline`

#### Launch configuration
Launched by `run_event_based_simulation_baseline`.

- threads per block: `256`
- blocks: `ceil((double) in.lookups / (double) nthreads)`

#### Work per thread
Each thread performs one complete lookup:

1. Fast-forwards the random seed by `2*i`.
2. Samples particle energy.
3. Samples material.
4. Computes macroscopic cross section.
5. Finds the maximum cross-section channel.
6. Writes `max_idx + 1` to `GSD.verification[i]`.

This kernel has potentially high warp divergence because different materials contain very different numbers of nuclides.

### Sampling kernel

#### Kernel
`sampling_kernel`

#### Launch configuration
Used by optimized variants.

- threads per block: `32`
- blocks: `ceil((double) in.lookups / 32.0)`

#### Work per thread
Each thread performs only the random sampling step:

1. Fast-forwards the LCG seed by `2*i`.
2. Generates sampled energy.
3. Generates sampled material.
4. Stores:
   - `GSD.p_energy_samples[i]`
   - `GSD.mat_samples[i]`

This separates sampling from cross-section lookup.

### Optimization 1 lookup kernel

#### Kernel
`xs_lookup_kernel_optimization_1`

#### Launch configuration
Launched after `sampling_kernel`.

- threads per block: `32`
- blocks: `ceil((double) in.lookups / 32.0)`

#### Work per thread
Each thread reads its sampled energy and material from device arrays and performs one full cross-section lookup.

This is equivalent in lookup work to the baseline but splits sampling and lookup into separate kernels.

### Optimization 2 material-specific lookup kernel

#### Kernel
`xs_lookup_kernel_optimization_2`

#### Launch configuration
Launched 12 times, once for each material ID `m`.

- threads per block: `32`
- blocks: `ceil((double) in.lookups / 32.0)` for every material launch

#### Work per thread
Each thread checks whether its sampled material matches the kernel’s material argument:

- if `mat != m`, return;
- otherwise perform the lookup.

This reduces within-kernel material heterogeneity for active threads, but every material kernel scans the full lookup array.

### Optimization 3 fuel / non-fuel lookup kernel

#### Kernel
`xs_lookup_kernel_optimization_3`

#### Launch configuration
Launched twice by `run_event_based_simulation_optimization_3`.

- threads per block: `32`
- blocks: `ceil((double) in.lookups / 32.0)`

Arguments used:

- first launch: `is_fuel = 0`
- second launch: `is_fuel = 1`

#### Work per thread
The kernel checks whether the sampled material belongs to the requested class:

- `is_fuel == 1` processes material `0`;
- `is_fuel == 0` processes all materials other than `0`.

The condition is:

- fuel path: `is_fuel == 1 && mat == 0`
- non-fuel path: `is_fuel == 0 && mat != 0`

This reduces the number of lookup kernel launches compared with optimization 2.

### Optimization 4 sorted material-specific lookup kernel

#### Kernel
`xs_lookup_kernel_optimization_4`

#### Host-side preprocessing
The driver:

1. Runs `sampling_kernel`.
2. Counts the number of lookups for each material using `thrust::count`.
3. Sorts by material using `thrust::sort_by_key`, with material IDs as keys and sampled energies as values.
4. Launches one segmented kernel per material.

#### Launch configuration
For each material `m`:

- threads per block: `32`
- blocks: `ceil((double) n_lookups_per_material[m] / (double) nthreads)`
- kernel arguments include:
  - material ID `m`,
  - segment length `n_lookups_per_material[m]`,
  - segment offset `offset`.

#### Work per thread
Each thread indexes within the material segment:

1. Compute local `i`.
2. Return if `i >= n_lookups`.
3. Add `offset` to get the global sorted-array index.
4. Optionally verify `mat == m`.
5. Perform lookup.
6. Write verification to `GSD.verification[i]` at the sorted position.

The verification reduction is order-insensitive, so sorting the samples does not affect the final checksum except through any floating-point or logic changes in preserved behavior.

### Optimization 5 fuel / non-fuel partitioned lookup kernel

#### Kernel
`xs_lookup_kernel_optimization_5`

#### Host-side preprocessing
The driver:

1. Runs `sampling_kernel`.
2. Counts fuel lookups using `thrust::count`.
3. Applies `thrust::partition`.
4. Launches two segmented kernels:
   - one for fuel segment,
   - one for non-fuel segment.

#### Launch configuration
First launch:

- segment length: `n_fuel_lookups`
- offset: `0`

Second launch:

- segment length: `in.lookups - n_fuel_lookups`
- offset: `n_fuel_lookups`

Threads per block are `32`.

#### Work per thread
Each thread processes one entry in its segment after adding the segment offset. Unlike optimization 3, this kernel does not test whether the material is fuel or non-fuel; it trusts the partitioning.

### Optimization 6 material and energy sorted lookup

#### Kernel reuse
Optimization 6 reuses `xs_lookup_kernel_optimization_4`.

#### Host-side preprocessing
The driver:

1. Runs `sampling_kernel`.
2. Counts lookups per material with `thrust::count`.
3. Sorts all lookups by material using `thrust::sort_by_key`.
4. For each material segment, sorts that segment by sampled energy using another `thrust::sort_by_key`.
5. Launches material-specific segmented kernels as in optimization 4.

This improves spatial locality and reduces divergence by grouping both material and energy.

## 5. Asymmetric, unusual, or potentially incorrect bounds, comparisons, and offsets that must be preserved verbatim

The following constructs appear asymmetric, non-obvious, or potentially erroneous. They should be treated as intentional benchmark behavior and MUST be preserved verbatim in the translation unless the goal is explicitly to fix the original program.

### `pick_mat` cumulative distribution loop excludes `dist[0]`

In `pick_mat`, the material-selection loop computes the cumulative probability as:

- outer loop: `for (int i = 0; i < 12; i++)`
- inner loop: `for (int j = i; j > 0; j--)`
- accumulation: `running += dist[j]`

This loop condition is `j > 0`, not `j >= 0`.

Consequences:

- For `i == 0`, `running` remains `0`, so material `0` is never selected in that iteration.
- The cumulative sum excludes `dist[0]` for all `i`.
- Material `0` is selected only by the final fallback `return 0`.

This is asymmetric and likely surprising, but it MUST be preserved exactly.

### Binary search comparison uses `>` rather than `>=`

Both binary search routines use:

- `if (A[examinationPoint] > quarry)`
- or `if (A[examinationPoint].energy > quarry)`

They do not use `>=`.

This means exact equality moves the lower bound upward rather than the upper bound downward. This affects returned lower indices for exact matches and MUST be preserved.

### Binary search loop condition is `while (length > 1)`

Both `grid_search` and `grid_search_nuclide` terminate when the interval length is not greater than 1.

This lower-index return convention is central to the interpolation logic and MUST be preserved.

### `calculate_micro_xs` edge handling for final grid point

In several paths, if the located index is the final grid point, the code backs up by one:

- if index equals `n_gridpoints - 1`, use index `idx - 1` or equivalent;
- otherwise use the located index directly.

This is used to ensure `high = low + 1` remains valid. The exact conditional structure and offsets MUST be preserved.

### Hash-grid lower-bound edge handling uses absolute endpoints

In the hash-grid path of `calculate_micro_xs`, after computing `u_low` and `u_high`, the code checks:

- if `p_energy <= e_low`, then `lower = 0`;
- else if `p_energy >= e_high`, then `lower = n_gridpoints - 1`;
- else perform bounded `grid_search_nuclide`.

The assignment to `0` and `n_gridpoints - 1` ignores `u_low` and `u_high` in these edge cases. This appears potentially asymmetric but MUST be preserved exactly.

### Hash-grid bin index uses implicit truncation

In `calculate_macro_xs`, for hash-grid mode:

- `du = 1.0 / hash_bins`
- `idx = p_energy / du`

The floating-point result is assigned to integer-like `idx`, relying on truncation. This behavior MUST be preserved.

### Optimization 3 launch argument order and condition

`run_event_based_simulation_optimization_3` launches:

1. `xs_lookup_kernel_optimization_3(..., 0)`
2. `xs_lookup_kernel_optimization_3(..., 1)`

Inside the kernel:

- `is_fuel == 1` processes material `0`;
- `is_fuel == 0` processes materials not equal to `0`.

Thus the first launch processes non-fuel lookups and the second launch processes fuel lookups. This is slightly counterintuitive relative to some comments, but the ordering and condition MUST be preserved.

### Optimization 4 and 6 segmented offset indexing

In `xs_lookup_kernel_optimization_4`, the local thread index is checked first:

- return if `i >= n_lookups`

Then the segment offset is added:

- `i += offset`

The verification value is written to the sorted global position:

- `GSD.verification[i] = max_idx + 1`

This offset order MUST be preserved.

### Optimization 5 segmented offset indexing

In `xs_lookup_kernel_optimization_5`, the same pattern is used:

1. compute local `i`;
2. return if `i >= n_lookups`;
3. add `offset`;
4. process `GSD.p_energy_samples[i]` and `GSD.mat_samples[i]`;
5. write `GSD.verification[i]`.

This MUST be preserved.

### Potential zero-block launches in segmented optimizations

In optimizations 4, 5, and 6, block counts are computed from per-segment lookup counts:

- `ceil((double) n_lookups_per_material[m] / (double) nthreads)`
- `ceil((double) n_fuel_lookups / (double) nthreads)`
- `ceil((double) (in.lookups - n_fuel_lookups) / (double) nthreads)`

If a segment count is zero, this can produce a zero-block launch. CUDA generally treats launching a kernel with zero blocks as invalid. The original behavior should be preserved unless deliberately adding guards.

### Optimization 5 `thrust::partition` usage is unusual

Optimization 5 calls `thrust::partition` with:

- `GSD.mat_samples` as the partitioned range,
- `GSD.p_energy_samples` as the stencil-like accompanying iterator,
- predicate `is_mat_fuel`, which tests `a == 0`.

This is unusual because the predicate name and type imply testing material IDs, but the call form may apply the predicate to the stencil iterator depending on the Thrust overload. It also does not obviously reorder sampled energies in lockstep with material IDs in the way `sort_by_key` does.

This behavior is potentially incorrect or at least non-obvious, but it MUST be preserved verbatim in translation.

### Material selection fallback returns material `0`

After the loop in `pick_mat`, the function returns `0`.

Because the cumulative loop excludes `dist[0]`, this fallback is part of the effective material distribution. It MUST be preserved.

### CLI behavior for event-based default lookup count is order-dependent

When `-m event` is parsed, the code multiplies default lookups by default particles only if both `default_lookups` and `default_particles` are still true. Therefore command-line option order can affect the final values when `-m`, `-l`, and `-p` are combined.

This is not CUDA-specific but is part of the observable program behavior and should be preserved.

### `XXL` gridpoint calculation uses floating-point multiplication assigned to integer type

For `-s XXL`, when `user_g == 0`, the code uses:

- `input.n_gridpoints = 238847 * 2.1`

The right-hand side is floating-point and is assigned to a `long`, causing truncation. This behavior MUST be preserved.

### Unionized-grid initialization assumes access to grid point `+1`

During unionized-grid initialization, the code initializes:

- `energy_high[i] = SD.nuclide_grid[i * in.n_gridpoints + 1].energy`

This assumes `in.n_gridpoints >= 2`, even though validation only rejects values less than 1. The indexing behavior MUST be preserved.

### Device memory release omits some allocations

As noted above, `release_device_memory` does not free:

- `GSD.index_grid`
- `GSD.p_energy_samples`
- `GSD.mat_samples`

This is likely an oversight, but it is original behavior and should be preserved unless the translation is also intended to fix memory leaks.
