## Key SYCL 2020 concepts for translating CUDA C++ to SYCL targeting Intel GPUs with `icpx`

### 1. Overall CUDA-to-SYCL terminology mapping

CUDA and SYCL use very similar data-parallel execution models, but different terminology:

- CUDA kernel → SYCL kernel
- CUDA thread → SYCL work-item
- CUDA block → SYCL work-group
- CUDA grid → SYCL range or ND-range
- CUDA warp → SYCL sub-group
- CUDA shared memory → SYCL local memory
- CUDA stream → SYCL queue
- `__syncthreads()` → `sycl::group_barrier()`
- CUDA built-in indices such as `threadIdx`, `blockIdx`, `blockDim`, `gridDim` → SYCL `nd_item` queries such as `get_local_id`, `get_group`, `get_local_range`, `get_global_id`

SYCL is standard C++: kernels are usually lambdas passed to `parallel_for`, rather than functions marked with CUDA qualifiers such as `__global__`.

---

### 2. Queue and device setup

In CUDA, device 0 and the default stream are often used implicitly. In SYCL, work is submitted to a `sycl::queue`, which is associated with a device and context.

A typical Intel GPU queue is created as:

```cpp
sycl::queue q{sycl::gpu_selector_v};
```

or, for CUDA-like ordering semantics:

```cpp
sycl::queue q{
    sycl::gpu_selector_v,
    sycl::property::queue::in_order{}
};
```

Important difference:

- CUDA streams are in-order.
- SYCL queues are out-of-order by default.
- To mimic a single CUDA stream, use an in-order SYCL queue.
- For explicit dependency control, use events, `depends_on`, or in-order queues.

With Intel oneAPI `icpx`, typical compilation is:

```bash
icpx -fsycl code.cpp -o app
```

Device selection can also be influenced at runtime, for example:

```bash
ONEAPI_DEVICE_SELECTOR=level_zero:gpu ./app
```

For Intel GPUs, the Level Zero backend is typically used.

---

### 3. Memory model and USM

SYCL supports buffers/accessors and Unified Shared Memory, but CUDA migrations usually map most naturally to USM.

Common USM allocation types:

#### `malloc_device`

```cpp
int* d_ptr = sycl::malloc_device<int>(N, q);
```

- Allocates memory physically accessible by the device.
- Host cannot directly dereference it.
- Similar to `cudaMalloc`.
- Use `q.memcpy`, kernels, or explicit copies to move data.

CUDA equivalent:

```cpp
cudaMalloc(&ptr, N * sizeof(int));
```

#### `malloc_shared`

```cpp
int* ptr = sycl::malloc_shared<int>(N, q);
```

- Allocates memory accessible from both host and device.
- Similar in spirit to CUDA Unified Memory from `cudaMallocManaged`.
- Convenient for migration, but performance may depend on migration, page faults, and placement.
- On Intel GPUs, shared USM can be very convenient, but explicit data movement or device USM may still perform better for bandwidth-sensitive code.

#### `malloc_host`

```cpp
int* h_ptr = sycl::malloc_host<int>(N, q);
```

- Allocates host memory that is accessible to the SYCL runtime and may be optimized for transfers.
- Comparable to pinned/page-locked host memory such as `cudaMallocHost`.
- Device kernels generally should not assume this behaves like high-performance device memory.

USM memory is freed with:

```cpp
sycl::free(ptr, q);
```

Memory operations are enqueued:

```cpp
q.memcpy(d_ptr, h_ptr, N * sizeof(int));
q.fill(d_ptr, 0, N);
q.wait();
```

Like CUDA, SYCL has a weakly ordered memory model. Ordering between memory operations and kernels must be established through queue ordering, events, dependencies, or explicit waits.

### 4. Kernel dispatch

CUDA launches kernels with special syntax:

```cpp
kernel<<<numBlocks, threadsPerBlock>>>(args);
```

SYCL uses standard C++ queue submission and `parallel_for`.

Simple 1D kernel:

```cpp
q.parallel_for(sycl::range<1>{N}, [=](sycl::id<1> i) {
    ptr[i] = i;
}).wait();
```

For CUDA-like block/thread structure, use `nd_range`:

```cpp
q.parallel_for(
    sycl::nd_range<1>{sycl::range<1>{global_size},
                      sycl::range<1>{local_size}},
    [=](sycl::nd_item<1> item) {
        size_t gid = item.get_global_id(0);
        size_t lid = item.get_local_id(0);
        size_t group = item.get_group(0);
    });
```

More explicit form using `submit`:

```cpp
q.submit([&](sycl::handler& h) {
    h.parallel_for(
        sycl::nd_range<1>{global_size, local_size},
        [=](sycl::nd_item<1> item) {
            // kernel body
        });
});
```

Use `q.wait()` or `q.wait_and_throw()` to synchronize with the host. `wait_and_throw()` is useful because SYCL reports asynchronous device errors through exceptions.

### 5. ND-range and thread indexing

CUDA index calculation:

```cpp
int gid = blockIdx.x * blockDim.x + threadIdx.x;
int lid = threadIdx.x;
int bid = blockIdx.x;
```

SYCL equivalent:

```cpp
size_t gid = item.get_global_id(0);
size_t lid = item.get_local_id(0);
size_t bid = item.get_group(0);
size_t lsize = item.get_local_range(0);
```

Manual equivalent:

```cpp
size_t gid = item.get_group(0) * item.get_local_range(0)
           + item.get_local_id(0);
```

For 2D/3D kernels, be careful: SYCL and CUDA use different dimension conventions.

CUDA treats `x` as the fastest-moving, contiguous dimension.

SYCL follows C++ multidimensional indexing convention: the last dimension is the fastest-moving dimension.

Therefore, CUDA:

```cpp
dim3 block(x, y, z);
threadIdx.x
threadIdx.y
threadIdx.z
```

often maps conceptually to SYCL dimensions in reverse order:

```cpp
sycl::range<3>{z, y, x};

item.get_local_id(2); // CUDA threadIdx.x
item.get_local_id(1); // CUDA threadIdx.y
item.get_local_id(0); // CUDA threadIdx.z
```

This dimension-order difference is one of the most common CUDA-to-SYCL migration pitfalls.

### 6. Local/shared memory

CUDA shared memory:

```cpp
__shared__ float tile[256];
```

SYCL local memory is represented with a `local_accessor` declared inside the command group:

```cpp
q.submit([&](sycl::handler& h) {
    sycl::local_accessor<float, 1> tile{
        sycl::range<1>{256}, h};

    h.parallel_for(
        sycl::nd_range<1>{global_size, local_size},
        [=](sycl::nd_item<1> item) {
            size_t lid = item.get_local_id(0);
            tile[lid] = ...;
        });
});
```

Local memory is:

- allocated per work-group,
- shared by work-items in the same work-group,
- not visible across work-groups,
- the SYCL equivalent of CUDA shared memory.

CUDA dynamic shared memory maps to a local accessor whose size is determined at submission time.

### 7. Synchronization

CUDA:

```cpp
__syncthreads();
```

SYCL:

```cpp
sycl::group_barrier(item.get_group());
```

or:

```cpp
item.barrier();
```

For sub-group/warp-level synchronization:

```cpp
sycl::group_barrier(item.get_sub_group());
```

Important pitfall:

- CUDA `__syncthreads()` synchronizes all non-exited threads in a block.
- SYCL `group_barrier()` requires all work-items in the work-group to encounter the barrier unless control flow is uniform.

This CUDA pattern is unsafe in SYCL:

```cpp
if (gid >= N) return;
sycl::group_barrier(item.get_group());
```

because some work-items may return before the barrier, potentially causing deadlock.

Prefer:

```cpp
bool active = gid < N;

sycl::group_barrier(item.get_group());

if (active) {
    // guarded work
}
```

or structure the kernel so all work-items either reach the barrier or uniformly skip it.

### 8. Atomics

Older CUDA atomics:

```cpp
atomicAdd(ptr, value);
```

are generally relaxed, device-scope atomics.

SYCL uses `sycl::atomic_ref`, modeled after C++ atomics:

```cpp
sycl::atomic_ref<
    int,
    sycl::memory_order::relaxed,
    sycl::memory_scope::device,
    sycl::access::address_space::global_space
> aref(*ptr);

aref.fetch_add(value);
```

To closely match common CUDA `atomicAdd` behavior, use:

- `memory_order::relaxed`
- `memory_scope::device`

Use stronger ordering or wider scope only when required, because it can reduce performance.

Be aware that not every device supports every atomic type, operation, or memory scope. For portable SYCL, query device capabilities when necessary.

---

### 9. Sub-groups and warp-level behavior

CUDA programmers often assume warp size is 32. SYCL sub-group size is device-dependent.

On Intel GPUs, sub-group sizes may differ from NVIDIA warp size and may be selectable or queryable. Avoid hard-coding 32 unless the kernel explicitly requires it and the device supports it.

CUDA warp shuffle operations map to SYCL group algorithms, for example:

```cpp
auto sg = item.get_sub_group();
auto y = sycl::permute_group_by_xor(sg, x, mask);
```

But CUDA’s independent thread scheduling and warp-level behavior do not always map exactly to SYCL. Code relying on implicit warp synchronization or NVIDIA-specific scheduling assumptions may need restructuring.

---

### 10. Error handling

CUDA commonly returns error codes:

```cpp
cudaError_t err = cudaDeviceSynchronize();
```

SYCL reports errors through exceptions.

Synchronous errors are thrown directly. Asynchronous kernel errors are typically observed at:

```cpp
q.wait_and_throw();
```

A queue can also be created with an asynchronous exception handler:

```cpp
sycl::queue q{
    sycl::gpu_selector_v,
    [](sycl::exception_list elist) {
        for (auto& e : elist) {
            try {
                std::rethrow_exception(e);
            } catch (const sycl::exception& ex) {
                std::cerr << ex.what() << "\n";
            }
        }
    }
};
```

During migration, replace CUDA error-code checks with SYCL exception handling.

### 11. Common CUDA-to-SYCL migration pitfalls

- Assuming SYCL queues are in-order by default. They are not; use `property::queue::in_order` or explicit dependencies.
- Confusing CUDA and SYCL dimension ordering. CUDA `x` maps to the last SYCL dimension.
- Hard-coding warp size as 32. SYCL sub-group size is device-dependent.
- Using early returns before barriers. SYCL work-group barriers require all work-items in the group to participate.
- Assuming CUDA shared memory globals map directly. Use `local_accessor`.
- Assuming CUDA device globals such as `__device__` variables have direct standard SYCL equivalents. Standard SYCL has more limited support for device global variables.
- Assuming CUDA atomics and SYCL atomics have identical defaults. Specify memory order and scope explicitly.
- Mixing SYCL objects from different contexts. USM allocations, queues, events, and other context-bound objects should be used with the correct context.
- Relying on CUDA-specific cooperative groups, grid-wide synchronization, tensor cores/WMMA, or other vendor-specific features. SYCL has related abstractions, but not always exact standard equivalents.
- Forgetting to wait for asynchronous work before reading results on the host.
- Using `malloc_shared` everywhere for convenience without considering performance. For high-performance Intel GPU code, `malloc_device` plus explicit copies may be better.
- Assuming migrated code from tools such as `dpct` or SYCLomatic is final. Tool output should be reviewed for correctness, idiomatic SYCL usage, and performance.

### 12. Practical migration pattern

A typical CUDA kernel launch:

```cpp
cudaMalloc(&d, N * sizeof(float));
cudaMemcpy(d, h, N * sizeof(float), cudaMemcpyHostToDevice);

kernel<<<numBlocks, blockSize>>>(d, N);

cudaMemcpy(h, d, N * sizeof(float), cudaMemcpyDeviceToHost);
cudaDeviceSynchronize();
```

maps conceptually to SYCL USM code:

```cpp
sycl::queue q{
    sycl::gpu_selector_v,
    sycl::property::queue::in_order{}
};

float* d = sycl::malloc_device<float>(N, q);

q.memcpy(d, h, N * sizeof(float));

q.parallel_for(
    sycl::nd_range<1>{
        sycl::range<1>{numBlocks * blockSize},
        sycl::range<1>{blockSize}},
    [=](sycl::nd_item<1> item) {
        size_t gid = item.get_global_id(0);
        if (gid < N) {
            // kernel body
        }
    });

q.memcpy(h, d, N * sizeof(float));
q.wait_and_throw();

sycl::free(d, q);
```

This is the basic structure for translating CUDA C++ kernels to SYCL 2020 C++ for Intel GPUs with `icpx`.
