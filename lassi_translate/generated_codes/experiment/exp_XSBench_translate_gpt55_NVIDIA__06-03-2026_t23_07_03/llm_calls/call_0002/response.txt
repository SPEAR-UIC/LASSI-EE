## 1. Overall purpose and algorithm

### Program purpose
This is a CUDA implementation of an XSBench-style event-based Monte Carlo cross-section lookup benchmark. It models repeated neutron cross-section lookups over a collection of nuclide energy grids and material compositions. The main profiled workload is the GPU lookup phase, not the CPU initialization phase.

The program:
1. Reads command-line inputs describing benchmark size, lookup count, grid type, and kernel variant.
2. Initializes or reads nuclear data structures on the CPU.
3. Copies simulation data to GPU memory.
4. Runs one of several event-based CUDA lookup kernels.
5. Reduces per-lookup verification values into a checksum.
6. Frees GPU memory and prints performance/verification results.

History-based simulation is explicitly not implemented in the CUDA path. The CUDA code only supports event-based simulation.

### Main computational algorithm
Each event-based lookup represents one independent neutron cross-section query.

For each lookup:
1. A deterministic pseudo-random seed is derived from the lookup index using a fast-forwarded linear congruential generator.
2. A neutron energy sample is generated.
3. A material ID is selected using a probability distribution.
4. A macroscopic cross-section vector of length 5 is computed for that material and energy.
5. The maximum-valued cross-section channel is found.
6. A small integer derived from that maximum index is written to a verification array.

The macroscopic cross section is computed by:
1. Iterating over all nuclides in the selected material.
2. For each nuclide, finding bounding energy grid points.
3. Interpolating five microscopic cross-section values.
4. Multiplying the microscopic values by that nuclide’s concentration.
5. Accumulating into the material-level macroscopic cross-section vector.

### Supported grid lookup modes
The code supports three grid-search modes:

#### NUCLIDE grid
Each nuclide’s own energy grid is binary-searched independently for every nuclide in the material.

#### UNIONIZED grid
A global unionized energy array is binary-searched once per lookup. The resulting unionized-grid index is used to index an acceleration table mapping each isotope to the corresponding nuclide-grid index.

#### HASH grid
A hash bin is computed from the neutron energy. The hash table provides approximate lower/upper index bounds into each nuclide grid, followed by a bounded binary search.

### Optimization variants
The baseline kernel performs sampling and lookup in one kernel, with one GPU thread per lookup.

The optimized variants split sampling from lookup and then use increasingly aggressive grouping/sorting:
- Optimization 1: separate sampling and lookup kernels.
- Optimization 2: one lookup kernel launch per material.
- Optimization 3: one lookup kernel for fuel and one for non-fuel.
- Optimization 4: sort by material, then launch material-specific kernels over compact ranges.
- Optimization 5: partition fuel/non-fuel, then launch two compact-range kernels.
- Optimization 6: sort by material and then by energy within each material, then reuse the Optimization 4 lookup kernel.

The optimizations are intended to reduce warp divergence and improve cache locality by grouping lookups with similar control flow and memory access behavior.

#### cudaMemcpy
Used in `move_simulation_data_to_device` to copy initialized CPU arrays into device allocations.

All copies are host-to-device copies:
- `cudaMemcpyHostToDevice`

#### cudaFree
Used in `release_device_memory` to free selected device allocations.

Important note: `release_device_memory` frees:
- `num_nucs`
- `concs`
- `mats`
- `unionized_energy_array`
- `nuclide_grid`
- `verification`

It does not free:
- `index_grid`
- `p_energy_samples`
- `mat_samples`

This omission should be preserved unless the translation is intentionally allowed to fix memory leaks.

#### cudaDeviceSynchronize
Used after memory initialization and after kernel/library operations to enforce completion and catch asynchronous errors.

Appears in:
- `move_simulation_data_to_device`
- all `run_event_based_simulation_*` functions

#### cudaPeekAtLastError
Used after kernel launches and some Thrust operations to check for pending CUDA errors.

#### cudaGetDevice and cudaGetDeviceProperties
Used in `print_inputs` to query and print the CUDA device name.

In a SYCL translation, this should map to querying the selected `sycl::queue` device.

### Thrust device algorithms

The program uses Thrust with `thrust::device` execution policy. These calls execute on the GPU and should be treated as device-side parallel operations in the translation.

Used algorithms:
- `thrust::reduce`
- `thrust::count`
- `thrust::sort_by_key`
- `thrust::partition`

Roles:
- `thrust::reduce` reduces the device verification array to a scalar checksum.
- `thrust::count` counts lookups belonging to a given material.
- `thrust::sort_by_key` sorts material IDs while carrying energy samples, or sorts energy samples within material ranges.
- `thrust::partition` is used in Optimization 5 to group fuel-related lookups.

These Thrust calls will need SYCL/DPC++ equivalents or explicit kernels/oneDPL equivalents using the same queue.

---

### CUDA execution configuration

Kernels are launched with one-dimensional grids and one-dimensional blocks.

Common launch patterns:
- Baseline: 256 threads per block.
- Optimized sampling/lookup variants: 32 threads per block.
- Number of blocks is computed using ceiling division based on lookup count or material-specific lookup count.

Each kernel computes a global thread index using block index, block dimension, and thread index.

---

### Shared memory
No CUDA `__shared__` memory is used.

All per-thread temporary arrays, such as `macro_xs_vector[5]` and `xs_vector[5]`, are automatic local arrays. Depending on compiler register pressure, these may reside in registers or local memory.

---

### Atomics
No CUDA atomic operations are used.

Each thread writes to a unique verification index, so no atomic update is required. The final reduction is performed separately using Thrust.

---

### CUDA-specific qualifiers and pointer attributes

#### `__restrict__`
Several device function pointer parameters use `__restrict__` to inform the compiler that the pointed-to memory regions do not alias. This affects optimization but not program semantics.

#### Structs passed by value to kernels
Both `Inputs` and `SimulationData` are passed by value to kernels. `SimulationData` contains device pointers after `move_simulation_data_to_device` creates the GPU-side shallow copy.

## 3. GPU kernel structure and thread/block organization

### Common indexing pattern
All kernels use a one-dimensional global thread ID:
- logical lookup index = block ID times block size plus thread ID.

Most kernels immediately return if the computed index is outside the active lookup range.

This establishes one GPU thread per logical lookup, except that some optimized kernels launch over filtered or compacted ranges.

---

### `xs_lookup_kernel_baseline`

#### Launch configuration
- Threads per block: 256.
- Blocks: ceiling of `in.lookups / 256`.

#### Work per thread
Each thread:
1. Computes lookup index `i`.
2. Returns if `i >= in.lookups`.
3. Initializes RNG seed and fast-forwards by `2*i`.
4. Generates neutron energy.
5. Picks material.
6. Computes macroscopic cross section.
7. Finds maximum channel among five values.
8. Writes `max_idx + 1` to `GSD.verification[i]`.

#### Performance characteristics
This kernel has substantial divergence because different threads in a warp may select materials with very different numbers of nuclides. Fuel material has many more nuclides than other materials.

---

### `sampling_kernel`

#### Launch configuration
Used by optimized variants.
- Threads per block: 32.
- Blocks: ceiling of `in.lookups / 32`.

#### Work per thread
Each thread:
1. Computes lookup index `i`.
2. Returns if `i >= in.lookups`.
3. Fast-forwards the RNG by `2*i`.
4. Generates energy and material samples.
5. Stores them into:
   - `GSD.p_energy_samples[i]`
   - `GSD.mat_samples[i]`

This separates sampling from lookup.

---

### `xs_lookup_kernel_optimization_1`

#### Launch configuration
- Threads per block: 32.
- Blocks: ceiling of `in.lookups / 32`.

#### Work per thread
Each thread:
1. Reads precomputed energy and material samples.
2. Computes macroscopic cross section.
3. Writes verification result.

This is similar to the baseline lookup phase but without RNG work inside the lookup kernel.

---

### `xs_lookup_kernel_optimization_2`

#### Launch configuration
Launched 12 times, once for each material ID.
- Threads per block: 32.
- Blocks: ceiling of `in.lookups / 32`.

#### Work per thread
Each thread:
1. Computes lookup index `i`.
2. Returns if `i >= in.lookups`.
3. Reads `mat = GSD.mat_samples[i]`.
4. Returns if `mat != m`, where `m` is the material handled by that launch.
5. Performs lookup only for matching material.
6. Writes verification result.

This groups execution by material at the kernel-launch level but still launches over the full lookup range each time.

---

### `xs_lookup_kernel_optimization_3`

#### Launch configuration
Launched twice:
- once with `is_fuel = 0`
- once with `is_fuel = 1`

Each launch uses:
- Threads per block: 32.
- Blocks: ceiling of `in.lookups / 32`.

#### Work per thread
Each thread:
1. Computes lookup index.
2. Reads material sample.
3. Performs lookup only if the thread belongs to the selected fuel/non-fuel category:
   - `is_fuel == 1` and `mat == 0`
   - or `is_fuel == 0` and `mat != 0`
4. Writes verification result.

The first launch processes non-fuel material lookups, and the second launch processes fuel lookups.

---

### `xs_lookup_kernel_optimization_4`

#### Launch configuration
Used by Optimization 4 and reused by Optimization 6.

For each material:
- Threads per block: 32.
- Blocks: ceiling of `n_lookups_per_material[m] / 32`.

#### Work per thread
Each thread:
1. Computes local index `i`.
2. Returns if `i >= n_lookups`.
3. Adds `offset` to map into the sorted global sample arrays.
4. Reads material and verifies it matches `m`.
5. Computes lookup.
6. Writes verification result at the sorted/global index.

Because data has been sorted by material, each launch operates on a compact range.

---

### `xs_lookup_kernel_optimization_5`

#### Launch configuration
Launched twice after fuel/non-fuel partitioning:
1. Fuel range:
   - `n_lookups = n_fuel_lookups`
   - `offset = 0`
2. Non-fuel range:
   - `n_lookups = in.lookups - n_fuel_lookups`
   - `offset = n_fuel_lookups`

Threads per block: 32.

#### Work per thread
Each thread:
1. Computes local index.
2. Returns if outside range.
3. Adds offset.
4. Reads energy and material sample.
5. Computes lookup.
6. Writes verification result.

Unlike Optimization 4, this kernel does not check material identity after applying the offset.

## 5. Asymmetric or potentially incorrect bounds, comparisons, and offsets that MUST be preserved

The following constructs are asymmetric, surprising, or potentially incorrect, but they are part of the current program behavior. They should be preserved verbatim in any behavior-preserving translation.

### `pick_mat` cumulative-distribution loop excludes material 0
In `pick_mat`, the inner accumulation loop starts at `j = i` and uses the condition `j > 0`.

This means:
- `dist[0]` is never included in the accumulated probability.
- For `i = 0`, the inner loop does not execute, so material 0 cannot be selected by the normal cumulative check.
- Material 0 is selected only by the final fallback return.

This `j > 0` condition is intentional for translation purposes and MUST be preserved verbatim.

---

### `pick_mat` resets `running` inside the outer loop
In `pick_mat`, `running` is initialized to zero inside each iteration of the outer loop over `i`.

This recomputes a partial cumulative sum from scratch for each `i`, excluding `dist[0]`.

This behavior MUST be preserved.

---

### `pick_mat` fallback returns material 0
If no cumulative probability test succeeds, `pick_mat` returns material 0.

Given the excluded `dist[0]`, this fallback is how fuel material is selected for the upper tail of the random distribution.

This fallback behavior MUST be preserved.

---

### Hash-grid lower-bound edge case uses absolute grid endpoints
In `calculate_micro_xs`, for the HASH grid path:
- If `p_energy <= e_low`, the code sets the lower index to 0.
- If `p_energy >= e_high`, the code sets the lower index to `n_gridpoints - 1`.

These choices use absolute nuclide-grid endpoints rather than the local hash-bin bounds `u_low` or `u_high`.

This is potentially surprising but MUST be preserved.

---

### High-end grid guard shifts the low pointer backward
In `calculate_micro_xs`, when the selected index is `n_gridpoints - 1`, the code uses the previous grid point as the low point so that `high = low + 1` remains valid.

This appears in multiple lookup paths:
- NUCLIDE grid path.
- UNIONIZED grid path.
- HASH grid path.

The offset behavior MUST be preserved.

---

### Unionized-grid initialization uses grid point `+1` for initial high energy
During unionized-grid acceleration-table construction, `energy_high[i]` is initialized from nuclide grid index 1 rather than index 0.

The logic then tracks `idx_low` and prevents it from advancing beyond `n_gridpoints - 2`.

This offset pattern MUST be preserved.

---

### Unionized-grid acceleration table caps `idx_low` at `n_gridpoints - 2`
In the unionized-grid construction, when `idx_low[i] == in.n_gridpoints - 2`, the code stores that index and does not advance further.

This avoids producing an index whose subsequent high point would be out of range.

This comparison and cap MUST be preserved.

---

### Binary searches return the lower index
Both grid-search functions use a loop condition equivalent to `length > 1` and return the lower bound index, not the upper bound or exact-match index.

This applies to:
- `grid_search`
- `grid_search_nuclide`

This lower-index return behavior MUST be preserved.

---

### RNG fast-forward uses `2*i`
Both the baseline kernel and `sampling_kernel` fast-forward the random seed by `2*i`.

This is because each lookup consumes two random numbers:
1. one for energy,
2. one for material selection.

The exact `2*i` offset MUST be preserved.

---

### Verification writes use sorted or partitioned indices
In optimized variants that sort or partition lookup samples, verification values are written to the current reordered index, not the original lookup index.

Because the final checksum is a reduction, the order does not matter for the checksum. However, the exact write-index behavior MUST be preserved.

---

### Optimization 4 and Optimization 6 use offset-adjusted compact ranges
`xs_lookup_kernel_optimization_4` first checks the local compact index against `n_lookups`, then adds `offset`.

This order is important:
1. bounds check on local range,
2. then offset addition.

This ordering MUST be preserved.

---

### Optimization 4 still checks material identity after sorting
Even though Optimization 4 sorts by material and launches compact material-specific ranges, the kernel still checks whether `mat != m` and returns if so.

This redundant-looking check MUST be preserved.

---

### Optimization 5 does not check material identity after partitioning
Unlike Optimization 4, `xs_lookup_kernel_optimization_5` does not verify fuel/non-fuel material identity after applying the offset.

This difference MUST be preserved.

---

### Possible zero-block launches
In Optimization 4, Optimization 5, and Optimization 6, the number of blocks can become zero if the material-specific or partition-specific lookup count is zero.

CUDA zero-block launches may be invalid or implementation-sensitive depending on context. A SYCL translation should preserve the effective behavior carefully, likely by avoiding work for zero-sized ranges while preserving observable results.

---

### XXL grid-point assignment uses floating-point multiplication assigned to an integer field
For the XXL benchmark size, the code assigns `238847 * 2.1` to `input.n_gridpoints`, which is an integer-like field.

This involves floating-point multiplication followed by conversion/truncation to the destination type.

This behavior MUST be preserved.

---

### Optimization 5 Thrust partition usage is unusual
Optimization 5 calls Thrust partition with `GSD.mat_samples` and `GSD.p_energy_samples` together and the predicate `is_mat_fuel`, whose predicate checks whether its argument equals zero.

This is a potentially delicate or unusual use of Thrust partitioning and may not correspond to a full key/value pair reorder in the way `sort_by_key` does.

The exact data-movement semantics of this call MUST be matched in the translation.

---

### Device memory release omits some allocations
`release_device_memory` does not free `GSD.index_grid`.

The optimized simulation functions allocate `GSD.p_energy_samples` and `GSD.mat_samples`, but these are not freed by `release_device_memory`.

This is likely a memory leak, but it is part of the current resource-management behavior and should not be silently changed unless the translation is explicitly allowed to fix leaks.
